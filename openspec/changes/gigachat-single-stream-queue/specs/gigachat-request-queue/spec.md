## Purpose

Не даёт боту самому выбивать себя из единственного потока GigaChat (второй одновременный запрос получает HTTP 429): все обращения процесса к API идут по одному, а запросы, которых ждёт пользователь, обслуживаются раньше фоновой работы планировщика.

## ADDED Requirements

### Requirement: Один запрос к API GigaChat за раз
Система SHALL выполнять в пределах процесса не более одного запроса к API GigaChat одновременно — независимо от того, откуда он сделан (цикл планировщика, команды и кнопки бота, Mini-App, панель модерации) и что делает (генерация ответа, загрузка файла, удаление файла, список моделей). Запрос, пришедший, пока поток занят, SHALL ждать своей очереди, а не отправляться параллельно. Получение OAuth-токена SHALL выполняться вне этого ограничения.

#### Scenario: Пользовательский запрос во время фоновой генерации
- **WHEN** планировщик ждёт ответа GigaChat на саммари, а в этот момент пользователь нажимает «Сделать саммари» в Mini-App
- **THEN** запрос пользователя отправляется в GigaChat только после завершения запроса планировщика, и ни один из них не получает 429 из-за другого

#### Scenario: Одновременные запросы из Mini-App
- **WHEN** два пользователя почти одновременно запрашивают саммари двух разных документов из Mini-App
- **THEN** запросы к GigaChat выполняются друг за другом, а не параллельно

#### Scenario: OCR занимает поток целиком по шагам
- **WHEN** выполняется OCR документа (загрузка PDF, распознавание, удаление файла)
- **THEN** каждый из этих шагов выполняется как отдельный запрос к API по очереди, одновременно с ним другие запросы к API GigaChat из процесса не выполняются

#### Scenario: Обновление токена
- **WHEN** запросу нужен новый OAuth-токен
- **THEN** получение токена не считается запросом к API GigaChat и не ограничивается очередью

### Requirement: Пользовательские запросы раньше фоновых
Запросы к GigaChat, сделанные ради пользователя (принудительная саммаризация, включая OCR, из бота, Mini-App и панели модерации), SHALL обслуживаться раньше всех ожидающих фоновых запросов (всё, что делает планировщик: саммари и OCR новых документов, оценка важности, добор оценок, фоновое саммари, пятничная «попытка 2»). Внутри каждого из двух классов запросы SHALL обслуживаться в порядке поступления. Уже выполняющийся запрос SHALL доводиться до конца и не прерываться ради пользовательского.

#### Scenario: Пользователь обходит ожидающий фон
- **WHEN** поток занят, в очереди ждут три фоновых запроса, и приходит пользовательский запрос
- **THEN** следующим после текущего выполняется пользовательский запрос, а фоновые — после него в прежнем порядке

#### Scenario: Выполняющийся фоновый запрос не прерывается
- **WHEN** выполняется фоновый OCR, и приходит пользовательский запрос
- **THEN** пользовательский запрос ждёт завершения OCR и выполняется сразу после него

#### Scenario: Порядок среди пользователей
- **WHEN** пользователи A, затем B отправили запросы, пока поток занят
- **THEN** запрос A выполняется раньше запроса B

#### Scenario: Фон при постоянной пользовательской нагрузке
- **WHEN** пользовательские запросы поступают непрерывно
- **THEN** фоновые запросы ждут, пока в очереди не останется ожидающих пользовательских; планировщик не падает и продолжает работу после освобождения очереди

### Requirement: Ожидание в очереди без потолка
Время ожидания в очереди SHALL не ограничиваться: запрос ждёт своей очереди сколько потребуется и не завершается ошибкой из-за долгого ожидания. Таймаут HTTP-запроса SHALL отсчитываться с момента отправки запроса в GigaChat, а не с момента постановки в очередь.

#### Scenario: Долгое ожидание за OCR
- **WHEN** пользовательский запрос ждёт в очереди дольше таймаута HTTP-запроса, пока выполняется длинный запрос
- **THEN** после освобождения потока он отправляется с полным таймаутом и не считается упавшим по таймауту

### Requirement: Повторы без потери очереди
Повтор запроса после временной ошибки (HTTP 429, 5xx, сетевая ошибка, таймаут) SHALL выполняться до того, как поток будет отдан следующему запросу из очереди: пока запрос не выполнен успешно или не исчерпал попытки, другие запросы к API GigaChat из процесса не отправляются.

#### Scenario: 429 от постороннего потребителя ключа
- **WHEN** запрос получил 429 (поток занят другим процессом с тем же ключом), а в очереди ждут другие запросы
- **THEN** запрос повторяется после паузы, ожидающие запросы не отправляются между попытками и не получают 429 вместо него

### Requirement: Отмена ожидания не блокирует очередь
Если вызывающий код отменяет запрос, пока тот ждёт очереди, система SHALL убрать его из очереди без отправки в GigaChat, и это SHALL не задерживать и не блокировать остальные запросы. Если отмена пришла в момент, когда очередь уже дошла до этого запроса, поток SHALL сразу передаваться следующему ожидающему.

#### Scenario: Отменён ожидающий запрос
- **WHEN** ожидающий в очереди запрос отменён
- **THEN** он не отправляется в GigaChat, следующий запрос в очереди выполняется в обычном порядке

#### Scenario: Отменён выполняющийся запрос
- **WHEN** выполняющийся запрос к GigaChat отменён
- **THEN** поток освобождается, и следующий ожидающий запрос отправляется

### Requirement: Число вызовов впереди пользовательского запроса
Система SHALL позволять в любой момент узнать, сколько запросов к API GigaChat будет обслужено раньше нового пользовательского запроса: выполняющийся запрос (если поток занят) плюс уже ожидающие пользовательские запросы. Ожидающие фоновые запросы SHALL в это число не входить. Получение значения SHALL не менять очередь.

#### Scenario: Поток свободен
- **WHEN** ни один запрос не выполняется и никто не ждёт
- **THEN** число вызовов впереди равно 0

#### Scenario: Поток занят фоном, ждут фоновые
- **WHEN** выполняется фоновый запрос и ждут пять фоновых
- **THEN** число вызовов впереди равно 1

#### Scenario: Поток занят, ждут пользовательские
- **WHEN** выполняется запрос и ждут два пользовательских и три фоновых
- **THEN** число вызовов впереди равно 3

### Requirement: Ожидание очереди видно в логе
Если запросу пришлось ждать очереди, система SHALL записать в лог его класс (пользовательский или фоновый) и сколько он ждал. Запрос, отправленный без ожидания, SHALL не порождать такой записи.

#### Scenario: Запрос ждал
- **WHEN** пользовательский запрос ждал очереди 12 секунд
- **THEN** в логе есть запись об ожидании пользовательского запроса около 12 секунд

#### Scenario: Запрос не ждал
- **WHEN** запрос отправлен сразу, поток был свободен
- **THEN** записи об ожидании в логе нет
