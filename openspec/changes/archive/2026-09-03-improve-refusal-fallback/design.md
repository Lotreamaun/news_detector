## Context

См. proposal.md — Why и What Changes. Текущая детекция отказа — `looks_like_refusal(text)` в `app/services/gigachat.py:483` — хэнд-шейпанный список `_REFUSAL_MARKERS` (подстрока) с жёстким лимитом длины ответа (2000 символов). Промахи бывают двух типов: новая формулировка, которой нет в списке, и длинный дисклеймер, который режется лимитом. Пользователь получал «лонгрид» с текстом отказа в путях: фоновый daily, кнопка «Сделать саммари» (`handlers.py:638` через `Summarizer.summarize`), `/summary`, OCR (`ocr_document_text`). Фолбэк-уведомление при `article.summary is None` уже есть (`scheduler._build_notification`, строка «Содержание этого закона пока не доступно…» + ссылка) — нужно гарантировать, что отказ всегда уходит в этот путь, а не просачивается как «саммари»/текст.

## Goals / Non-Goals

**Goals:**
- Поднять полноту распознавания отказов до целевых 70–80% на реальных формулировках GigaChat, не повышая ложные срабатывания (естественное саммари/OCR не должно резаться).
- Гарантировать, что распознанный отказ нигде не превращается в `summary`/`original_text`/уведомление с сырым текстом — всегда идёт фолбэк со ссылкой на оригинал.
- Отличить «отказ» от «временной ошибки» там, где это меняет сообщение пользователю.

**Non-Goals:**
- Не менять схему БД и внешний API.
- Не добавлять новых внешних зависимостей/LLM-провайдеров.
- Не трогать логику месячных лимитов принудительной саммаризации.
- Не гарантировать 100% детекцию (эвристика намеренно консервативна к ложным срабатываниям).

## Decisions

### D1: Гибридная эвристика вместо чистого списка маркеров
Заменить одиночный список подстрок на **гибрид**: (а) расширенный, но структурированный набор маркеров-фраз (разбитых на группы: «нет мнения/отказ/этический лимит/чувствительные темы/служебный дисклеймер», RU+EN) + (б) **легковесные паттерны-шаблоны** (например, regex на «(не )?(может|могу|в состоянии|имею права).{0,60}(отказа|огранич|чувствительн|мнени)»), которые ловят синонимичные перефразировки, не попадающие в точные маркеры.
Рациональность: точные маркеры дают низкий FP, паттерны расширяют recall. Alternative (отклонено): подключение LLM-классификатора (ещё один запрос GigaChat) — дорого и само может отказать; string-эвристика достаточна для 70–80%.

### D2: Порог по доле маркерного «мусора», а не по длине
Вместо жёсткого `len > 2000 → не отказ` использовать **два уровня**: короткие ответы (≤ ~600 символов) решаются по любому маркеру/паттерну; длинные (> 600) — только по «сильным» маркерам (точные фразы-буклеты вида «не обладает собственным мнением», «сгенерирован нейросетевой моделью»), которых не бывает в содержательном саммари. Это убирает промах длинного дисклеймера, сохраняя низкий FP на длинных настоящих саммари.

### D3: Единый сторожевой модуль и точка отказа→None
Добавить модуль-обёртку (например, в `gigachat.py`: функция `classify_reply(text) -> Literal["content","refusal","empty"]`), а `looks_like_refusal` сделать тонкой обёрткой над ним. Все потребители (`Summarizer.summarize`, `ocr_document_text`) SHALL звать один этот классификатор. При `"refusal"`/`"empty"` — результат не используется: `summarize` бросает `GigaChatError`, `ocr_document_text` возвращает `None`. Это устраняет рассинхронизацию, когда одна точка ловит, а другая нет.
### D4: Сообщение-фолбэк различает отказ и временную ошибку

В путях принудительной саммаризации (`handlers.py` `except GigaChatError`) сейчас шлётся отдельный короткий текст. По фидбеку: фолбэк встраивается **в тело уведомления на место саммари** — название, ссылка на портал и кнопка «Полный текст» (WebApp) остаются (helper `_summary_refused`), отдельное сообщение не шлётся. Текст отказа нейтрален к провайдеру: «Языковая модель отказалась сформировать саммари… Распознанный текст доступен по кнопке «Полный текст»». Временная ошибка — «Не удалось сделать саммари. Попробуйте позже.» Фоновая daily уже даёт корректный фолбэк через `_build_notification` — там текст менять не обязательно, но унифицировать формулировку желательно.

### D5: Тестовая матрица формулировок
Завести регрессионный набор реальных формулировок отказа (включая обе, что попадали при тестах) + негативный набор настоящих саммари. Проверка полноты/ложных срабатываний — через этот набор, целевая достижимость 70–80% по нему.

## Risks / Trade-offs

- [Паттерны дают ложные срабатывания на необычных саммари] → Ограничить паттерны «сильными» комбинациями (отказ+ограничение/мнение вместе), держать порог `content`-ветки по «сильным» маркерам для длинных ответов; покрыть негативным набором в D5.
- [Длинный дисклеймер всё ещё просачивается] → D2 + расширяемая матрица; если конкретная формулировка вновь просочится — добавить в набор и маркер.
- [Накопительная сложность хэндшейпа] → Маркеры/паттерны структурированы по группам и живут в одном модуле + тестовая матрица, чтобы правки были точечными.

## Migration Plan

- Обратная совместимость: подпись `looks_like_refusal` сохраняется, добавление `classify_reply` не ломает существующие вызовы.
- Деплой: изменение только в коде детекции и сообщений; БД/API без миграций.
- Rollback: вернуть предыдущую версию `gigachat.py`/сообщений.
