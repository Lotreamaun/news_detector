## Context

БД — один файл SQLite, путь к которому кодируется в `DATABASE_URL`
(`sqlite+aiosqlite:///./data/news_detector.db`, см. `app/core/config.py`,
`app/core/database.py::init_database`). В проде (см. `deploy-to-dockhost`) `./data`
смонтирован bind-mount volume'ом — файл живёт вне контейнера, но ничего не мешает снести его
одной неверной командой (`rm`, неудачный скрипт миграции), как уже случилось локально.
Периодические задачи в проекте уже реализованы через PTB `JobQueue`
(`app/main.py::_schedule_jobs`, `check_legislation_updates`), с тем же обходом
`run_repeating(first=0)` через ручной вызов при старте (`_run_initial_check`). Мотивация и
контракт поведения — см. `proposal.md` и `specs/db-backup/spec.md`.

## Goals / Non-Goals

**Goals:**
- Автоматические, консистентные, ротируемые бэкапы SQLite-файла без ручных действий.
- Не уронить и не замедлить бота при сбое бэкапа (диск полон, нет прав и т.п.).
- Минимум нового кода и конфигурации, никаких новых внешних зависимостей (KISS).

**Non-Goals:**
- Восстановление автоматизацией/bot-командой — только ручная процедура (см. Migration Plan).
- Офсайт-хранение (Telegram/S3) — по решению пользователя оставлено локальной ротацией на
  диске в этом change; можно добавить отдельным change позже, если понадобится.
- Бэкап иных СУБД, кроме SQLite — проект их не использует (см. `DATABASE_URL` в `.env.example`).
- Проверка целостности бэкапа через открытие файла отдельным подключением после копирования
  (`PRAGMA integrity_check`) — не входит в v1, см. Open Questions.

## Decisions

**Механизм копирования: `sqlite3.Connection.execute("VACUUM INTO ?", (path,))`, а не
`shutil.copy`/`shutil.copyfile` файла.**
`aiosqlite`/SQLite — файл на диске, в который бот пишет в фоне (WAL или rollback journal).
Побайтовое копирование файла ОС во время активной записи может захватить файл в
промежуточном состоянии и дать нечитаемую или тихо повреждённую копию — именно то, от чего
должен защищать фолбэк. `VACUUM INTO` — штатная команда SQLite (с версии 3.27, доступна в
`aiosqlite`/стандартном `sqlite3`), создаёт консистентный, транзакционно-безопасный снимок
БД в новый файл, попутно компактизируя его (меньше места, чем raw-копия с фрагментацией).
Открывается синхронным `sqlite3` в отдельном потоке (`asyncio.to_thread`), чтобы не
блокировать event loop бота на время копирования.

**Путь к файлу БД берётся из `config.DATABASE_URL`, не из отдельной новой переменной.**
Один источник истины про расположение БД — тот же, что использует `init_database()`. Функция
разбора SQLAlchemy-URL вида `sqlite+aiosqlite:///./data/news_detector.db` →
`./data/news_detector.db` — несколько строк (`URL.database` через
`sqlalchemy.engine.make_url` уже в зависимостях проекта). Если схема URL не начинается с
`sqlite`, бэкап-job не регистрируется (см. Requirement «Отсутствие поддержки для не-SQLite
БД»).

**Ротация: по количеству файлов (`DB_BACKUP_RETENTION_COUNT`), не по возрасту.**
Проще реализовать и объяснить (сортировка по имени/mtime, удалить лишние сверх N) чем
парсить возраст и учитывать часовые пояса; имя файла кодирует timestamp
(`news_detector_YYYYMMDD_HHMMSS.db`), так что сортировка по имени = сортировка по времени.

**Уведомление о сбое через `ADMIN_CHAT_IDS` + `context.bot.send_message`.**
`ADMIN_CHAT_IDS` уже существует в конфиге (сейчас используется только для снятия лимита
`/summary`), переиспользуется без новой переменной. Паттерн отправки — тот же
`context.bot.send_message` с обработкой `Forbidden`, что и в
`app/services/scheduler.py` при обычных уведомлениях: один заблокировавший бота админ не
должен ронять рассылку остальным. Успешные бэкапы уведомлений не шлют (не спамить) — только
сбои.

**Размещение кода: новый `app/services/backup.py`.**
Бизнес-логика (файловые операции, работа с SQLite, оркестрация ротации) — по слоям проекта
это `app/services/`, не `app/core/` (который отвечает за infra подключения, а не за бэкапы) и
не `app/bot/` (нет Telegram-хендлеров, только job-callback, который регистрируется в
`app/main.py`, как и `check_legislation_updates`).

**Альтернатива, которая была отклонена: `Application.job_queue.run_once` для стартового
бэкапа отдельно от `_run_initial_check`.**
Проще переиспользовать уже существующий `_post_init` hook и вызвать бэкап-функцию напрямую
(как это уже сделано для `_run_initial_check`), чем заводить второй `run_once(when=0)` —
меньше кода, тот же самый обход известной ловушки PTB/APScheduler.

## Risks / Trade-offs

- [Риск] Локальная ротация на диске не защищает от потери всего volume/диска целиком (только
  от удаления/порчи конкретно файла БД) → **Митигация**: осознанно принято пользователем для
  v1 (см. вопросы при `/opsx:propose`); офсайт-хранение — возможное расширение отдельным
  change, если появится реальный риск потери всего `./data`.
- [Риск] `VACUUM INTO` компактизирует БД — при очень большой БД может занять заметное время и
  временно нагрузить диск/CPU → **Митигация**: для этого проекта БД — таблицы пользователей,
  фильтров и статей за разумный период, размер на порядки меньше, чем нужно для проблемы;
  явно не оптимизируем на будущее (KISS, YAGNI).
- [Риск] Уведомление о сбое бэкапа само может не дойти (все админы заблокировали бота) →
  **Митигация**: ошибка в любом случае остаётся в `app.log` — уведомление в Telegram
  дополнительный, не единственный канал.
- [Риск] Если `DB_BACKUP_INTERVAL_HOURS` слишком велик, а инцидент («снёс БД») происходит
  вскоре после последнего бэкапа — теряются изменения за интервал → **Митигация**: дефолт 24
  часа и бэкап сразу при старте — разумный компромисс между свежестью и нагрузкой для
  пет-проекта; значение настраивается через `.env` без правки кода.

## Migration Plan

Новый функционал, миграции данных не требуется — только новая переменная окружения и
поведение при старте.

Восстановление (ручная процедура, добавляется в README):
1. Остановить бота (`docker compose down` или локально прервать процесс) — не восстанавливать
   поверх файла, в который параллельно идёт запись.
2. Выбрать нужный файл в `DB_BACKUP_DIR` (обычно самый свежий по имени/времени).
3. Скопировать его поверх текущего пути из `DATABASE_URL`
   (например `cp data/backups/news_detector_20260920_030000.db data/news_detector.db`).
4. Запустить бота заново (`docker compose up -d` / `python -m app.main`).
5. Смоук-тест: `/start`, `/latest` — убедиться, что пользователи/фильтры/статьи на месте.

Откат самого фича-change: удалить/не задавать `DB_BACKUP_*` переменные и не запускать job —
поведение бота вне бэкапа не меняется, откатывать нечего.

## Open Questions

- Стоит ли добавить `PRAGMA integrity_check` на свежесозданном файле бэкапа перед тем, как
  считать его успешным (сейчас успех = `VACUUM INTO` не бросил исключение) — не меняет
  спеку/подход/разбивку задач, можно добавить позже как небольшое усиление надёжности, если
  на практике возникнут повреждённые бэкапы.
