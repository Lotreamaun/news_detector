## Context

См. proposal.md — Why. Сейчас `handlers.py` содержит dev-команды `test_gigachat`/`notify_me`/`myid_command` (нет в прод-спеке), `latest` показывает последние 10 `Article` без фильтра и с саммари (до 200 симв), `main._run_initial_check` прогоняет `job.run` на старте и рассылает все пропущенные законы (100+ для нового юзера), `start` шлёт «в разработке». Нужно привести к MVP.

## Goals / Non-Goals

**Goals:**
- Удалить dev-поверхность (`/test`, `/notify_me`, `/myid`) из хендлеров, регистрации и `BotCommand` списка, проверить `grep` на остатки.
- `/latest` — 10 последних **за последние 30 дней в хронологическом порядке** по подпискам (дефолт для нового — `[Конституция, ФКЗ, ФЗ]` с подсказкой «например, юристу по крипте», иначе фильтры; `Все` — без фильтра), заголовок «Законы за последние 30 дней», только заголовок+ссылка, без `summary`.
- Старт без спама: первый запуск после деплоя не рассылает старые `external_id` (только новые после `first_run`).
- Приветствие `/start` — ценность + CTA (`/latest`, `/settings`), без «в разработке», с учётом онбординга `law-force-filter` и примером + кнопка `[🔍 Показать пример уведомления]` (последний FZ) для демо.
- Лимит `/summary` 10/мес не для Конституции/ФКЗ/ФЗ (авто-саммари без кнопки), фолбэк при недоступности GigaChat/pravo (без саммари + ссылка) и обработка Telegram `429`/`403`.

**Non-Goals:**
- Не менять классификаторы сфер/регионов — они в своих change.
- Не добавлять новые зависимости.
- Не трогать `ADMIN_CHAT_IDS`/`WEBAPP` — остаётся.

## Decisions

### 1. Удаление dev-команд — grep + удаление целиком
Удаляем `test_gigachat`, `notify_me`, `myid_command`, их `CommandHandler` и `BotCommand` из `main._register_commands`, `HELP_TEXT`. Проверяем `rg "notify_me|myid|test_gigachat"` и `rg "TELEGRAM_PROXY"` — прокси оставляем (нужен в РФ). Альтернатива — оставить за флагом `DEBUG` — отклонена, в проде не нужно.

### 2. `/latest` — подписочно-ориентированный, без саммари, с дефолтом, 30 дней
Переписать `handlers.latest`: получить `user` → `levels = _get_user_levels(...)` (если пусто — дефолт `[Конституция, FKZ, FZ]`), `spheres`/`region` аналогично (пока только `level` из `law-force-filter`, остальные — заглушка `if spheres: where`). Строить `select(Article).where(Article.published_at >= now-30d).where(Article.level.in_(levels))` только если фильтр не пустой (дефолт считается непустым), `order_by(Article.published_at.desc())`, `limit(10)`. Заголовок сообщения — `*Законы за последние 30 дней*` перед списком. Рендер: `f"*{title_esc}*\n\n{_full_text_block(url)}"` без `summary`, `parse_mode="MarkdownV2"`. Если пусто — «Пока нет законов за последние 30 дней по вашим фильтрам. Настройте: /settings».

Почему без саммари: `/latest` — быстрый обзор заголовков, саммари — в уведомлении/WebApp, экономит токены и место.
Почему дефолт `[Конституция,ФКЗ,ФЗ]` а не «Все»: новый юзер без настройки получает самые важные акты, а не шум из 89 регионов/ведомственных — снижает спам на старте.
Почему 30 дней и `published_at DESC`: хронологический порядок за месяц — ожидаемо для «последних», не «последних 10 вообще» (может быть старье).

### 3. Старт без спама — флаг `initial_sync_done` vs отметка времени
Выбираем простую отметку: при `init_db_schema` создаём `kv_store` или используем `Article` с `max(external_id)`? Проще: в `scheduler._filter_new_entries` уже есть идемпотентность по `external_id`, но спам происходит потому что `_run_initial_check` прогоняет `check_legislation_updates` сразу и находит 30 новых `external_id` для пустой БД. Для нового юзера с пустой БД — это старые законы, которые он не должен получить. Решение: при первом запуске после деплоя — не рассылать, а только сохранить `Article` без `notify`. Реализуем флаг `is_first_run` в `context.bot_data` или проверку `users count == 0` → `notify = False` на первом прогоне. Альтернатива — хранить `last_checked` в БД — тяжелее. Выбираем `is_first_run` + проверка `if not users: log + save without notify`.

Дополнительно: Telegram rate limiting — при 10 юзерах не критично, при 100+ — риск бана. Добавляем в `scheduler._notify_users` простой `await asyncio.sleep(0.05)` между отправками, `try/except` для `RetryAfter` (429 → `sleep(retry_after) + retry`) и `Forbidden` (403 → `is_active=False`). Для MVP 10 юзеров — терпимо, но заложить.

### 4. Приветствие — актуализация + пример уведомления
`handlers.start`: для нового — «Привет! Присылаю саммари новых законов по твоим фильтрам...» + Inline-кнопка `[🔍 Показать пример уведомления]` (`callback_data=show_example`) → хендлер `show_example` берёт последний `FZ` (`SELECT ... WHERE level='FZ' ORDER BY published_at DESC LIMIT 1`, fallback любой `level='FZ'` или последний вообще) и шлёт через `_build_notification` как тестовое уведомление (с кнопками «Сделать саммари»/«Полный текст») — чтобы сразу показать как выглядит уведомление и фишки. Для существующего — кратко + команды (`/latest` — 10 за 30 дней, `/settings`, `/help`). Убираем «в разработке». `HELP_TEXT` — только прод-команды.

### 5. Лимиты и авто-саммари для Конституции/ФКЗ/ФЗ
Расширяем `rss_parser.is_important` / `LEVEL_MAP` на `Конституция` + `ФКЗ` + `ФЗ` (3 уровня). `scheduler` для них всегда делает `ocr_document_text` (если нет текста) + `summarizer` без проверки лимита, сохраняет `Article` с `summary`. `handlers._summarize_and_reply` bypass лимита `FORCE_SUMMARIZE_MONTHLY_LIMIT` если `article.level in [Конституция,FKZ,FZ]` — иначе лимит 10/мес для остальных (указы/ПП/ведомственные) по кнопке. Причина: важные акты должны приходить сами, без нажатия кнопки.

### 6. Фолбэк при недоступности GigaChat/pravo
Уже есть в `scheduler._process_entry`: `except GigaChatError` → `summary=None` + `ВСТАВКА Article` + `_notify_users` с фолбэком «Не удалось проанализировать... Оригинал: url». Для `pravo` API `FetchError` → `retry` 1/2/4с, затем `log` и `return` без падения. Для MVP без `alembic` — `create_all` + `ALTER IF NOT EXISTS` уже заложен.

## Risks / Trade-offs

- [Удаление `/test` лишит smoke-теста GigaChat в проде] → оставляем `GigaChatClient` тестируемым через логи, при необходимости вернуть за флагом.
- [`/latest` без саммари — юзер не увидит кратко] → компенсируется WebApp «Полный текст» и уведомлением с саммари.
- [Старые `external_id` до `level` колонки — `UNKNOWN`] → фильтр «Все» их покажет, дефолт `[Конституция,ФКЗ,ФЗ]` — нет, это ожидаемо; подсказка в онбординге.
- [Фильтр в `latest` делает `IN` по 6 уровням — медленно] → индекс на `articles.level` уже есть, до 10 записей — ок.
- [Telegram 429/403 без обработки — бан при 100+ юзерах] → добавили `sleep(0.05)` + `RetryAfter`/`is_active=False`; для MVP 10 юзеров — не критично, но заложили.
- [Дефолт `[Конституция,ФКЗ,ФЗ]` vs «Все» — новый юзер пропустит ПП] → подсказка «юристу по крипте — оставь только ФЗ» + `/settings` всегда доступен.
- [GigaChat/pravo недоступен — без фолбэка упадёт] → уже есть фолбэк без саммари + ссылка, не падаем.

## Migration Plan

1. Миграция не нужна (level уже есть, `create_all` + `ALTER IF NOT EXISTS` уже заложен, без `alembic` для MVP).
2. Деплой: удалить dev-хендлеры, обновить `latest` (дефолт `[Конституция,ФКЗ,ФЗ]` + подсказка), добавить флаг `first_run` + `429`/`403` handling, расширить `is_important` на 3 уровня и bypass лимита.
3. Роллбэк: вернуть `latest` без фильтра (дефолт «Все»), вернуть dev-команды, убрать `429` handling.
