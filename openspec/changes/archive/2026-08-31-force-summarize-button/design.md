## Context

Сейчас уведомления создаются только автоматическим пайплайном (`scheduler._build_notification`), без интерактивности. Callback-кнопок и инлайн-потоков в боте нет. Ограничения на потребление GigaChat нет. См. proposal.md — Why/What Changes; требования в specs/force-summarization/spec.md.

## Goals / Non-Goals

**Goals:**
- Инлайн-кнопка «Сделать саммари» на уведомлении о законе (автоматическом и/или из `/latest`)
- Принудительная саммаризация по кнопке: любой закон, независимо от важности и наличия текста (OCR fallback)
- Месячный лимит 10 принудительных саммаризаций на пользователя
- TODO в коде о будущем платном тарифе «бесконечная принудительная саммаризация»

**Non-Goals:**
- Автоматическая дообработка статей без текста (отдельная тема, не в этом change)
- Платёжная логика — только TODO-заметка
- Снятие/частичная отмена лимита, админ-панель

## Decisions

### 1. Учёт месячного лимита — новая модель `UsageRecord` (или счётчик на User)

Выбираем отдельную модель `SummarizationUsage` с ключом `(user_id, month)`:

- `id`, `user_id (FK -> users.id)`, `month` (строка `YYYY-MM`), `count` (int, default 0). Уникальное ограничение на `(user_id, month)`.
- Почему не колонка на `User`: счётчики по месяцам накапливаются и требуют истории/сброса; отдельная строка на месяц чище, позволяет вести историю и легко «сбросить» — просто ищем строку текущего месяца.
- При нажатии: получаем строку `(user, month)`, если нет — создаём; если `count >= LIMIT` → отказ; иначе `count += 1`, переходим к саммаризации.
- Отдельная таблица создаётся как обычно через `Base.metadata.create_all` (новая таблица, `create_all` добавит колонки/таблицы без проблем, в отличие от изменения существующей).

### 2. Константа лимита

`FORCE_SUMMARIZE_MONTHLY_LIMIT = 10` — константа в `app/core/config.py` (или `handlers.py`). Делаем константой в `config`, чтобы можно было подстроить через `.env` (default 10), read-only для пользователя.

### 3. Кнопка на уведомлении

В `scheduler._build_notification` (и в `/latest`) добавить `InlineKeyboardMarkup` с кнопкой `callback_data="force_sum:summary:<external_id>"`. Кнопка присутствует всегда, даже для документов уже с саммари (пользователь может запросить пересоздание — решено разрешить, т.к. лимит сам ограничивает).

### 4. Callback-обработчик

Новый `CallbackQueryHandler` в `app/bot/handlers.py` (`force_summarize`):
- Парсит `external_id` из `callback_data`
- Проверяет лимит пользователя (см. п.1)
- Если исчерпан → `answer` с сообщением о лимите, ничего не считаем
- Иначе — выполняет саммаризацию и отправляет результат; `answer_callback_query` для снятия "loading"

### 5. Переиспользование текста/OCR

Принудительная саммаризация использует ту же цепочку, что автоматический пайплайн: `get_legal_text` → при отсутствии текста `is_important` не требуется — сразу `ocr_document_text` (создаём временный `GigaChatClient`) → `Summarizer.summarize`. Отличия от автопайплайна: не сохраняем в статьи (или обновляем `summary` закону) — решение: **обновляем** `Article.summary`/`original_text`, если статья уже есть, чтобы результат сохранялся; если это новый документ — не создаём рассылку, просто отправляем саммари нажавшему пользователю.

### 6. TODO — платный тариф

В `force_summarize` оставить `# TODO: Рассмотреть платный тариф — бесконечная принудительная саммаризация` на месте проверки лимита.

## Risks / Trade-offs

- [Запросы к GigaChat по кнопке] → ограничены лимитом 10/месяц/пользователь; OCR дорогой — но блокируется лимитом.
- [Callback без синхронизации] → гонка при двойном клике: оба клика могут пройти проверку до инкремента. Приемлемо (лимит мягкий); при желании — `SELECT ... FOR UPDATE`.
- [Сохранение результата в Article] → не усложняем; обновляем существующую запись, только если она есть.
- [Кнопка на всех уведомлениях] → позволяет пересоздавать саммари и для уже обработанных; ограничено лимитом.
