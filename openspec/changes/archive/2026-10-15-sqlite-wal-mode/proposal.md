## Why

SQLite сейчас работает в режиме журнала по умолчанию (`journal_mode=delete`). В нём чтение и запись мешают друг другу. Пока запись фиксирует транзакцию, никто не читает. Пока кто-то читает, запись не может зафиксироваться. После changes `async-summary-delivery-bot` и `async-summary-delivery-miniapp` в БД параллельно ходят хендлеры бота, Mini-App (aiohttp), фоновые задачи саммари, джоба проверки публикаций и бэкап. Движок держит пул из нескольких соединений (`AsyncAdaptedQueuePool`), так что одновременный доступ реален. Самый долгий читатель — бэкап (`VACUUM INTO`). Он держит блокировку чтения всё время копирования, и если оно идёт дольше 5 с, параллельная запись получает `database is locked`. Перед анонсом (150–200 новых пользователей за первые часы) ошибок блокировки станет больше, а `/start`, лимиты саммари и отметки рассылки — это записи. Это п. 7 P0 в `docs/PLAN.md`.

## What Changes

- При старте приложения SQLite-база переводится в режим **WAL**. Читатели (включая бэкап) больше не блокируют запись, запись не блокирует читателей. Друг друга ждут только одновременные записи.
- Ожидание занятой БД (`busy_timeout`) задаётся явно: **10 с** вместо неявных 5 с (дефолт `timeout` у Python `sqlite3`). Одновременные записи ждут друг друга и не падают сразу с `database is locked`.
- В лог при старте пишется фактический режим журнала. Если WAL включить не удалось, пишется предупреждение, и бот работает в прежнем режиме, не падая.
- Для не-SQLite `DATABASE_URL` ничего из этого не применяется.
- Рядом с файлом БД теперь лежат служебные файлы `<имя>.db-wal` и `<имя>.db-shm`. Они добавляются в `.gitignore`. Инструкция восстановления из бэкапа в README дополняется: удалить `-wal`/`-shm` перед подстановкой копии.

## Capabilities

### New Capabilities
- `database-concurrency`: как приложение работает с SQLite при параллельном доступе: режим WAL, ожидание занятой БД, поведение, если WAL недоступен, и отсутствие эффекта для других СУБД.

### Modified Capabilities
- `db-backup`: в требование «Целостность резервной копии» добавляется сценарий: копия содержит записи, ещё не перенесённые из WAL-файла в основной файл БД. Восстановление из копии — это подстановка одного файла после удаления `-wal`/`-shm` старой базы.

## Impact

- `app/core/database.py`: `init_database` передаёт драйверу таймаут ожидания (только для SQLite), `init_db_schema` перед созданием таблиц включает WAL и логирует результат.
- `.gitignore`: шаблоны `*.db-wal`, `*.db-shm`. `.dockerignore` уже исключает весь `data/`.
- `README.md`: шаг восстановления из бэкапа.
- `CLAUDE.md`, `docs/PLAN.md`: короткие отметки.
- Прод (Dockhost): сетевой диск `/app/data` подключён в режиме ReadWriteOnce (подтверждено). Для контейнера это локальная ФС, а WAL требует именно её. Режим WAL сохраняется в самом файле БД: откат кода не возвращает базу в прежний режим (см. design.md, «Откат»).
- Зависимостей, переменных `.env` и изменений схемы БД нет.
