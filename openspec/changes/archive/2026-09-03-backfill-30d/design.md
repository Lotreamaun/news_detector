## Context
См. proposal.md — Why. `fetch_documents` берёт только `PeriodType=daily` (30 шт сегодня), а текущая пагинация `currentPage`/`page`/`offset` игнорируется (`PeriodType` без осмысленной даты всегда отдаёт сегодня). Поэтому 309-ФЗ от 04.08 не попадал в БД. Исследование API:
- `GET /api/documents?periodType=day&date=04.08.2026` возвращает документы именно этого дня (total=546 за 04.08), `date` в формате `dd.mm.yyyy`.
- `pageSize=200` — максимальный размер страницы (300+ → n=0); пагинация страниц не сдвигает (всегда первая страница).
- **`documentTypes=<GUID>` повторяющимся параметром фильтрует на сервере**: `documentTypes=FZ&documentTypes=FKZ` → только ФЗ+ФКЗ за день (total=59 на 04.08). `documentTypeId` (кейс/одиночный) — не фильтрует.
- Реальность данных: ФЗ/ФКЗ публикуются пачками, не ежедневно. В окне 30 дней (08.04–09.03) федеральные есть только на 04.08 (59 законов), остальные дни дают 0.

## Goals / Non-Goals
**Goals:** Одноразовый бэкфилл 30 дней при первом запуске через `periodType=day` + серверный фильтр `documentTypes`, дальше daily без бэкфилла; `FZ` GUID `82a8bf1c...`; `/latest` — чистый SELECT из БД по `UserFilter` на календарное окно 30 дней.

**Non-Goals:** Не менять API текста, не трогать LLM, не делать per-user бэкфилл, не тянуть региональные акты (их 546/день и они не нужны фильтрам).

## Decisions

### Бэкфилл через periodType=day + documentTypes (серверный фильтр)
eoNumber-перебор найден рабочим, но неэффективен (пропуски, ~2400-2700 запросов) и не покрывает все ФЗ. Локальная фильтрация по первым 200/день тоже ненадёжна (региональные вытесняют ФЗ из первых 200 на большинстве дней). Решение: для каждого из последних 30 дней (включительно) — один запрос `GET /api/documents?periodType=day&date={D:%d.%m.%Y}&pageSize=200&documentTypes={FZ}&documentTypes={FKZ}`, который возвращает **только ФЗ+ФКЗ** за день. Итого ~31 запрос, без регионального шума.

### Календарное окно 30 дней (не now-30d по времени)
`published_at >= now - 30d` (с временем суток) отсекает закон, опубликованный утром 30 дней назад (midnight < since). В `/latest` и `show_example` окно считается как `datetime.combine(today - 30d, time.min, utc)` — полночь 30 дней назад — через хелпер `_window_start(days)`. Бэкфилл тоже идёт 31 день (включая самый старый день окна).

### Логика фильтров /latest
`/latest` — `SELECT` из `Article` по `UserFilter.level` на календарное окно, `LIMIT 10`. Смена фильтра — только SQL, без пересинхронизации. Дефолт нового юзера `[CONSTITUTION, FKZ, FZ]`.

## Risks
- [ФЗ/ФКЗ не каждый день] → Реальность данных: если в окне нет федеральных законов, `/latest` покажет меньше 10 или «пока нет законов». Это корректно для портала (ФЗ публикуются пачками). Бэкфилл гарантированно сохраняет те, что есть.
- [limit браузера/скорость] → 31 запрос один раз при старте в фоне, `sleep(0.1-0.2)` между днями; не блокирует `/latest`.
- [Конституция в дефолтном фильтре] → GUID конституции неизвестен/заглушка; на практике поправки к Конституции попадают в ФКЗ/ФЗ. Для MVP фильтруем ФЗ+ФКЗ.

## Migration
Бэкфилл заполнит пропущенные `FZ`/`FKZ` за 30 дней, старые `UNKNOWN` останутся. Повторный запуск — `is_first_run=False`, без бэкфилла.

## Open Questions
Нет (гипотеза `periodType=day` + `documentTypes` проверена: 04.08 → 59 ФЗ/ФКЗ).
