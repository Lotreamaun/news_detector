## Context

См. proposal.md — Why. Текущее состояние, на которое опирается дизайн:

- `Article` (`app/models/article.py`) не хранит время приёма: только `published_at`, а это **дата без времени** (из `publishDateShort`, полночь UTC). Окно «пятница 18:00 → пятница 18:00» по `published_at` задать нельзя.
- `Article` создаётся не только в `_save_article` (приём, бэкфилл), но и напрямую в `app/bot/handlers.py` — при `/summary` и «Сделать саммари» по закону, которого ещё нет в БД. Такая строка потом не проходит `_process_entry`: лента видит, что `external_id` уже есть.
- `_process_entry` (`scheduler.py`) для каждого нового документа пробует получить текст, суммаризует (если текст есть) и сохраняет; OCR — только для `is_important()` (ФКЗ). Саммари у указов и постановлений бывает редко (текст готов не сразу).
- Уровни `DECREE` и `GOV_RESOLUTION` не имеют GUID в `LEVEL_MAP` и определяются только по заголовку (`classify_level_for_title`) подстроками. На выборке 681 федерального акта за 120 дней 26 из 513 (5%) федеральных постановлений уходят в `REGIONAL` (в названии «области», «края», «республики»), а региональные указы со словами «…в Указ Президента Республики …» попадают в `DECREE`. Это расходится с действующим требованием `law-force-filter` («региональные→REGIONAL»).
- Объём кандидатов (та же выборка): федеральных указов ~1,4 в сутки, постановлений Правительства ~4,3 в сутки; 365 из 513 постановлений названы «О внесении изменений в некоторые акты Правительства» — по названию их важность не определить. ФЗ приходят пачками.
- `_build_digest` — готовый тизер: заголовок «Приняли новые законы — N» и сортировка по уровню/алфавиту зашиты в функции; для пунктов без саммари добавляются кнопки «Сделать саммари №N» (через `_summarize_and_reply`, с месячным лимитом пользователя для уровней вне `AUTO_LEVELS`); кнопка «Дайджест» ограничена `DIGEST_ID_CAP = 30`.
- MiniApp показывает только полный текст; показ саммари в карточках дайджеста добавляет change `miniapp-digest-summary` (поле `summary` в `/full_text`).
- Расписание — PTB `JobQueue`. В установленной PTB 22.6 `run_daily(days=...)` нумерует дни 0–6 как **воскресенье–суббота** (пятница = 5).
- Миграции колонок — ручные идемпотентные `_ensure_*_column` в `app/core/database.py`; новые таблицы создаёт `create_all`.
- Образ деплоя `python:3.14-slim`, в `requirements.txt` нет `tzdata`; `zoneinfo` на slim-образах может не найти `Europe/Moscow`.

## Goals / Non-Goals

**Goals:**
- Точность оценки важности (приоритет над объяснимостью): отдельный запрос, рубрика с долями уровней, few-shot, измеримая калибровка.
- Подборка без пропусков и дублей между неделями, одинаковая для всех; у каждого пункта по возможности есть саммари.
- Безопасное включение: оценки, саммари и предпросмотр до первой реальной рассылки.

**Non-Goals:**
- `/latest` и `/today`, мгновенные уведомления, пользовательские фильтры, показ меток важности.
- Финальное ранжирование «топ-N из пачки»: подборка берёт все уровни `3` и `2`.
- Настройка дня недели (пятница зашита), персональные подборки, сферы/регионы.
- Отписка от еженедельной подборки — отдельным change, если появятся жалобы.
- Пересчёт `level` у уже сохранённых строк после исправления классификации.

## Decisions

1. **Колонки `importance` и `created_at` у `Article`.** `importance` — nullable `SmallInteger` (NULL = не оценён, 0–3 уровни); `created_at` — nullable `DateTime(timezone=True)` со значением по умолчанию «сейчас, UTC» **на уровне модели**, а не в `_save_article`: так время приёма получают и строки, созданные из `/summary` и «Сделать саммари», и они участвуют в окне и доборе. Старые строки получают NULL и в окна не попадают (безопасно: прошлое не рассылаем). Миграции — `_ensure_importance_column`, `_ensure_created_at_column` по образцу `_ensure_is_demo_column`. Альтернатива — окно по `published_at` с интервалом в сутки — отвергнута: теряет акты, пришедшие в пятницу после 18:00, и выходные.

2. **Окно по времени приёма + защитное условие по дате публикации с допуском.** Подборка выбирает `created_at` в `(prev_moment, this_moment]` **и** `published_at >= prev_moment.date() − 7 дней`. Непересечение окон обеспечивает `created_at`; условие по дате только отсекает явную историю (бэкфилл создаёт строки с `created_at = now`, но до 30-дневной давности). Допуск в 7 дней нужен, чтобы не терять акты, опубликованные накануне окна, но принятые ботом уже в нём (простой бота, задержка портала). `prev_moment`/`this_moment` — запланированные моменты (пятница `WEEKLY_DIGEST_TIME` в `WEEKLY_DIGEST_TZ`), не фактическое время отправки: при отложенной отправке и догоне окна не пересекаются и не имеют разрывов.

3. **Классификация уровней — строгие префиксы** (приведение кода к действующему требованию `law-force-filter`, без изменения спеки). В `classify_level_for_title`: `DECREE` — заголовок начинается с «Указ Президента Российской Федерации»; `GOV_RESOLUTION` — начинается с «Постановление Правительства Российской Федерации», без проверки маркеров регионов; региональные «Указ Главы/Раиса/Губернатора…» → `REGIONAL`, даже если внутри цитируется «Указ Президента Республики …». Остальные ветки не меняются. Уже сохранённые строки не пересчитываются: в окна подборки они не попадают (`created_at` NULL), а погрешность фильтров на истории приемлема. Примеры для ручной проверки: «Указ Главы Республики Саха (Якутия) … "О внесении изменений в Указ Президента Республики Саха (Якутия) …"» → `REGIONAL`; «Постановление Правительства Российской Федерации … "Об утверждении Правил … в области …"» → `GOV_RESOLUTION`. Альтернатива — строгий префикс только внутри `importance.py` — отвергнута: фильтры пользователей и подборка по-разному понимали бы, что такое «указ».

4. **Отдельный модуль `app/services/importance.py`, функции без классов** (KISS, как `summarizer`). Публично: `score_importance(client, title, body) -> int | None`, `prefilter_zero(level, title) -> bool` и константа `CANDIDATE_LEVELS = {"CONSTITUTION","FKZ","FZ","DECREE","GOV_RESOLUTION"}`. Промпты и шаблоны предфильтра — константы модуля (prompt management, vision.md). Использует `GIGACHAT_MODEL` из конфига (`GigaChat-2-Max`).

5. **Предфильтр по заголовку.** Перед вызовом LLM предмет акта (текст заголовка после `№ … "`) проверяется по шаблонам (начало строки, без учёта регистра, кроме шаблона ФИО); совпадение → `0` без вызова GigaChat. Применяется только к `DECREE` и `GOV_RESOLUTION`. Покрытие на выборке за 120 дней (`scripts/importance_titles_sample.json`): указы 109 из 168 (65%), постановления 9 из 513.

   | Уровень | Шаблон | На выборке |
   |---|---|---|
   | DECREE | `О` / `Об <Фамилия> И.О.` (персональный кадровый указ, весь предмет) | 22 |
   | DECREE | `О Чрезвычайном и Полномочном После` | 19 |
   | DECREE | `О присвоении` (классные чины, почётные наименования и звания, имена, дипломатические ранги) | 17 |
   | DECREE | `О награждении` | 14 |
   | DECREE | `О внесении изменени[йя] в состав` (составы комиссий и советов) | 11 |
   | DECREE | `О праздновании` | 8 |
   | DECREE | `О (заместителе\|руководителе\|советнике\|генеральном директоре\|атамане\|председателе)` | 6 |
   | DECREE | `О присуждении` (госпремии) | 4 |
   | DECREE | `О назначении (на должность\|судей)` | 2 |
   | DECREE | `О Полномочном представителе`, `Об исполняющ(ем\|ей) обязанности`, `Об освобождении`, `О восстановлении в правах на государственн`, `О приеме в гражданство`, `Об увековечении памяти`, `О Дне ` | 0–1 каждый |
   | GOV_RESOLUTION | `Об авансировании государственн` | 7 |
   | GOV_RESOLUTION | `Об изменении существенных условий (государственных )?контрактов` | 2 |

   Намеренно **не** в предфильтре (решает модель): «О назначении выборов» (поэтому шаблон назначений узкий); ратификации и «О внесении на ратификацию» (бывают значимыми); «О внесении изменения в Указ … № 95» (42 за 4 месяца, исключения по иностранным кредиторам — если на калибровке стабильно `0`, шаблон добавляется); «О внесении изменений в некоторые акты Правительства» (по названию не определить).

6. **Рубрика (источник правды; финальные формулировки уточняются на калибровке и живут в константах модуля).**
   - Повышает: (1) охват — сколько людей/организаций; (2) прямое влияние на деньги, права, обязанности (налоги, штрафы, пособия, пенсии, тарифы, ипотека, уголовная/административная ответственность); (3) новизна — новый закон/кодекс/запрет/льгота против технической правки; (4) скорое вступление в силу; (5) общественный резонанс.
   - Понижает: ратификации, кадровые акты и награждения, технические уточнения («в связи с переименованием»), продления сроков, нормы для узкого круга.
   - Шкала и ориентиры долей в промпте: `3` — единицы в месяц (≲2% кандидатов); `2` — ~10–15%; `1` — основная масса; `0` — технические/кадровые/ратификации. Без ориентиров LLM завышает.
   - Приёмы точности: один запрос на одну задачу; ответ JSON `{"reason": "...", "level": N}` — поле `reason` идёт **первым** (короткое рассуждение перед меткой повышает точность) и не хранится; низкая температура (0–0.1; сейчас у суммаризации 0.3); 6–8 few-shot примеров из реальных актов (по 1–2 на уровень, из ФЗ и из указов/постановлений), подобранных на калибровке; при невалидном JSON — один повтор, затем «не оценено».

7. **Вход оценки.** Название + саммари; иначе название + начало текста (≤ ~3000 символов, константа); иначе только название — но только на финальном проходе перед отправкой или после неудачного OCR (п. 8). На приёме без саммари и текста оценка откладывается (текст часто появляется позже).

8. **Когда оценивать.**
   - (а) При приёме в `_process_entry`, в собственном `try/except`: сбой оценки не должен ломать сохранение и рассылку (принцип «бот не молчит»). Предфильтр — первым, без сети.
   - (б) Добор в конце каждого цикла `check_legislation_updates` — после мгновенных уведомлений (оценка накопившихся актов не должна задерживать рассылку новых) и перед проверкой недельной подборки: кандидаты без оценки с `created_at` не старше 14 дней и защитным условием по дате (так покрываются и текущее окно, и предыдущее, если его отправка отложена), не более `N` за цикл (константа, ~20). Для кандидата без текста — повторный `get_legal_text`; полученный текст **сохраняется** в `original_text`. Если текста нет дольше 24 часов после `created_at` (константа) — один OCR через GigaChat **до** оценки (`ocr_document_text`, текст сохраняется); если и OCR не дал текста — оценка по названию сразу. Чтобы не повторять OCR каждый цикл, id уже пробованных хранятся в памяти процесса (`bot_data`); после рестарта возможна одна лишняя попытка — приемлемо.
   - (в) Финальный проход перед отправкой подборки — оценивает всех оставшихся кандидатов окна, в т.ч. по названию.
   - Отказ GigaChat (`classify_reply == "refusal"`) → повторная оценка по одному названию (на нейтральном названии модель отказывает реже); повторный отказ → `2` с записью в лог (чувствительная тема не должна выпадать). Временная ошибка → NULL и повтор при следующем доборе.

9. **Фоновая саммаризация актов с оценкой `≥ 2`.** Не более двух попыток на акт, без новых колонок:
   - попытка 1 — сразу после присвоения оценки `≥ 2` (на приёме или при доборе): если саммари нет — текст (при отсутствии — OCR), затем `summarizer.summarize`; текст и саммари сохраняются в `Article`. Для ФЗ/ФКЗ попыткой 1 считается обычная суммаризация в `_process_entry`;
   - попытка 2 — в финальном проходе непосредственно перед фактической отправкой (выполняется один раз на период, см. п. 11).
   - Отказ или сбой **не** записывает ничего в `Article.summary` — иначе текст неудачи стал бы «кэшированным саммари» для `/summary` и кнопок.
   - Акт, у которого после попытки 2 нет саммари, **исключается из подборки**, его `external_id` пишется в лог. Заглушки вместо саммари нет: в подборку попадает только то, что можно прочитать. Компромисс: акты с двойным отказом модели (чувствительные темы, получившие `2` по правилу отказа, п. 8) в автоматическую подборку не попадают; вернуть такой акт вручную сможет будущая модерация подборки (`weekly-digest-moderation`).
   - Фоновая саммаризация не расходует лимиты пользователей. Отсутствие саммари у части актов отправку остальных **не** задерживает.

10. **Расписание и конфигурация.** `JobQueue.run_daily(weekly_digest_job, time=time(h, m, tzinfo=ZoneInfo(WEEKLY_DIGEST_TZ)), days=(5,))` — пятница по нумерации PTB 22.6 (0 = воскресенье). Конфиг: `WEEKLY_DIGEST_TIME` (формат `HH:MM`, пусто = выключено), `WEEKLY_DIGEST_TZ` (по умолчанию `Europe/Moscow`); валидация в `Config.load()` с `ConfigError`. Префикс `WEEKLY_` — потому что «дайджест» в коде уже занят дневным пакетным тизером (`_build_digest`, `DIGEST_ID_CAP`). День недели не настраивается (YAGNI). В `requirements.txt` добавляется `tzdata`.

11. **Единая точка отправки `_maybe_send_weekly_digest(context)`.** Вызывается из трёх мест: пятничной задачи (п. 10), `_post_init` после `_run_initial_check` (догон после простоя) и конца каждого `check_legislation_updates` (повтор отложенной отправки). Под `asyncio.Lock` из `bot_data`, чтобы задача и цикл не отправили одновременно. Порядок проверок:
    1. `WEEKLY_DIGEST_TIME` пуст → выход.
    2. `period_end` — последний прошедший запланированный момент. Есть запись `weekly_digest_runs` с `finished_at` за него → выход.
    3. Сейчас позже воскресенья 22:00 этой недели (в `WEEKLY_DIGEST_TZ`) → пропуск с записью в лог; пропущенная подборка не отправляется.
    4. Сейчас вне дневного окна 09:00–22:00 (константы) → выход до следующего цикла. Пятничное 18:00 в окне.
    5. Финальный проход оценки (п. 8в). Если остались неоценённые кандидаты окна (GigaChat недоступен) и сейчас раньше последнего часа окна воскресенья (21:00) → выход, повтор следующим циклом. В последний час воскресенья отправляется то, что оценено; неоценённые исключаются, их список пишется в лог.
    6. Попытка 2 саммаризации пунктов подборки (п. 9), исключение пунктов без саммари (их id — в лог), сборка сообщения, запись `started_at`, рассылка, запись `finished_at`. Пустая подборка — в том числе опустевшая после исключения — без отправок, но период фиксируется как завершённый.

    Окно подборки (п. 2) не зависит от того, когда фактически произошла отправка.

12. **Идемпотентность — таблица `weekly_digest_runs`** (`period_end` — запланированный момент, уникален; `started_at`; `finished_at` NULL до конца рассылки). Пустая подборка тоже фиксируется как завершённый период. При падении посреди рассылки `finished_at` остаётся NULL, и следующий вызов `_maybe_send_weekly_digest` отправит подборку заново **всем** — часть пользователей получит дубль. Альтернатива — таблица доставок на пользователя — отвергнута как избыточная для масштаба проекта; семантика «минимум один раз» та же, что у `Article.notified`.

13. **`_build_digest` получает необязательные параметры** `header: str | None` и `sort_key`; значения по умолчанию сохраняют текущее поведение дневных дайджестов. Недельная подборка передаёт свой заголовок (константа «📌 Еженедельная подборка: главные законы — N») и порядок (`importance` ↓, `published_at` ↓). Параметр для отключения кнопок «Сделать саммари №N» не нужен: их уже убрал из тизера change `miniapp-digest-summary`. Параметр текста-заглушки не нужен: пунктов без саммари в подборке нет (п. 9). Альтернатива — отдельная функция сборки недельного сообщения — отвергнута: дублирует разметку.

14. **Рассылка.** Получатели — те же, что в `_notify_users_batch` (активные, `channel_verified`), без `UserFilter`; отправка через существующий `_send_notification` (обработка `Forbidden`) с той же анти-спам паузой. Один и тот же текст/клавиатура строится один раз.

15. **Предпросмотр.** `/test_digest weekly` расширяет `test_digest_command` (проверка `ADMIN_CHAT_IDS` уже есть): строит подборку за текущее окно (последний запланированный момент → сейчас) тем же селектором и той же сборкой, отправляет только администратору, **не** пишет в `weekly_digest_runs` и не запускает оценку/саммаризацию. Работает и при пустом `WEEKLY_DIGEST_TIME` (окно считается от пятницы 18:00): так подборку можно проверить до включения рассылки (Migration Plan, шаг 3). Второе сообщение: включённые акты (`external_id`, оценка); акты с оценкой `2`–`3` без саммари (их исключат, если саммари не появится до отправки); неоценённые кандидаты окна (именно они задерживают отправку); счётчики — отсеяно предфильтром, оценено `0`, оценено `1`.

16. **Калибровка.** Скрипт `scripts/calibrate_importance.py` + файл разметки `scripts/importance_golden.csv`. Эталон ~40 актов: ~25 ФЗ из пачки 04.08.2026 (от технических поправок до крупных) и ~15 федеральных указов и постановлений за 1–2 обычные недели; акты, отсеиваемые предфильтром, в эталон не берутся (их оценка детерминирована). Пользователь размечает, скрипт прогоняет `score_importance`, печатает матрицу ошибок и список расхождений. Чтобы размечать по тому же входу, что видит модель, режим `--fill` дописывает в эталон колонки `url` и `summary` (саммари кэшируются в `scripts/.calibration_cache.json`, он в `.gitignore`). Few-shot примеры промпта берутся из размеченного эталона и исключаются из метрик калибровки (`FEW_SHOT_IDS`), иначе точность была бы завышена. Рядом лежит `scripts/importance_titles_sample.json` — выборка заголовков, на которой проверяется покрытие предфильтра. Для проверки предпросмотра на реальных данных до накопления свежих актов — разовый `scripts/seed_weekly_window.py`: подгружает федеральные акты текущего окна с `notified=True` (без рассылки), проставляет `created_at` уже сохранённым и оценивает их тем же кодом, что и приём. Критерий готовности (согласован на калибровке): граница `1/2` верна на подавляющем большинстве эталонных актов в обеих группах, `3` не раздаётся щедро. Это разовый инструмент, а не тесты репозитория (проект не стремится к полному покрытию).

## Risks / Trade-offs

- [Модель завышает/занижает границу `1/2`: каждая завышенная `2` попадает всем подписчикам] → ориентиры долей в промпте, few-shot из обеих групп, калибровка на эталоне, админский предпросмотр перед включением `WEEKLY_DIGEST_TIME`.
- [Отказы GigaChat приходятся именно на важные темы, особенно силовые указы] → сначала повторная оценка по названию; `2` — только при повторном отказе. Кадровые и наградные силовые указы отсекает предфильтр до LLM.
- [Предфильтр отсекает значимый акт] → узкие шаблоны (например, «О назначении» только на должность/судей, не выборы), счётчик «отсеяно предфильтром» в предпросмотре, выборка заголовков для перепроверки.
- [GigaChat недоступен в пятницу] → отправка откладывается до восстановления (в пределах воскресенья 22:00), а не теряет неоценённые акты; в последний час воскресенья уходит то, что есть.
- [Дубль подборки части пользователей при падении посреди рассылки] → принято сознательно (см. п. 12); редкость и низкая цена.
- [Оценка по названию точна хуже] → применяется только после неудачного OCR или на финальном проходе, когда ни саммари, ни текста так и не появилось.
- [Стоимость OCR и саммари] → только для кандидатов без текста дольше 24 часов (OCR до оценки) и для актов `≥ 2` (~10–15% кандидатов); при ~5–6 федеральных актах в сутки это единицы вызовов.
- [Пакетные дни (59 ФЗ) = десятки вызовов GigaChat подряд, возможны лимиты] → добор ограничен числом за цикл; приём не блокируется оценкой.
- [Исправление классификации меняет поведение фильтров для части актов] → это приведение к действующей спеке; затрагивает только новые строки.
- [`WEEKLY_DIGEST_TIME` задан без `WEBAPP_URL`: пользователь видит только 3 закона без кнопки] → предупреждение в лог при старте; конфигурация рассылки без WebApp считается ошибкой настройки, а не поддерживаемым режимом.
- [Неверная нумерация дней в PTB (воскресенье = 0)] → зафиксирована в п. 10, покрыта ручной проверкой расписания в задачах.
- [Акт с двойным отказом модели (чувствительная тема) получает `2`, но без саммари выпадает из подборки] → принято сознательно (п. 9): в подборку идёт только то, что можно прочитать; ручное добавление — в будущей модерации подборки.

## Migration Plan

1. Выкатить предусловия: `fix-ingestion-pagination` и `miniapp-digest-summary`.
2. Выкатить этот change с пустым `WEEKLY_DIGEST_TIME`: миграции колонок, исправленная классификация, оценка при приёме, добор и фоновая саммаризация работают, рассылки нет.
3. Накопить оценки, сверить с эталоном и проверить подборку через `/test_digest weekly`.
4. Задать `WEEKLY_DIGEST_TIME=18:00` (и `WEEKLY_DIGEST_TZ`) в `.env` прода; первая рассылка — ближайшая пятница. Решено при реализации: рассылка включается не в этом change, а вместе с модерацией подборки (`weekly-digest-moderation`: черновик, согласование администратором); до тех пор на проде остаётся шаг 2 (оценки накапливаются, рассылки нет).
5. Откат: очистить `WEEKLY_DIGEST_TIME` — рассылка выключается без отката кода и БД; колонки и таблица безвредны при отключении.
