## Context

См. proposal.md — Why/What Changes для мотивации. Технические ограничения, важные для реализации:

- Схема БД создаётся через `Base.metadata.create_all` (`app/core/database.py:init_db_schema`) — это `CREATE TABLE IF NOT EXISTS`, миграций (Alembic и т.п.) в проекте нет. Новая колонка на уже существующей таблице `users` **не появится** автоматически при рестарте — `create_all` не трогает существующие таблицы.
- `User.is_active` — единственный существующий precedent булева поля со `server_default=text("1")` (`app/models/user.py`) — используем тот же паттерн для консистентности.
- `Config.load()` сейчас падает `ConfigError`, если отсутствуют обязательные переменные (`TELEGRAM_BOT_TOKEN`, `DATABASE_URL`). Канал по условию (Q2 грилла) ещё не создан на момент мержа кода — значение переменной появится позже.

## Goals / Non-Goals

**Goals:**
- Добавить гейт без миграции данных для уже существующих 2 пользователей.
- Не сломать запуск бота, если переменная канала ещё не заполнена (плейсхолдер).
- Сделать проверку подписки переиспользуемым сервисом (задел под будущую периодическую проверку — вне scope этого change).

**Non-Goals:**
- Периодическая перепроверка подписки (только разовая проверка на онбординге).
- UI-порядок экранов `/start` (welcome → тест → гейт → визард) — это `onboarding-flow-redesign`, зависящий от этого change.
- Массовая рассылка/уведомление существующих пользователей о новом канале — не нужно, гейт применяется только к новым регистрациям.

## Decisions

### Ручная idempotent-миграция колонки вместо Alembic
Добавляем маленькую функцию (например `_ensure_channel_verified_column` в `app/core/database.py`), вызываемую из `init_db_schema()` после `create_all`: проверяет наличие колонки `channel_verified` в `users` (`PRAGMA table_info(users)` для SQLite) и, если её нет, выполняет `ALTER TABLE users ADD COLUMN channel_verified BOOLEAN NOT NULL DEFAULT 1`. Идемпотентно, безопасно при повторных запусках, не требует внешней библиотеки миграций — соответствует принципу KISS проекта (полноценный Alembic избыточен для одной колонки в pet-проекте).
**Альтернатива (отклонена):** завести Alembic — оверинжиниринг для проекта, который явно избегает тяжёлых абстракций (см. CLAUDE.md).

### Конфигурация канала — опциональна, гейт отключается сам, если не задана
`Config.REQUIRED_CHANNEL_ID: str | None` (принимает numeric chat id или `@username`), без записи в обязательные поля `Config.load()`. Если переменная не задана — сервис проверки подписки считает любого пользователя автоматически подтверждённым (лог warning при старте: "REQUIRED_CHANNEL_ID не задан, гейт подписки отключён"), чтобы не блокировать локальную разработку/тестирование до того, как канал будет создан и вписан в `.env`.
**Альтернатива (отклонена):** сделать переменную обязательной — сломало бы текущий рабочий `.env` пользователя сразу после мержа, до того как он вручную впишет канал.

### Сервис проверки — отдельный модуль `app/services/channel_subscription.py`
Функция вида `async def is_subscribed(bot: Bot, telegram_id: int, channel_id: str) -> bool`, оборачивает `bot.get_chat_member(chat_id=channel_id, user_id=telegram_id)`, возвращает `True` для статусов `member`/`administrator`/`creator`, `False` для `left`/`kicked`. Исключения (бот не в канале, канал не найден, сетевые ошибки) — перехватываются, логируются, возвращается `False` (fail-closed: при сомнении просьба подписаться, не молчаливый пропуск гейта).
**Альтернатива (отклонена):** встроить проверку прямо в callback-обработчик в `handlers.py` — не даёт переиспользовать её позже для периодической проверки (Non-Goal этого change, но задел по требованию Q5 грилла).

### Выборка в `_notify_users` — доп. условие в существующем SQL-запросе
`select(User).where(User.is_active.is_(True), User.channel_verified.is_(True))` — расширение уже существующего запроса (scheduler.py), без отдельного слоя фильтрации.

## Risks / Trade-offs

- [Риск] Бот не добавлен в канал (или не админ) → `get_chat_member` кидает `BadRequest`/`Forbidden` → **Митигация**: `is_subscribed` перехватывает исключение, трактует как "не подписан", логирует на уровне WARNING с понятным сообщением (это операционный prerequisite — бота нужно добавить в канал вручную, не код-фикс).
- [Риск] SQLite `ALTER TABLE ADD COLUMN` в момент, когда таблица уже используется в проде → **Митигация**: выполняется в рамках той же транзакции `engine.begin()`, что и `create_all`, до старта polling — безопасно, т.к. происходит один раз при старте процесса, до обработки трафика.
- [Trade-off] Fail-closed при ошибке проверки (пользователь остаётся `channel_verified=False`, если Telegram API недоступен в момент проверки) — осознанно: лучше попросить нажать кнопку ещё раз, чем случайно дать доступ без реальной подписки.

## Migration Plan

1. Деплой кода с новой колонкой и `_ensure_channel_verified_column` — при следующем старте бота колонка добавится автоматически (`DEFAULT 1`), существующие 2 пользователя получат `channel_verified=True`.
2. `.env`: добавить `REQUIRED_CHANNEL_ID=` (пусто) в `.env.example`; пока не заполнено в реальном `.env` — гейт неактивен (см. Decision выше), бот работает как раньше.
3. Когда канал создан и `REQUIRED_CHANNEL_ID` вписан в `.env` — гейт активируется для новых регистраций без дополнительного деплоя.
4. Откат: если гейт нужно временно выключить — очистить `REQUIRED_CHANNEL_ID` в `.env` и перезапустить бота (колонку в БД можно оставить, она не мешает при отключённом гейте).
