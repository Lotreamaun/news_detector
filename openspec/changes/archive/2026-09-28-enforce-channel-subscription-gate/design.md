## Context

См. `proposal.md — Why`. Сегодня единственная точка использования `channel_verified` — `scheduler.py:_notify_users_batch`, которая просто фильтрует получателей фоновой рассылки. Все интерактивные обработчики в `app/bot/handlers.py` регистрируются в `app/main.py` без какой-либо проверки этого поля. Экран «предложи подписаться + Проверить подписку» уже существует как часть онбординга (`onboarding_show_example`, `check_subscription` в `handlers.py:454-517`) — текст сообщения и кнопка там сейчас захардкожены внутри `onboarding_show_example`.

Слой `app/bot/` — единственное место, где живут все обработчики (`.cursor/rules/conventions.mdc`: `app/bot/` — только Telegram-обвязка), поэтому и гейт, и его подключение к регистрации остаются в этом слое; в `app/services/channel_subscription.py` уже есть переиспользуемая функция проверки (`is_subscribed`), которая не меняется.

## Goals / Non-Goals

**Goals:**
- Единая, не дублируемая по каждому хендлеру точка проверки `channel_verified`, подключаемая при регистрации обработчиков в `app/main.py`.
- Ровно один список исключений (онбординг + `/start`), без риска забыть добавить гейт к новому хендлеру в будущем (гейт должен быть «default-deny», а не «default-allow с ручным подключением»).
- Переиспользовать существующий текст/кнопку «Проверить подписку» один раз, а не дублировать в двух местах (онбординг и гейт).

**Non-Goals:**
- Не переделываем механизм самой проверки подписки (`is_subscribed`, `get_chat_member`) — он остаётся синхронным, по нажатию кнопки.
- Не добавляем повторную live-проверку через Bot API на каждую команду — используем закешированный флаг `channel_verified` в БД (как и `scheduler.py`), иначе каждая команда стоила бы одного вызова Telegram API и была бы уязвима к рейт-лимитам.
- WebApp/Mini-App не трогаем (см. proposal.md — Impact).

## Decisions

**1. Механизм подключения: "wrap-at-registration", а не decorator на каждом хендлере.**
Вместо того чтобы расставлять `@require_channel_verified` над каждой функцией-обработчиком в `handlers.py` (легко забыть на новом хендлере), гейт оборачивает обработчик в момент регистрации в `app/main.py` — единая функция-обёртка (например, `_gated(handler)`), применяемая ко всем `add_handler(...)` вызовам, кроме явного allowlist'а (`start`, `show_example`, `onboarding_show_example`, `check_subscription`). Это даёт default-deny: новый обработчик, добавленный без явного исключения, автоматически защищён.
Альтернатива (decorator на каждой функции) отклонена — она default-allow по духу (забыл добавить декоратор — дыра), что и есть текущий баг.

**2. Источник истины при проверке — поле `User.channel_verified` из БД, а не live-запрос к Bot API.**
Совпадает с тем, что уже делает `scheduler.py`. Не вызывает дополнительной нагрузки на Bot API на каждое сообщение пользователя. Разошедшееся состояние (пользователь вышел из канала после проверки) устраняется отдельно — не в рамках этого изменения (нет требования на повторную ре-верификацию).

**3. Текст/кнопка "подпишись" переиспользуются, а не дублируются.**
Сообщение и `InlineKeyboardButton("Проверить подписку", callback_data="check_subscription")`, сейчас захардкоженные внутри `onboarding_show_example` (`handlers.py:471-474`), выносятся в отдельную небольшую функцию (например, `_subscribe_prompt_message()` в `handlers.py`), которую использует и онбординг, и новая обёртка гейта — одна точка правды на формулировку.

**4. Гейт полностью отключается, если `REQUIRED_CHANNEL_ID` не задан.**
Уже заложено в `is_subscribed()` (`app/services/channel_subscription.py`) — обёртка должна читать это же условие, чтобы поведение при выключенном гейте не менялось (см. спека — сценарий «Гейт отключён конфигурацией»).

**5. `start()` не оборачивается `require_channel_verified`, но получает собственную ветку на `channel_verified`.**
`/start` обязан быть доступен всегда (иначе новый пользователь не попадёт на экран онбординга), поэтому обёртка-гейт к нему не применяется. Но это не значит «`/start` игнорирует `channel_verified`»: сам `start()` уже различает `is_new` (новый/существующий пользователь) и должен научиться различать третий случай — существующий пользователь с `channel_verified = False`, которому вместо приветствия со списком команд показывается тот же баннер подписки (`_subscribe_prompt()`), что и на защищённых командах. Обнаружено при ручной проверке (см. tasks.md, п. 4.1): без этой ветки гейт формально работает (команды блокируются), но `/start` вводит пользователя в заблуждение, показывая список команд, которыми нельзя воспользоваться.

## Risks / Trade-offs

- [Пользователь уже существовал в БД до внедрения гейта, `channel_verified` дефолтится в `True`] → не блокируется, т.к. это заложено в исходном требовании «Пользователь, зарегистрированный до внедрения гейта» (`channel-subscription-gate` спека) и не меняется этим change.
- [`ConversationHandler` для `/settings` использует несколько entry points/states] → обёртка должна применяться на уровне `CommandHandler("settings", ...)`/entry point, а не внутри промежуточных состояний диалога, иначе пользователь, уже прошедший гейт и начавший диалог, будет неожиданно заблокирован на середине шага. Проверить при реализации, что `wizard:setup`/`wizard:skip` callbacks (доступные только после верификации в потоке онбординга) не требуют повторной обёртки.
- [Сообщение «подпишись» показывается на каждое нажатие защищённой команды] → соответствует ожидаемому поведению («ни одна команда, кроме /start», по формулировке пользователя); не спамим никуда, кроме прямого ответа на попытку пользователя.

## Migration Plan

- Разработка — в отдельной ветке (не в `main`), т.к. деплой на Dockhost выполняется автоматически из `main` и любое изменение в `main` сразу уезжает в прод. Ветка и стратегия мержа — по согласованию с пользователем на шаге `/opsx:apply` (не в рамках этого планирования).
- Обратной несовместимости с БД нет — поле `channel_verified` и его дефолты уже существуют, миграций не требуется.
- Отката: ветку не мержить / ревертнуть коммит; фоновой рассылки и БД-схемы изменение не касается, откат безопасен.
