## Context

Оценка важности живёт в `app/services/importance.py`:

- `_parse_level(reply)` достаёт из ответа уровень 0–3. Если ответ не по формату, возвращает `None`: сначала пробует JSON, потом регулярку `_LEVEL_RE` для сломанного JSON.
- `_ask(client, title, body)` делает до двух попыток. Возвращает уровень, `-1` при отказе модели (`classify_reply`) или `None`, если оба ответа невалидные.
- `score_importance` при отказе по входу с текстом спрашивает ещё раз по одному названию, а при повторном отказе ставит `REFUSAL_FALLBACK_SCORE = 2`. И `GigaChatError`, и невалидный ответ дают `None`, и снаружи их не отличить.

`_rate_article` (`scheduler.py`) вызывают из трёх мест: при приёме (`_process_entry`, обёрнуто в `try/except Exception`), из `_rate_backlog` (то же) и на финальном проходе подборки (`final=True`, то же). `None` значит «не оценено»: в БД ничего не пишется, и в следующем цикле акт снова попадает в `_rate_backlog`. Выборка добора — `ORDER BY created_at LIMIT IMPORTANCE_BACKLOG_LIMIT` (20), так что застрявший старый акт всегда идёт первым.

`_send_weekly_digest` вызывается в пятницу в `WEEKLY_DIGEST_TIME` и в конце каждого цикла проверки. Порядок: финальный проход (`_rate_article(final=True)` для всех `is_awaiting_rating`), затем проверка оставшихся неоценённых — если они есть, подборка откладывается до `SUNDAY_LAST_HOUR_START` (воскресенье 21:00), затем попытка 2 саммари (`needs_summary_retry`) и состав `final_selection` (только документы с саммари; `weekly_review.py`). Один неоценённый кандидат откладывает подборку для всех.

В `bot_data` уже есть похожее состояние на процесс: `ocr_tried` (`set[str]`).

Ответ `{"reason": "...", "level": null}` — валидный JSON, но `_parse_level` даёт на него `None`. Проблема описана в proposal.md (Why).

## Goals / Non-Goals

**Goals:**
- Ответ без уровня приводит к окончательной оценке не больше чем за два вызова GigaChat на акт.
- Любой другой упорно невалидный ответ стоит не больше 3 циклов (до 6 вызовов) на акт за жизнь процесса до финального прохода.
- Сбои сети и API не расходуют лимит.
- В логе виден `external_id` акта, оценка которого не получена, поставлена по правилу «нет информации» или отложена из-за лимита.
- Неоценённые кандидаты не задерживают подборку, если в ней уже не меньше 3 актов.

**Non-Goals:**
- Отличать «пустой» текст акта от настоящего (вариант D из #21).
- Хранить счётчик в БД или переживать перезапуск.
- Менять промпт, few-shot примеры, окно бэклога и логику финального прохода (кого и как он оценивает).
- Догонять в подборку акт, оценённый после отправки.

## Decisions

### 1. «Нет информации» — третий код `_ask`, как `-1` для отказа

`_parse_level` при валидном JSON с ключом `"level"` и значением `null` возвращает `_NO_INFO = -2` (константа модуля). Для сломанного JSON то же делает регулярка `"level"\s*:\s*null\b`. `_ask` возвращает `_NO_INFO` сразу, без второй попытки: результат не `None`, поэтому существующий `if level is not None: return level` сработает без изменений.

Альтернатива — отдельный enum или класс результата. Отклонена: модуль уже кодирует отказ как `-1`, и второй служебный код в том же стиле проще (KISS). Наружу из `score_importance` служебные коды не выходят.

Строка `"level": "null"` (в кавычках) специально не распознаётся. Такого ответа в логах не было, он считается невалидным и попадает под лимит из п. 4.

### 2. Откат на название, затем `1` (или `2` после отказа)

В `score_importance` условие повторного запроса по названию расширяется: `result in (-1, _NO_INFO) and body`. Перед повтором запоминается `refused = result == -1`. Затем по итоговому результату:
- `-1` (отказ и по названию) → `REFUSAL_FALLBACK_SCORE` (как сейчас);
- `_NO_INFO` → `REFUSAL_FALLBACK_SCORE`, если `refused`, иначе новая константа `NO_INFO_FALLBACK_SCORE = 1`; в лог пишется `logger.warning`.

| по входу с текстом | по названию | итог `score_importance` |
|---|---|---|
| `_NO_INFO` | уровень | уровень |
| `_NO_INFO` | `_NO_INFO` | `1` |
| `_NO_INFO` | отказ | `2` (отказ на названии = чувствительная тема) |
| отказ | `_NO_INFO` | `2` (отказ по тексту не отменяется) |
| `_NO_INFO` / отказ | невалидный | `None` → засчитывается в лимит (п. 4) |
| любой | `GigaChatError` | исключение → не засчитывается (п. 5) |
| вход только из названия → `_NO_INFO` | — | `1` |

Почему `1`, а не `2`, как при двойном отказе: отказ указывает на чувствительную тему, а «нет информации» — на бессодержательный вход. Пускать такие акты в подборку незачем, а `1` — самая частая оценка («основная масса актов»). Решение согласовано с пользователем.

Почему `2` при отказе по тексту и «нет информации» по названию: «нет информации» по одному названию не отменяет отказ по тексту, а отказ — сигнал чувствительной темы. Лишний акт в подборке админ уберёт в панели, а выпавший молча никто не заметит. Цена — одна переменная `refused`.

### 3. `external_id` в логах — через необязательный параметр `ref`

`score_importance(client, title, body, *, ref: str | None = None)` передаёт `ref` в `_ask`. Обе функции подставляют его в свои строки лога («невалидный ответ», «отказ модели…», «нет информации…»). Без `ref` пишется, как сейчас, `title[:150]`. `_rate_article` передаёт `ref=article.external_id` и сам логирует итоги, где оценки нет (п. 4–5).

Альтернатива — логировать только в `_rate_article`. Отклонена: строка «невалидный ответ» с текстом ответа пишется внутри `_ask`, а в #21 не хватало именно связи «этот ответ — этот акт».

### 4. Лимит невалидных циклов — `dict` в `bot_data`, проверка в `_rate_article` и в SQL добора

- `IMPORTANCE_MAX_INVALID_CYCLES = 3` — константа рядом с `IMPORTANCE_BACKLOG_*` в `scheduler.py`.
- Счётчик: `context.bot_data.setdefault("importance_invalid", {})`, тип `dict[str, int]`, ключ — `external_id`.
- В `_rate_article` сразу после предфильтра: если `not final` и счётчик ≥ лимита, вернуть `None` без запроса текста и без LLM (`logger.debug`). Предфильтр идёт раньше, потому что он бесплатный и даёт окончательный `0`.
- `_rate_backlog` исключает в SQL акты с исчерпанным лимитом: `Article.external_id.notin_(exhausted)`, где `exhausted` — ключи счётчика со значением ≥ лимита (условие добавляется, только если список не пуст). Без этого такие акты, старые и первые в `ORDER BY created_at`, занимают места из `IMPORTANCE_BACKLOG_LIMIT`, и 20 таких актов останавливают добор. Проверка в `_rate_article` остаётся для приёма.
- `score_importance` вернула `None` (теперь это только невалидный ответ): счётчик увеличивается. При достижении лимита пишется `logger.warning("Оценка %s: %d циклов с невалидным ответом — добор пропускает до финального прохода", …)`, в остальных случаях `logger.info` с номером цикла.
- Оценка получена: `pop(external_id, None)`.
- Финальный проход проверку лимита пропускает, но счётчик при невалидном ответе всё равно увеличивает. Это безвредно.

Счётчик считает **циклы** с невалидным ответом до успешной оценки или перезапуска, а не отдельные вызовы. Циклы с `GigaChatError` и отложенные без текста его не сбрасывают. Внутри цикла `_ask` по-прежнему делает две попытки, плюс возможен запрос по названию после отказа или «нет информации».

Альтернативы:
- Хранить время последней неудачи и бэкофф на несколько часов (вариант B из #21). Отклонено: нужно выбрать ещё один параметр, а лимит из #11 проще и уже закрывает расход.
- Хранить счётчик в колонке `articles`. Отклонено: понадобится миграция, а сброс при перезапуске приемлем (#11).
- Проверять лимит только в `_rate_backlog`. Отклонено: приём (`_process_entry`) тоже зовёт `_rate_article`, а `final` уже передаётся именно в эту функцию.

### 5. `GigaChatError` пробрасывается из `score_importance`

Сейчас `score_importance` перехватывает `GigaChatError` и возвращает `None`, поэтому сбой сети неотличим от невалидного ответа и тоже расходовал бы лимит. Теперь блок `try/except` из `score_importance` убирается, а в docstring появляется `Raises: GigaChatError`. `_rate_article` оборачивает вызов в `except GigaChatError`: пишет `logger.warning("Оценка %s не удалась (%s) — повтор при доборе", …)` и возвращает `None`, не трогая счётчик. `scripts/calibrate_importance.py` оборачивает свой вызов так же и записывает `None`, как раньше.

Альтернатива — вернуть из `score_importance` кортеж или отдельный код. Отклонена: исключение здесь и есть естественный сигнал «временный сбой». Все места вызова `_rate_article` и так обёрнуты в `except Exception`, а прямых вызовов `score_importance` всего два.

### 6. Подборка уходит без неоценённых, если в ней уже ≥ 3 актов

- `weekly_review.py`: `WEEKLY_MIN_ACTS_WITHOUT_WAIT = 3` рядом с `WEEKLY_MIN_IMPORTANCE` и чистая функция `expected_selection(window)` — документы окна с `include`, а также без решения и с оценкой ≥ `WEEKLY_MIN_IMPORTANCE`, в порядке подборки, без требования саммари. `final_selection` = `expected_selection` с саммари.
- `_send_weekly_digest`: после финального прохода подборка откладывается, только если `unrated`, `len(expected_selection(window)) < WEEKLY_MIN_ACTS_WITHOUT_WAIT` и ещё не наступило воскресенье 21:00. Иначе, если `unrated` не пуст, пишется существующий `logger.warning` со списком id, затем попытка 2 и `final_selection`. Повторной проверки N после попытки 2 нет.
- Почему без саммари: акт с оценкой ≥ 2 без саммари почти всегда получает его на попытке 2, а она идёт после решения об отправке. Если считать по `final_selection`, подборка откладывалась бы из-за таких актов. Альтернатива «попытка 2 до подсчёта» отклонена: пока подборка отложена, попытка повторялась бы каждые 15 минут.
- Почему 3: решение пользователя. Важна периодичность, а 1–2 акта — повод подождать неоценённых, которые могут дополнить подборку. Настройку в `.env` не выносим (KISS).
- Без неоценённых поведение прежнее: уходит любое число актов, пустая подборка не отправляется. `/test_digest weekly` и панель используют `final_selection` и не меняются.

## Risks / Trade-offs

- [Акт получил `1` по пустому входу, а позже у него появились настоящий текст или саммари] → Повторной оценки не будет, и важный акт может не попасть в подборку. Ситуация редкая: модель должна не найти информации и в названии. Администратор может включить акт вручную (`digest_override = include`). Если окажется, что «пустой» вход — заглушка портала, это закроет вариант D.
- [Акт упёрся в лимит, и у него потом появился текст] → До финального прохода или перезапуска он не оценивается. Значит, фоновое саммари для оценки ≥ 2 не запускается, а финальный проход оценит акт по тексту и запустит саммари. Задержка — до пятницы.
- [Упорно невалидный акт на тонкой неделе] → Финальный проход игнорирует лимит, поэтому, пока в подборке меньше 3 актов, такой акт держит её до воскресенья 21:00 и тратит 2 вызова за цикл. Если актов уже 3 и больше, подборка уходит без него (п. 6). Бесконечный `null` закрыт п. 2, а для остального нужно, чтобы модель дважды подряд сломала формат в каждом цикле. Если это повторится, в логе будет `external_id`, и вопрос решим отдельно.
- [Подборка ушла без неоценённого акта, а позже он получил высокую оценку] → В подборку он не попадёт: окно считается по `created_at`. Неоценённые видны админу в панели до отправки, напоминание приходит в 12:00, акт можно включить вручную.
- [После попытки 2 подборка может уйти с 1–2 актами] → Так решено: решение об отправке принимается один раз, повторно подборка не откладывается.
- [Модель начнёт отвечать `null` массово, например после смены модели] → Многие акты получат `1` вместо настоящей оценки. Это видно в логе по строкам «нет информации» с id, и `scripts/calibrate_importance.py` это покажет.
- [Частые перезапуски сбрасывают счётчик] → Каждый перезапуск даёт ещё до 3 циклов на акт. На Dockhost перезапуски редки, и это приемлемо (#11).

## Migration Plan

Миграций нет. Акты, которые уже застряли с `null`, в первом же цикле добора после деплоя получат оценку по названию или `1`. Откат — возврат коммита: уже поставленные `1` останутся в БД, это допустимо.
