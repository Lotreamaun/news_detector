## Context

Вся логика живёт в одной функции — `_summarize_and_reply()` (`app/bot/handlers.py`), которую вызывают четыре обработчика: `force_summarize` (кнопка на одиночном уведомлении, передаёт `message=query.message` — результат **правит** это сообщение через `_deliver`), `force_summarize_digest` (кнопка в тизере дайджеста, передаёт только `status_message` — результат уходит **новым** сообщением), `/summary` и `/notify_me` (оба передают `status_message`, результат — новым сообщением).

Внутри `_summarize_and_reply` уже есть готовый правильный паттерн для одного из четырёх исходов — отказ GigaChat (`except GigaChatError`, строки ~839-868): он вызывает `_summary_refused(config, title, url, fallback, external_id)`, которая строит `*заголовок*\n\n_фолбэк_\n\n[Читать на портале](url)` + кнопку «Полный текст», и это уходит через `_deliver`. Три другие исхода той же функции — лимит исчерпан (~709-728), текст недоступен (~767-775), generic `except Exception` (~869-877) — вместо этого зовут `_deliver` с голой строкой, `parse_mode=None`, `reply_markup=None`. Когда `_deliver` при этом правит существующее сообщение (кнопочный путь), голая строка заменяет собой всё уведомление целиком.

## Goals / Non-Goals

**Goals:**
- Все четыре исхода `_summarize_and_reply` (успех уже ок; отказ LLM уже ок; лимит; текст недоступен; ошибка) используют один и тот же формат сообщения при неудаче: заголовок + причина + ссылка на портал.
- Заголовок и ссылка достаются без лишнего похода в БД там, где это возможно.
- Правка не меняет поведение успешного пути и уже работающей ветки `GigaChatError`.

**Non-Goals:**
- Не меняется логика лимитов, OCR, самого механизма саммаризации.
- Не меняется формат дайджест-тизера (`_build_digest`) — там своя логика, вне `_summarize_and_reply`.
- Не добавляется автоматический повтор саммаризации — только текстовая подсказка про ручной `/summary`.

## Decisions

**Переиспользовать `_summary_refused`, а не писать новую функцию.** Три сломанные ветки (лимит, текст недоступен, generic-ошибка) получают ровно ту же форму сообщения, что уже строит `_summary_refused(config, title, url, fallback, external_id)`. Ветки отличаются только текстом `fallback` и тем, добавлять ли кнопку «Полный текст». Проще всего дать `_summary_refused` необязательный параметр (например, `with_webapp_button: bool = True`) и звать её из всех четырёх мест вместо дублирования сборки заголовка/ссылки. Альтернатива — три новых похожих функции — отвергнута: это ровно тот вид дублирования, который `.cursor/rules/conventions.mdc` просит не плодить.

**Кнопка «Полный текст» — только когда есть реальный текст.** В ветке «текст недоступен» текста нет вообще (ни прямого, ни OCR) — показывать кнопку в WebApp, ведущую к точно такому же сообщению «текст недоступен» (см. `content-viewing`), бессмысленно и создаёт мёртвый тап. В ветках «лимит исчерпан» и «ошибка» текст тоже не был получен на этом прогоне — кнопка также не добавляется. Это совпадает с уже существующим правилом `_summary_final`: «кнопка показывается только когда есть что показать».

**Источник заголовка/ссылки — переиспользовать уже загруженный `cached`, а не делать новый запрос.** В начале `_summarize_and_reply` уже есть `cached = await session.scalar(select(Article)...)` (используется для проверки закешированного саммари) — он же даёт `title`/`url` для веток «лимит» и «текст недоступен» без дополнительного обращения к БД. Ветка `GigaChatError` сегодня делает свой отдельный запрос `art` — можно оставить как есть (не в рамках этого фикса трогать соседний рабочий код) или тоже переиспользовать `cached`, если это не усложнит diff; решение оставлено на этап реализации, поведенчески не отличается. Если `cached` не найден (закон ещё не в БД — редкий путь для `/summary` по внешнему `external_id`, которого нет локально), используется тот же фолбэк, что и сегодня: `title = external_id`, `url = f"http://publication.pravo.gov.ru/document/{external_id}"`.

**Подсказка про `/summary <external_id>` — только в ветке «текст недоступен».** Именно там кнопка «Сделать саммари» пропадает безвозвратно и юзеру нужен явный путь повторить попытку позже. В ветке «лимит исчерпан» подсказка не нужна — лимит сам объясняет, когда повторить («в следующем месяце»); в ветке generic-ошибки текст уже говорит «Попробуйте позже» — воздержимся от подсказки с командой, чтобы не путать с ошибкой текста (можно добавить при реализации, если легко ляжет, но не обязательно по спеке).

**MarkdownV2-экранирование.** `_summary_refused` уже экранирует заголовок и фолбэк через `escape_markdown(..., version=2)` — при переиспользовании это не меняется; `parse_mode="MarkdownV2"` должен передаваться в `_deliver` теперь и для этих трёх веток (сегодня передаётся `parse_mode=None` — баг сам по себе, т.к. голая строка и не нуждалась в разметке, но после фикса разметка обязательна).

**[Ревизия после ручного тестирования] Notification-style только когда закон реально известен.** Изначальное решение (см. выше) переиспользовало `_summary_refused` во всех трёх ветках одинаково, подставляя `external_id` как заголовок, если `cached is None`. На практике (ручной тест `/summary` с несуществующим `external_id`) это выглядит как уведомление о законе, у которого на самом деле нет ни заголовка, ни подтверждённой ссылки — вводит в заблуждение. Разделили по наличию `cached`:
- `cached is not None` (обычный случай для кнопки — она есть только на уже сохранённых статьях) → как раньше, `_summary_refused` (жирный заголовок + причина + ссылка + опционально кнопка «Полный текст»).
- `cached is None` (реалистично только для `/summary` с `external_id`, которого бот не отслеживает) → новая `_summary_refused_plain`: обычный текст без псевдозаголовка, но с `external_id` (для сверки) и той же канонической ссылкой `.../document/<external_id>` (это не «угадывание» — тот же паттерн уже использовался как фолбэк-URL в проекте, просто теперь не завёрнут в оформление уведомления).

Диспетчеризация вынесена в `_deliver_summary_failure` — общий вызов для всех трёх веток (лимит/текст недоступен/ошибка), чтобы не дублировать `if cached is not None: ... else: ...` трижды.

## Risks / Trade-offs

- [Риск] Расширение сигнатуры `_summary_refused` может задеть единственный существующий вызов (ветка `GigaChatError`) → мера: новый параметр опциональный с дефолтом, сохраняющим текущее поведение этого вызова (кнопка показывается, как сейчас).
- [Риск] Escape-функция должна одинаково хорошо экранировать все виды fallback-текста (включая эмодзи 😢, которое не является спецсимволом MarkdownV2 и не требует экранирования) → проверить вручную при реализации, что сообщение доходит без `Bad Request: can't parse entities`.
- [Риск] `cached` может быть `None`, если `/summary` вызван по `external_id`, которого ещё нет в БД, — тогда заголовок будет просто `external_id` (как и сегодня) → это уже текущее поведение, не регрессия.
