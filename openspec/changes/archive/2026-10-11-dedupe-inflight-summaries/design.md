## Context

См. proposal.md — Why. Текущее состояние, на которое опирается решение:

- `force_summarize(config, session_maker, user, external_id)` в `app/services/force_summary.py` — общее ядро трёх точек входа: бот (`handlers._summarize_and_reply` для `/summary` и кнопок), Mini-App (`server.handle_summarize`), панель модерации (`admin.py`, с временным `User(telegram_id=admin_id)` без `id`). Все они ждут `ForceSummaryResult` и сами формулируют ответ; результат только читают, не меняют.
- Порядок внутри сейчас: чтение `Article` → лечение псевдозаголовка (`fetch_document`, сеть pravo.gov.ru) → готовое саммари из БД (`ok` без лимита) → проверка лимита (`limit`) → текст / OCR → сохранение текста → `Summarizer.summarize` → сохранение саммари (или создание `Article`) → +1 к `SummarizationUsage` **в той же сессии** → `ok`. Сбои GigaChat → `refused`/`error`, прочее → `error`; исключения наружу не выходят.
- Всё работает в одном event loop одного процесса (PTB + aiohttp, см. спеку `deployment`). Между проверкой и действием в коде есть `await` (БД, сеть) — значит возможны гонки двух корутин.
- PTB обрабатывает апдейты последовательно (`Application.builder()` без `concurrent_updates`): два запроса из одного только бота сейчас не пересекаются — второй ждёт завершения первого и получает саммари из БД. Реально параллельны пары бот ↔ Mini-App, Mini-App ↔ Mini-App, панель модерации ↔ любой; после change `async-summary-delivery-bot` — и бот ↔ бот.
- aiohttp 3.13 по умолчанию не отменяет хендлер при обрыве соединения клиента, но полагаться на это не стоит: отмену может принести и остановка PTB, и будущие точки входа.
- Фоновая саммаризация планировщика `_summarize_in_background(context, session_maker, summarizer, llm_client, article)` в `app/services/scheduler.py` — вне `force_summarize`: текст (при отсутствии — OCR, один раз за процесс по `ocr_tried`) → `summarizer.summarize` → `_update_article(summary=...)` и `article.summary` в памяти; неудача ничего не пишет в `summary`. Вызывается из `_rate_article` при оценке ≥ 2 без саммари (добор оценок `_rate_backlog`; для новых документов из `_process_entry` — только если текста не было, `summary_tried`) и в пятничном финальном проходе `_maybe_send_weekly_digest` («попытка 2» для `needs_summary_retry`). Объект `article` загружен в начале прохода и может устареть. Финальный проход сразу после «попытки 2» исключает из подборки документы без `summary` **в памяти** — по тому же списку `window`, без перечитывания.
- Саммаризация новых документов в `_process_entry` идёт до `_save_article` и до рассылки: документа ещё нет в БД, пользователь его не видит.

## Goals / Non-Goals

**Goals:**
- Одна работа на документ, сколько бы запросов ни пришло, пока она идёт.
- Итог работы доходит до всех ожидающих, даже если запустивший запрос отменён.
- Фоновая саммаризация не дублирует уже идущую пользовательскую и не вызывает модель, если саммари уже сохранено.
- Никаких изменений в точках входа: контракт `force_summarize` прежний, у `ForceSummaryResult` только добавляется поле со значением по умолчанию.
- Основа для changes `async-summary-delivery-*`: тот же реестр будет держать фоновую работу, к которой привязывается доставка.

**Non-Goals:**
- Присоединение пользовательского запроса к уже идущей фоновой саммаризации (фон начал первым) — кандидат на отдельный change после `gigachat-single-stream-queue`, когда станет ясна механика приоритетов (P2, по наблюдениям). См. Risks.
- Саммаризация новых документов в `_process_entry` — документ пользователю ещё не виден.
- Сериализация вызовов GigaChat между разными документами — change `gigachat-single-stream-queue`.
- Сохранение реестра между перезапусками — принято, что задачи теряются при редеплое.
- Изменение кулдауна Mini-App после неудачи.

## Decisions

1. **Разделить `force_summarize` на «пользовательскую» и «документную» части.** Пользовательская (остаётся в `force_summarize`): присоединение к идущей работе, проверка лимита, списание попытки. Документная (новая приватная корутина, условно `_summarize_document(config, session_maker, external_id)`): перечитывание `Article` (п. 5) → текст / OCR → сохранение текста → саммари → сохранение `Article` → `ForceSummaryResult` со статусом `ok`/`no_text`/`refused`/`error`. Документная часть не знает про пользователя — поэтому её результат можно отдать любому числу ожидающих. Статус `limit` по построению возникает только в пользовательской части и не может «утечь» к другим (сценарий «Исчерпанный лимит не передаётся другим»). Название/ссылку для любых исходов документная часть берёт из перечитанной записи.
   - Альтернатива — общий результат всего `force_summarize` целиком — отвергнута: лимит и списание — свойства пользователя, их нельзя разделять между запросами.

2. **Реестр — модульный словарь `external_id → asyncio.Task`, без списка ожидающих.** Задача создаётся `asyncio.create_task(_summarize_document(...))`; при любом завершении (успех, неудача, отмена) `add_done_callback` снимает запись с реестра и, если задача завершилась исключением, забирает его и пишет `logger.error` с `external_id` (иначе, если все ожидающие отменены, остаётся только «Task exception was never retrieved»). Живёт в памяти процесса, как и кулдаун Mini-App (`app["summarize_failed_at"]`). Модульный уровень, а не `bot_data`/`app[...]`, — потому что ядро вызывают и бот, и aiohttp, а у них разные «карманы»; сам модуль `force_summary` у них общий.
   - «Ожидающие» нигде не записываются: это корутины, которые ждут задачу (п. 3); asyncio будит их всех по её завершении. Changes `async-summary-delivery-*` доставляют результат так же — фоновой корутиной «дождись задачи и отправь», явный список им не нужен. Список понадобится только для доставки после рестарта (`persist-pending-summaries`), и тогда он будет в БД.
   - Альтернатива — `asyncio.Future` с ручной установкой результата — отвергнута: задача сама хранит результат/исключение и сама снимается с реестра.

3. **Ожидание через `asyncio.shield(task)` — и у инициатора, и у присоединившихся, и у фона.** Отмена любого ожидающего (обрыв, остановка) не отменяет работу; остальные получают результат, а сохранение в БД доводится до конца (сценарий «Запустивший запрос прерван»). Инициатор не «владеет» задачей — он лишь первый ожидающий.

4. **Порядок проверок в `force_summarize` и защита от гонки:**
   ```
   1. есть задача в реестре? ──да──► await shield(task) → вернуть (без лимита, без списания)
   2. чтение Article, лечение псевдозаголовка, готовое саммари → ok      (как сейчас)
   3. проверка лимита → limit                                           (как сейчас)
   4. есть задача в реестре? ──да──► присоединиться (как в п.1)
      нет ─► create_task + запись в реестр          ← между 4-й проверкой и записью нет await
   5. await shield(task)        (задача сначала перечитывает Article — п. 5)
   6. ok, не from_cache, не админ, не уровень без лимита → +1 инициатору (своя короткая сессия)
   ```
   Проверка 1 даёт присоединившемуся обойти лимит и лишние обращения к БД/порталу. Проверка 4 закрывает гонку с задачей, созданной, пока инициатор шёл через `await` в шагах 2–3: между `get` и записью в словарь нет точек переключения корутин — значит две задачи на один документ возникнуть не могут. Гонку с задачей, которая за это время **успела завершиться** (в реестре её уже нет, а саммари уже в БД), закрывает перечитывание в начале задачи (п. 5).
   - Остаточное окно: присоединившийся с исчерпанным лимитом, пришедший в те миллисекунды, пока первый запрос ещё в шагах 2–3, получит `limit`. Приемлемо — после создания задачи он присоединится.

5. **Задача начинает с перечитывания `Article`.** Если саммари уже сохранено (завершилась другая принудительная саммаризация или фон), задача возвращает `ok` с `from_cache=True`, не обращаясь к порталу и модели. Это один `select` — дешевле любой альтернативы и закрывает окно из п. 4 (сценарий «Саммари появилось, пока запрос проходил проверки»).

6. **`ForceSummaryResult`: `@dataclass(frozen=True)` и поле `from_cache: bool = False`.** Один экземпляр отдаётся всем ожидающим — неизменяемость исключает плавающие ошибки, если кто-то начнёт его менять. `from_cache=True` — модель не вызывалась (саммари взято из БД в п. 5); по нему `force_summarize` не списывает попытку и пишет это в лог. Точки входа поле не читают. Готовое саммари на шаге 2 тоже возвращается с `from_cache=True` — одно значение признака для обоих путей выдачи из БД.
   - Альтернатива — задача возвращает пару `(результат, вызывалась_ли_модель)` — отвергнута: тип сложнее, а признак полезен и в логах, и в changes `async-summary-delivery-*`.

7. **Списание лимита — после завершения задачи, отдельной сессией.** Сейчас +1 делается в той же сессии, что и сохранение саммари. После разделения документная часть ничего не знает о пользователе, поэтому `SummarizationUsage` обновляется в `force_summarize` отдельной короткой сессией только при `ok` и `not from_cache`. Окно между сохранением саммари и списанием не меняет наблюдаемое поведение (при сбое или отмене ожидания инициатора между ними попытка просто не спишется — в пользу пользователя). Условия списания (`is_admin`, `auto_bypass` по уровню из БД) вычисляются, как сейчас, до запуска задачи.

8. **Фон уступает пользовательской саммаризации.** `force_summary` отдаёт хелпер `inflight_task(external_id) -> asyncio.Task | None` (выполняющаяся задача из реестра). В начале `_summarize_in_background`, до получения текста и OCR:
   ```
   1. перечитать Article.summary из БД ──есть──► article.summary = …, выйти (модель не вызывается)
   2. inflight_task(external_id)? ──да──► result = await shield(task)
         ok      ─► article.summary = result.summary (и original_text, если пусто), выйти
         неудача ─► лог, выйти без своей попытки
   3. дальше — как сейчас
   ```
   Охватывает все вызовы `_summarize_in_background` — добор оценок и пятничную «попытку 2».
   - Почему фон **ждёт**, а не пропускает документ: финальный проход сразу после «попытки 2» исключает документы без `summary` в памяти (Context) — пропуск выбросил бы из подборки документ, чьё саммари будет готово через секунды. Цикл шедулера последовательный и потратил бы на ту же работу столько же времени сам.
   - Почему хелпер, а не вызов `force_summarize`: у фона нет пользователя, лимит и списание к нему неприменимы; фон только наблюдает за реестром и сам в него задачи не кладёт.
   - Неудача пользовательской саммаризации засчитывается фону как неудачная попытка — по той же логике, что «неудача отдаётся всем присоединившимся».

9. **Логи.** Инициатор: «Саммари %s: запуск (user=%s)». Присоединившийся: «Саммари %s уже в работе — присоединяем запрос user=%s». Задача: «Саммари %s уже в БД — модель не вызываем». Фон: «Фоновое саммари %s: уже в БД — пропускаем» и «Фоновое саммари %s: ждём пользовательскую саммаризацию». Колбэк: ERROR при исключении задачи. По ним проверка на живом боте (см. tasks).

## Risks / Trade-offs

- [Задача-«сирота» при остановке процесса] → при shutdown loop отменит задачу; результат не сохранится — то же, что сейчас при рестарте посреди саммаризации.
- [Исключение задачи, которое никто не забрал] → логируется колбэком (п. 2), а не теряется.
- [Долгая работа держит всех присоединившихся] → OCR может идти минуты; присоединившийся ждёт столько же, сколько ждал бы со своим запросом, но без второго запроса в GigaChat. Решение для UX ожидания — changes `async-summary-delivery-*`.
- [Цикл шедулера ждёт пользовательскую задачу] → при OCR до минут; столько же цикл потратил бы на эту работу сам, и без второго вызова GigaChat.
- [Неудача отдаётся всем присоединившимся и фону] → это намеренно: повтор того же документа через секунды почти наверняка кончился бы так же (та же логика, что у кулдауна Mini-App по документу).
- [Обход лимита присоединением] → пользователь с исчерпанным лимитом получает саммари только если его уже кто-то делает и оплачивает; новой работы он не запускает. Равносильно выдаче сохранённого саммари.
- [Фон начал первым] → пользовательский запрос по документу, который фон уже саммаризует (например, во время OCR), реестр не видит и запускает свою работу: два вызова модели, и фон, закончив последним, перезапишет саммари (корректным, но другим текстом). Принято: окно — конкретный документ в конкретные секунды/минуты работы фона; всплеск пользовательских запросов приходится на момент рассылки, а фон берётся за документ позже, когда появляется текст. Закрывается присоединением пользователя к фоновой работе (Non-Goals) — если такие случаи появятся в логах.
- [Несколько процессов] → реестр не общий; сервис работает одним процессом (спека `deployment`).

## Migration Plan

Изменение в `app/services/force_summary.py` и `app/services/scheduler.py` (`_summarize_in_background`), без БД и конфигурации. Деплой — новой версией через `release/stage-10-prod` вместе с остальными P0 этапа 10; откат — предыдущей версией.
