## Context

В `_summarize_and_reply` (`app/bot/handlers.py`) закон не из ленты сохраняется как `Article(title=external_id, url=<канонический>, level=None)`: настоящего названия у бота нет. Признак «заголовок известен» (`title_known`) вычисляется только как `article is not None` (успешный путь, ветка `GigaChatError`). В ветке кэша он вообще не передаётся (по умолчанию `True`). `_deliver_summary_failure` выбирает формат по `cached is not None`. Поэтому запись с `title == external_id` при повторном запросе выводится с жирным id.

Проверено на живом API: `GET http://publication.pravo.gov.ru/api/Document?eoNumber=<id>` отвечает около 0,3 с. Он возвращает объект с теми же полями, что и элементы ленты `/api/Documents` (`eoNumber`, `title`, `complexName`, `documentTypeId`, …). Для неизвестного id приходит `{"message": "Документ не найден: <id>"}`.

## Goals / Non-Goals

**Goals:**
- Записи о законах не из ленты хранят настоящие название, ссылку и уровень.
- Уже сохранённые записи с псевдозаголовком лечатся при следующем обращении, без миграции.
- Сбой портала не ломает `/summary` и не приводит к жирному id.

**Non-Goals:**
- Правки кода WebApp и `/notify_me`: они исправляются сами, когда в БД настоящее название.
- Пакетная миграция старых записей: лечение только по обращению.
- Название с портала в сообщениях о неудаче для id, которого нет в БД. Там остаётся простое служебное сообщение (требование `force-summarization` «Отказоустойчивое сообщение…» не меняется).

## Decisions

**1. `fetch_document(external_id) -> FeedEntry | None` в `app/services/rss_parser.py`.**
Эндпоинт — `/api/Document?eoNumber=<id>` на хосте из `_PUBLICATION_DOCUMENT_URL` / ленты. Функция берёт ответ через `_fetch_with_retries`, парсит JSON и отдаёт объект в существующий `_entry_from_item`. Любая ошибка (`RssError`, не-JSON, нет `eoNumber`, `message` вместо документа) даёт `None` и запись в лог. Контракт «никогда не бросает» тот же, что у `get_legal_text`.
*Альтернатива:* искать документ через `/api/Documents?...` с фильтром. Отклонена: фильтра по `eoNumber` у списка нет (параметр игнорируется, приходит вся лента), а отдельный эндпоинт отдаёт ровно один документ.
*Альтернатива:* колонка-флаг «заголовок неизвестен» в `Article`. Отклонена: нужна миграция, а признак однозначно следует из данных (`title == external_id`).

**2. Уровень — через `classify_level_for_title(entry.title, entry.document_type_id)`**, как в шедулере (`_process_entry`). Ссылка — `entry.url`.

**3. Лечение найденной записи — в начале `_summarize_and_reply`, до расчёта `auto_bypass`.**
После загрузки `cached`: если запись есть и `not _has_real_title(cached, external_id)`, вызываем `fetch_document`. При успехе обновляем `title`/`url`/`level`, коммитим и дальше работаем с исправленной записью. Так исправленные название и уровень используются во всех ветках: в кэше, в проверке лимита (ФКЗ/ФЗ обходят лимит), в сообщениях о неудаче. Для этого текущая отдельная выборка `Article.level` для `auto_bypass` переносится после лечения и считается из `cached.level`.

**4. Создание записи — `fetch_document` перед `Article(...)`** в успешном пути и в ветке `GigaChatError`. Сеть к моменту создания уже была задействована (текст/OCR/LLM), так что +0,3 с незаметны. Если `fetch_document` вернул `None`, пишем `title=external_id`, канонический `url`, `level` не задаём — как сейчас. Чтобы не дублировать код, обе ветки используют маленький хелпер, который строит `Article` по результату `fetch_document`.

**5. Признак для вывода — `_has_real_title(article, external_id) -> bool`** (`False`, если записи нет, `title` пуст или равен `external_id`). Он заменяет `is not None` в `title_known` всех веток и в выборе формата `_deliver_summary_failure` (псевдозаголовок → `_summary_refused_plain`). В ветке кэша передаётся в `_summary_final`. Это запасной путь на случай, когда портал не ответил.

## Risks / Trade-offs

- [Портал недоступен] → `fetch_document` возвращает `None`, срабатывает запасной путь, пользователь получает ответ без жирного id. Время ограничено ретраями `_fetch_with_retries` (как для текста).
- [Портал долго недоступен, а пользователь много раз запрашивает одну и ту же запись с псевдозаголовком] → на каждый запрос одна лишняя попытка запроса. Приемлемо: это редкий путь (только законы не из ленты), нагрузка ограничена месячным лимитом и ручным характером `/summary`.
- [Изменение формата ответа портала] → `_entry_from_item` уже терпим к отсутствию `title` (фолбэк на `complexName`). При полном несовпадении — `None` и запасной путь.
- [Реальный уровень ФКЗ/ФЗ включает обход лимита для законов не из ленты] → поведение согласовано с законами из ленты (`auto_bypass` по `level`), это ожидаемо.
