## Context

Реализован `force_summarize` (callback кнопки) в `app/bot/handlers.py`. Его логика: регистрация пользователя, проверка лимита `SummarizationUsage`, получение текста (`get_legal_text` → OCR `ocr_document_text`), `Summarizer.summarize`, обновление `Article`, инкремент счётчика, отправка саммари нажавшему. `_build_notification` в `app/services/scheduler.py` уже возвращает `(text, InlineKeyboardMarkup)` с кнопкой «Сделать саммари». /latest уже показывает саммари при наличии. См. proposal.md; требования в specs/manual-summary-request/spec.md.

## Goals / Non-Goals

**Goals:**
- Команда `/notify_me <external_id>`: отправить пользователю уведомление с кнопкой по закону из БД (тест без новых законов)
- Команда `/summary <external_id>`: принудительная саммаризация конкретного закона
- Обе команды делят единый месячный лимит 10 с кнопкой
- Переиспользовать существующую логику, не дублировать

**Non-Goals:**
- Кнопки внутри списка `/latest` (криво — один reply_markup на сообщение)
- Произвольные изменения лимита
- Платёжная логика (остаётся TODO)

## Decisions

### 1. Общая функция принудительной саммаризации `_summarize_and_reply`

Извлекаем из `force_summarize` тело (валидация лимита + получение текста + саммари + обновление + инкремент + отправка) в переиспользуемую async-функцию:

```
async def _summarize_and_reply(context, user, external_id) -> str | None
```

- Принимает уже зарегистрированного `user` и `external_id`.
- Возвращает итоговый текст саммари (для отправки) или `None` (сбой/лимит), причём в случае лимита/ошибки сама отправляет сообщение пользователю через `context.bot.send_message`.
- Использует `context.bot` напрямую (а не `query.message`), чтобы её можно было звать и из callback, и из команды.

### 2. Callback `force_summarize` — использует общую функцию

`force_summarize` остаётся тонкой обёрткой:
- парсит callback_data, регистрирует пользователя
- вызывает `_summarize_and_reply`
- результат шлёт через `answer_callback_query` (а текст — через `context.bot.send_message(chat_id=user.telegram_id)`), либо через общую функцию, которая сама шлёт.

Уточнение: общая функция шлёт текст саммари в личку пользователю. Для callback это приемлемо (сообщение-результат приходит от бота). `answer_callback_query()` вызывается без текста, чтобы снять индикатор нажатия.

### 3. Команда `/notify_me <external_id>`

- Принимает аргумент `external_id` (через `context.args`).
- Ищет `Article` в БД; если нет — сообщение «закон не найден».
- Если есть — вызывает `_build_notification(article)` (даёт текст+кнопку) и `context.bot.send_message(chat_id, text=..., reply_markup=...)`.
- Не тратит счётчик месячного лимита (это только тест кнопки, саммаризация не выполняется, пока не нажать кнопку).

### 4. Команда `/summary <external_id>`

- Принимает аргумент `external_id`.
- Регистрирует пользователя, вызывает `_summarize_and_reply`.
- Делит общий лимит с кнопкой (та же таблица `SummarizationUsage`, тот же ключ user+month).

### 5. Регистрация в `app/main.py`

Добавить `CommandHandler("notify_me", notify_me)` и `CommandHandler("summary", summary_command)`. В `HELP_TEXT` добавить описания. В `_register_commands` (set_my_commands) добавить записи.

### 6. Обработка ошибок и сообщений

- Обе команды работают через `update.message.reply_text` для подсказок/ошибок (аргумент отсутствует, закон не найден, лимит).
- Общая функция саммаризации ловит исключения и отправляет понятное «Не удалось сделать саммари».

## Risks / Trade-offs

- [Рефакторинг force_summarize] — вынос тела в общую функцию может слегка переработать существующий работающий callback. Компенсируем: поведение сохраняется, callback-часть логики идентична; проверяется py_compile и логически.
- [Два канала (callback/команда)] — для кнопки результат выводится правкой исходного сообщения, для команды — обычным reply/новым сообщением. Приемлемо.
- [Общий лимит] — кнопка и /summary делят один лимит (по замыслу), поэтому злоупотреблений одним каналом не будет.

## Доработки (итерация 2)

### Процесс и результат кнопки

1. **Генерация результата в том же сообщении (кнопка).** `_summarize_and_reply` получает «цель доставки» результата:
   - путь **кнопки**: `edit_message_text` исходного сообщения (то, где была кнопка) — сначала на индикатор «⏳ Саммари в процессе создания…», затем на итоговый текст `{title}\n\n{summary}\n\n{url}` без reply_markup (кнопка пропадает).
   - путь **команды** `/summary`: `send_message`/reply_command — новое отдельное сообщение (исходного сообщения с кнопкой нет).
   Для этого `force_summarize` передаёт в `_summarize_and_reply` исходное сообщение (`query.message`, chat_id + message_id) как цель правки, а `summary_command` — цель на новый reply.

2. **Индикатор процесса.** При нажатии кнопки сразу:
   - `edit_message_text(query.message, text="⏳ Саммари в процессе создания…", reply_markup=None)` — убираем кнопку и показываем состояние;
   - затем после завершения генерации — `edit_message_text` того же сообщения на финальный результат.
   `query.answer()` вызывается без текста, чтобы снять индикатор нажатия (toast не нужен, т.к. состояние показано правкой сообщения).

### Приём ссылки в /summary

`summary_command` (и опционально `notify_me`) перед саммаризацией прогоняет аргумент через хелпер `_resolve_external_id(value)`:
- если `value` — голый id (без `/` и без `http`) → возвращается как есть;
- если `value` — URL вида `http://publication.pravo.gov.ru/document/<id>` (и аналогичные) → извлекается <id> из последнего сегмента пути;
- если не удаётся определить → возвращается `None`, команда шлёт подсказку по использованию.

Хелпер переиспользуется в `summary_command` (обязательно) и `notify_me` (опционально, для единообразия).

## Доработки (итерация 3): переиспользование сохранённого саммари

**Проблема:** `_summarize_and_reply` при каждом вызове безусловно загружает текст (при отсутствии — OCR) и генерирует саммари через GigaChat, даже если для `external_id` в БД уже есть готовое `article.summary`. Повторный `/summary` той же ссылки снова обращается к LLM (OCR + генерация).

**Решение:** перед генерацией проверить наличие готового саммари в БД и вернуть его без LLM.

1. **Проверка до генерации.** В начале `_summarize_and_reply` загрузить `Article` по `external_id`. Если `article.summary` не пуст:
   - сформировать результат `{title}\n\n{summary}\n\n{url}` из сохранённых данных;
   - доставить через `_deliver` (для кнопки — правка исходного сообщения, для команды — новое сообщение);
   - **не** инкрементировать счётчик `SummarizationUsage` (LLM не вызывался) и **не** выполнять загрузку текста/OCR/генерацию;
   - вернуться сразу.

2. **Инкремент лимита — только при реальной генерации.** Инкремент `usage.count` остаётся в ветке, где выполняется новая LLM-генерация. При переиспользовании сохранённого саммари счётчик не меняется.

3. **Кнопка и `/summary` одинаково.** Кэш-проверка живёт в общей функции, поэтому и кнопка, и `/summary` переиспользуют сохранённое саммари. `_resolve_external_id` уже даёт `external_id` и для id, и для ссылки — ключ совпадёт с БД.

**Trade-off:** статья в БД, у которой ещё нет `summary` (например, только собранная как пустая), будет обработана через LLM один раз и затем переиспользована.
