## Context

Мотивация — см. proposal.md («Why»). Текущее состояние кода:

- `app/bot/handlers.py`: три точки входа — `summary_command` (`/summary`), `force_summarize` (кнопка `force_sum:summary:` под уведомлением), `force_summarize_digest` (кнопка `force_sum:digest:` в старых дайджестах). Все три в конце делают `await _summarize_and_reply(...)`, который ждёт `run_force_summarize` (GigaChat, OCR, очередь) прямо в хендлере. `_deliver` для кнопки под уведомлением правит исходное сообщение (`message`), для остальных — удаляет `status_message` и шлёт новое.
- PTB 22.6, `Application.builder()` без `concurrent_updates` — апдейты обрабатываются строго по одному; пока хендлер ждёт, бот молчит для всех.
- `app/services/force_summary.py` (change 1): реестр `_inflight: external_id → Task`, общая задача `_summarize_document`, присоединение через `asyncio.shield`, списание лимита у инициатора после успеха. Проверка лимита — только по `SummarizationUsage.count`, задачи «в работе» не учитываются; сравнение стоит внутри `async with session_maker()`, а выход из него — `await` закрытия сессии, т.е. между сравнением и `create_task` есть точка переключения.
- `app/services/summary_usage.py`: `get_summary_usage` — счётчик `used/limit` для `/settings`, сообщения о лимите и чипа Mini-App; `force_summary.py` импортирует отсюда `current_month`.
- `app/services/gigachat.py` (change 2): `calls_ahead_of_user()` — сколько вызовов API впереди нового пользовательского запроса; пока никому не показывается.

## Goals / Non-Goals

**Goals:**
- Хендлеры саммари завершаются за время пары запросов к Telegram и БД, без ожидания портала и GigaChat.
- Оценка времени без новых зависимостей и без изменения очереди GigaChat.
- Резерв лимита за задачами «в работе» — в общих сервисах (`force_summary.py` + `summary_usage.py`), без изменения схемы БД; счётчик попыток показывает резерв как занятую попытку.

**Non-Goals:**
- Mini-App и панель модерации остаются синхронными (`async-summary-delivery-miniapp` — отдельный change); на них действует только резерв лимита.
- Сохранение задач между перезапусками (`persist-pending-summaries`, P1).
- Присоединение к фоновой саммаризации шедулера (P2, п. 13).
- `concurrent_updates` / `block=False` в PTB.

## Decisions

### 1. Фоновая задача — `asyncio.create_task` с удержанием ссылки в модуле хендлеров

Хендлер делает быстрые шаги в таком порядке: `query.answer()` → `_get_or_create_user` → статус-сообщение (под уведомлением статусом становится само уведомление, переписанное в «⏳ …») → запуск. Пользователь определяется до статуса: если его нет (`None`), не остаётся ни висящего «⏳», ни переписанного впустую уведомления.

Запуск — через обёртку над `_summarize_and_reply(...)`, созданную `asyncio.create_task` и положенную в модульное множество `_summary_tasks` (сильная ссылка, иначе GC может собрать задачу) с `add_done_callback(_summary_tasks.discard)`. Обёртка ловит любое исключение `_summarize_and_reply` (например, `BadRequest` разметки, ошибка БД, `Forbidden`/сеть при отправке), пишет его в лог и делает одну попытку последней доставки: удалить статус-сообщение и отправить простой текст без разметки «Не удалось сделать саммари. Попробуйте позже: /summary <external_id>». Ошибка этой попытки только логируется. Так статус «⏳» не остаётся единственным ответом (принцип «бот не молчит», `docs/vision.md`).

- Альтернатива: `context.application.create_task(...)`. Отклонена: в PTB задачи, созданные так при работающем приложении, **ожидаются в `Application.stop()`** — редеплой во время OCR задержал бы остановку на минуты (а Docker после grace period всё равно убьёт процесс). Потеря задач при редеплое принята решением этапа 10.
- Альтернатива: `concurrent_updates=True` / `block=False`. Отклонены ещё в PLAN: хендлер всё равно держит задачу, а параллельные апдейты ломают последовательную логику `ConversationHandler` и онбординга.

### 2. Оценка времени — колбэк режима из ядра саммаризации

`force_summarize(config, session_maker, user, external_id, on_mode=None)` получает необязательный **синхронный** колбэк `on_mode(mode)`, где `mode` — `"text"` (текст получен с портала) или `"ocr"` (нужно распознавание). Ядро не знает про Telegram — колбэк generic. Контракт: колбэк не блокирует (без `await`, без сетевых вызовов внутри), его исключения ядро ловит и пишет в лог.

- Колбэк передаётся в `_summarize_document` только инициатором — тем, кто создаёт задачу документа. `_summarize_document` вызывает его на месте сразу после определения режима: `"text"` — как только `get_legal_text` вернул текст, `"ocr"` — перед OCR.
- Присоединившийся запрос (к задаче документа, уже бывшей в реестре) колбэк не передаёт и оценку не получает: статус остаётся «⏳ Готовлю саммари — пришлю отдельным сообщением.» до доставки результата.
- Кэш (`from_cache`) и `limit` до `_summarize_document` не доходят — колбэк не вызывается, оценки нет (требование спеки).
- Бот в колбэке сразу, синхронно, снимает `calls_ahead_of_user()` и уже сам запускает задачу правки статус-сообщения (ссылка — в `_summary_tasks`). Ошибка правки (сообщение уже удалено, пользователь заблокировал бота) логируется и не влияет на доставку.
- Альтернатива: ядро запускает колбэк отдельной задачей (`create_task`). Отклонена: после `create_task` задача документа продолжает выполняться синхронно до первого настоящего `await` и успевает войти в `_stream_slot` (выставить `_stream_busy = True`). Колбэк, выполнившийся позже, посчитал бы собственный запрос пользователя «впереди» — при пустой очереди показал бы «занято».
- Альтернатива: ядро само считает `ahead` и передаёт `on_mode(mode, ahead)`. Отклонена: ядро начинает знать про очередь ради показа; синхронный колбэк даёт тот же момент замера.
- Альтернатива: оценка присоединившимся через модульный словарь `_modes[external_id]`. Отклонена: присоединение редко (двойной тап, два пользователя на одном документе); у присоединившегося `calls_ahead_of_user()` почти всегда считает выполняющийся вызов этого же документа — снова ложное «занято»; лишнее состояние и ветка.
- Альтернатива: оценка по `Article.original_text` до запуска (одно статус-сообщение без правки). Отклонена: у большинства документов текст есть на портале, но не в БД — оценка была бы «OCR» почти всегда неверно.
- Альтернатива: опрос состояния ядра из бота. Отклонена: гонка с регистрацией задачи в реестре и лишний цикл.

Тексты статуса (финальные формулировки — на этапе apply):
- сразу: «⏳ Готовлю саммари — пришлю отдельным сообщением.»
- `text`: «⏳ Готовлю саммари — обычно до полуминуты. Пришлю отдельным сообщением.»
- `ocr`: «⏳ Распознаю текст закона — обычно 1–3 минуты. Пришлю отдельным сообщением.»
- при `calls_ahead_of_user() > 0` добавляется строка «Сейчас модель занята другими запросами — может занять больше времени.» Число не показываем: `calls_ahead_of_user()` считает вызовы API, а не людей или документы, и один вызов — это и 3-секундное саммари, и минутный OCR; число дало бы ложную точность, а диапазон уже задаёт порядок ожидания.

### 3. Доставка — всегда новым сообщением

`_deliver` и `_deliver_summary_failure` теряют параметр `message` (правка исходного сообщения) — остаётся одна ветка: удалить `status_message`, `bot.send_message(user.telegram_id, ...)`. Тексты и разметка результатов (`_summary_final`, `_summary_refused`, `_summary_refused_plain`, `limit_message`) не меняются.

Кнопка под уведомлением: статусом становится само уведомление — `status_message = query.message`, `await query.message.edit_text(<статус>, reply_markup=None)`. Один вызов убирает и текст, и кнопку (повторно запустить запрос с этого сообщения нельзя). Ошибка правки пишется в лог и запрос не прерывает. Дальше путь общий: `on_mode` правит это же сообщение, `_deliver` перед отправкой результата удаляет его — в чате не остаётся ни статуса, ни старого уведомления, только результат (новое сообщение, с push). `/summary` и кнопка в дайджесте по-прежнему шлют отдельное статус-сообщение ответом.

Почему так, а не «уведомление остаётся, статус и результат — отдельными сообщениями» (первоначальное решение): у результата тот же заголовок и ссылка, что у уведомления, и в чате лежали два похожих сообщения подряд.
- Альтернатива: вернуть правку результата в самом уведомлении. Отклонена: правка не даёт push, а ожидание теперь может занимать минуты — пользователь мог выйти из чата и пропустить результат; к тому же возвращается вторая ветка `message` в `_deliver`.
- Альтернатива: оставить уведомление как есть. Отклонена: дубль в чате (см. выше).

Ошибки доставки (`Forbidden`, сеть) не ловятся разрозненными `try` в `_deliver`: их ловит обёртка фоновой задачи (решение 1), пишет в лог и делает попытку последней доставки; саммари к этому моменту уже сохранено ядром.

### 4. Резерв лимита — учёт попыток «в работе» в `summary_usage.py`

Учёт живёт в `app/services/summary_usage.py`: модульный `_reserved: dict[int, int]` (ключ — `telegram_id`; у панели модерации `User` не персистентный и без `id`, но админы и не резервируют) и три функции — `reserve(tid)`, `release(tid)` (запись удаляется при нуле), `reserved(tid)`. Не в `force_summary.py`: тот уже импортирует `current_month` из `summary_usage`, а `get_summary_usage` должен читать резерв — получился бы циклический импорт. У счётчика попыток одно место.

Проверка лимита в `force_summarize` (только при `charge` — не админ, не `AUTO_LEVELS`):
1. Внутри `async with session_maker()` только читаем `count` (0, если строки `SummarizationUsage` нет).
2. После выхода из сессии — одним синхронным куском, **без `await`**: сравнение `count + reserved(tid) >= limit` → `limit`; повторная проверка `_inflight` — если задача по документу уже есть, запрос присоединяется к ней без резерва; иначе `reserve(tid)` + `create_task` + запись в реестр.

Почему так: выход из `async with` — это `await` закрытия сессии. Если сравнивать внутри сессии, два запроса одного пользователя по разным документам успели бы оба сравнить при нулевом резерве и оба запуститься при одной попытке.

Резерв снимается (`release`) в `finally` вокруг ожидания задачи — только если его ставил этот вызов: после коммита списания при успехе, сразу при неудаче или отмене вызывающего.

`get_summary_usage` возвращает `used = min(count + reserved(tid), limit)`: `/settings`, сообщение о лимите (`limit_message`) и чип Mini-App показывают одно и то же — попытка «в работе» видна как занятая, после неудачи возвращается. Тексты и Mini-App не меняются.

- Присоединение к выполняющейся задаче и выдача кэша проходят до проверки лимита — резерв на них не влияет (как в спеке).
- Альтернатива: снимать резерв в done-callback задачи документа. Отклонена: задача документа не знает про пользователя, а списание всё равно делает вызывающий; если вызывающего отменили (обрыв соединения Mini-App), списания не будет — значит и резерв держать незачем.
- Альтернатива: `asyncio.Lock` на пользователя вокруг проверки и запуска. Отклонена: лишняя сущность при том же результате.
- Альтернатива: словарь в `force_summary.py` и ленивый импорт внутри `get_summary_usage`. Отклонена: ленивые импорты в проекте не используются, учёт размазан по двум модулям.
- Альтернатива: отдельный текст отказа «последняя попытка уже в работе — дождитесь результата». Отклонена: нужен новый признак в `ForceSummaryResult` и правка обоих клиентов; учёт резерва в счётчике снимает противоречие «использованы (4/5)» без новых текстов.

## Risks / Trade-offs

- [Редеплой во время саммаризации — пользователь не получит результат, статус «⏳» останется висеть] → принято (PLAN, P0). Саммари, если успело сохраниться, выдаётся из БД по повторному запросу. Лечение — `persist-pending-summaries` (P1).
- [Быстрые ответы (кэш, лимит) дают «мигание»: статус появляется и сразу удаляется] → принято ради единого пути; альтернатива (проверять кэш в хендлере) дублирует логику ядра.
- [Пользователь жмёт кнопку быстрее, чем уведомление переписывается в статус / шлёт `/summary` повторно] → повтор присоединяется к выполняющейся задаче (change 1): GigaChat не вызывается, лимит не тратится; придут два одинаковых сообщения — допустимо.
- [Флуд `/summary` по разным документам уровней без лимита или админом] → каждая задача ждёт в общей очереди GigaChat; бот не блокируется. Отдельного ограничения не вводим.
- [Присоединившийся никогда не видит оценку, только «⏳ Готовлю саммари…»] → принятое упрощение (см. решение 2).
- [Колбэк оценки сработал после доставки результата и удаления статуса] → правка падает с ошибкой «сообщение не найдено», ловится и логируется; на практике маловероятно — режим известен до вызова модели.
- [Окно между коммитом списания и снятием резерва: попытка посчитана дважды, новый запрос того же пользователя в эти миллисекунды может получить «лимит» при одной оставшейся попытке] → принято: ошибка в безопасную сторону; обратный порядок (снять резерв до коммита) открыл бы окно для лишнего запуска.
- [Редеплой во время саммаризации по кнопке — уведомление уже переписано в «⏳», заголовка и ссылки в нём нет] → принято вместе с потерей фоновых задач до `persist-pending-summaries`; запрос можно повторить через `/summary <id>`, а при готовом саммари оно выдаётся из БД.
- [Статус (бывшее уведомление) не удалился — например, сообщение слишком старое для удаления] → ошибка в лог, результат всё равно приходит новым сообщением; в чате остаётся «⏳ …». Принято: редкий случай, отдельной обработки нет.
- [Последняя доставка при сбое удаляет статус, то есть бывшее уведомление, и шлёт простой текст с `/summary <id>`, без заголовка] → принято: это путь непредвиденного сбоя, id достаточно для повторного запроса.
- [Последняя доставка при сбое тоже не проходит (`Forbidden`, сеть)] → только лог; пользователь, заблокировавший бота, ответа и не ждёт.

## Migration Plan

Без миграций БД и переменных окружения. Ветка `change/async-summary-delivery-bot` → `release/stage-10-prod` → `main` вместе с остальными P0. Откат — revert мёржа; данные не затрагиваются. Старые уведомления с кнопкой `force_sum:summary:` продолжают работать (новое поведение: уведомление превращается в статус и заменяется результатом — новым сообщением).
