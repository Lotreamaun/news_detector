## Context

Мотивация — в proposal.md. Требования — в `specs/bot-activity-stats/spec.md` и дельте `specs/weekly-digest-moderation/spec.md`.

Текущее состояние, которое определяет подход:
- В БД есть только состояние: `users` (`created_at`, `is_active`, `channel_verified`), `user_filters`, `summarization_usage` (счётчик по месяцам), `articles`, `weekly_digest_runs`. Действия пользователей видны только в логах.
- `is_active = False` ставится только по ошибке 403 при рассылке (`scheduler._send_notification`), без даты. `run_polling(allowed_updates=Update.ALL_TYPES)` уже получает `my_chat_member`, но обработчика для него нет.
- Команды и кнопки регистрируются в `app/main.py`, кроме мастера `/settings` (`level_wizard_handler` в `app/bot/handlers.py`, там же `/cancel`). PTB по умолчанию обрабатывает апдейты последовательно, поэтому медленная запись в обработчике задерживает следующий апдейт.
- `GET /app`, `/full_text` и `/today_list` анонимны. Подписанная `initData` есть только у POST-запросов (`/summarize`, `/summary_status`, `/usage`), её проверяет `_verify_init_data`.
- Админ-панель (`app/webapp/admin.py`, `static/admin.html`) подключается целиком только при `moderation_unavailable_reason(config) is None`, то есть при заданном `WEEKLY_DIGEST_TIME`.
- SQLite в WAL, `busy_timeout` 10 с. Даты хранятся в UTC и возвращаются без `tzinfo` (`scheduler._as_utc`). Аудитория — меньше 100 пользователей, проверка pravo.gov.ru — раз в 15 минут.

## Goals / Non-Goals

**Goals:**
- Одна плоская таблица событий и одна функция записи, которую можно вызвать из любого места одной строкой.
- Запись никогда не задерживает и не ломает пользовательский путь.
- Статистика считается SQL-запросами по запросу, без предрасчёта.

**Non-Goals:**
- Аналитическая платформа, когорты, воронки с произвольными шагами, экспорт.
- Изменение `is_active` по `my_chat_member` (это фикс issue #23, отдельный change).
- Учёт апдейтов, которые не являются командами или кнопками (свободный текст, служебные апдейты).

## Decisions

### 1. Одна таблица `events`, пользователь по `telegram_id`

```
events
  id           INTEGER PK autoincrement
  at           DateTime(timezone=True), NOT NULL, index   — UTC
  kind         String(32), NOT NULL                       — вид события, константы в events.py
  telegram_id  BigInteger, NULL                            — NULL у системных событий
  ref          String(128), NULL                           — уточнение
  INDEX (kind, at)
```

- **`telegram_id`, а не FK на `users.id`.** `ADMIN_CHAT_IDS` — это Telegram ID, поэтому исключение администраторов становится простым `NOT IN` без JOIN. Трекер активности срабатывает до `/start`, когда строки в `users` ещё нет, а `telegram_id` известен из апдейта сразу. Для ленты делается `LEFT JOIN users ON users.telegram_id = events.telegram_id`, чтобы получить `username`.
- **Виды событий** (строковые константы в `app/services/events.py`): `user.registered`, `user.verified`, `user.blocked`, `user.unblocked`, `cmd`, `button`, `settings.changed`, `webapp.open`, `summary.requested`, `summary.result`, `summary.limit`, `notify.sent`, `notify.failed`, `check.ok`, `check.failed`, `act.processed`, `weekly.sent`.
- **`ref` у `act.processed`** — строка `"<источник>/<исход>"`, например `ocr/ok` или `none/none`. Одна строка на акт, без второго события.
- Альтернативы: таблица на каждый тип событий (много миграций и запросов ради одинаковой формы) или колонки `last_seen_at`/`blocked_at` в `users` (нет истории, нет трендов). Обе отклонены.
- Создаётся `create_all`, существующие таблицы не меняются. Поэтому ручной `ALTER` в `database.py` не нужен.

### 2. Запись — «выстрелил и забыл»

`record_event(session_maker, kind, telegram_id=None, ref=None) -> None` — синхронная функция. Она создаёт фоновую задачу (`asyncio.create_task`; ссылки хранятся в модульном `set`, чтобы задачу не собрал GC), которая открывает короткую сессию, делает `INSERT` и `commit`. Любое исключение внутри задачи → `logger.warning` без `exc_info` с секретами. Вызывающий код ничего не ждёт.

- Почему не `await`: при занятой БД `busy_timeout` до 10 с задержал бы команду пользователя, а PTB обрабатывает апдейты последовательно. Так нарушилось бы требование «не задерживает».
- Почему нет буфера в памяти со сбросом раз в N секунд: дополнительная логика и потеря буфера при перезапуске. При сотнях–тысячах событий в сутки отдельный `INSERT` в WAL занимает миллисекунды.
- Цена: события из незавершённых задач при остановке процесса теряются. Для статистики это приемлемо.
- `at` выставляется в момент вызова `record_event` (`datetime.now(timezone.utc)`), а не при вставке. Время блокировки берётся из `my_chat_member.date`.

### 3. Где снимаются события

| Событие | Точка |
|---|---|
| `cmd`, `button` | `TypeHandler(Update, track_activity)` в группе `-1` в `app/main.py`. `cmd` — сообщение, начинающееся с `/`, ref = команда без `@bot` и аргументов, если она есть в константе `BOT_COMMANDS` рядом с трекером (`start`, `today`, `summary`, `settings`, `cancel`, `help`, `admin`, `test_digest`), иначе `other`. Так в журнал не попадает произвольный текст пользователя; при добавлении команды константу нужно дополнить. `button` — `callback_query`, ref = первые два сегмента `callback_data` по `:` (`force_sum:summary`, `onboarding:example`) без идентификаторов. Остальные апдейты игнорируются. Группа `-1` не мешает обычным обработчикам: PTB выполняет все группы, и трекер не бросает `ApplicationHandlerStop`. Действие считается, даже если его потом отклонит гейт канала: пользователь всё равно проявил активность. |
| `user.blocked` / `user.unblocked` | `ChatMemberHandler(..., MY_CHAT_MEMBER)`, только приватные чаты. Новый статус `kicked` → blocked; переход из `kicked` в `member` → unblocked. `is_active` здесь не трогается (#23). |
| `user.registered` | `start`, ветка `is_new`. |
| `user.verified` | `check_subscription`, когда `channel_verified` впервые становится `True`. |
| `settings.changed` | сохранение фильтров в мастере `/settings`. |
| `summary.requested` / `summary.result` / `summary.limit` | `force_summarize`: `requested` при входе. Затем по итогу для **каждого** вызывающего, включая присоединившихся: `limit` при статусе `limit`, иначе `result` с ref = статус. Так это работает одинаково для бота, Mini-App и панели. |
| `notify.sent` / `notify.failed` | `_send_notification`: новый параметр `kind` (`law` / `digest` / `weekly`) передают вызывающие. `failed` ref = `blocked` (ветка 403) или `error`. |
| `check.ok` / `check.failed` | `check_legislation_updates`: `failed` в ветке `RssError`, иначе `ok` с ref = число новых записей. Прогон бэкфилла не пишется. |
| `act.processed` | `_process_entry` после сохранения: источник текста `page` / `ocr` / `none`, исход саммари `ok` / `refused` / `error` / `none`. Бэкфилл не пишет, чтобы не исказить «акты за сутки». |
| `weekly.sent` | `_send_weekly_digest` после `_weekly_run_finish`, ref = число актов. |
| `webapp.open` | `POST /seen` (см. п. 4). |

### 4. Открытие Mini-App: `POST /seen`

Тело — `{init_data, view}`, где `view ∈ {law, digest, today}`. Сервер проверяет подпись через `_verify_init_data` и при успехе вызывает `record_event("webapp.open", telegram_id, view)`. Любой исход → `204` без тела: что запрос не прошёл проверку, наружу не сообщается. Пользователь не ищется в `users` и не проверяется гейтом: событие — факт открытия, а не доступ к данным.

Страница вызывает его один раз после загрузки, только если `tg.initData` не пуст. `view` берётся из параметров URL: `external_id` → `law`, `ids` → `digest`, `view=today` → `today`. Используется `fetch(..., {keepalive: true})`, ошибка игнорируется.

Альтернатива — встроить запись в `POST /usage`. Его вызывают не на всех видах страниц, и одна ручка выполняла бы две несвязанные задачи. Отклонено.

### 5. Расчёт статистики — `app/services/stats.py`

Две чистые асинхронные функции `pulse(session_maker, config, now) -> dict` и `trend(session_maker, config, now) -> dict` (всегда 12 недель, включая текущую) без HTTP. Все подсчёты — агрегирующие SQL-запросы (`COUNT`, `COUNT(DISTINCT telegram_id)`, `GROUP BY`), без выгрузки строк в Python, кроме ленты (50 строк).

- **Часовой пояс:** границы «сегодня», «7 дней» и недель (понедельник 00:00) считаются по Москве в Python (`app/services/today.py` уже знает московский «сегодня») и передаются в SQL как UTC-моменты.
- **Недельные корзины:** номер недели = `CAST((julianday(at) - julianday(:origin)) / 7 AS INTEGER)`, где `origin` — понедельник 00:00 по Москве самой ранней показываемой недели в UTC. Один запрос на ряд, без цикла по неделям. То же выражение применяется к `users.created_at` и `articles.created_at`.
- **Исключение администраторов:** `telegram_id NOT IN (:admin_ids)` для событий и `users.telegram_id NOT IN (...)` для аудитории. Пустой список — без условия. Метрики конвейера (`check.*`, `act.processed`, `weekly.sent`) не фильтруются: у них нет пользователя.
- **Заблокировавшие и подписчики.** `is_active` по-прежнему ставится только рассылкой и не снимается (#23), поэтому одного его мало: блокировка без последующей рассылки и разблокировка ему не видны. Признак «заблокирован» = последнее по `at` событие `user.blocked`/`user.unblocked` этого `telegram_id` — `user.blocked`; если таких событий нет — `is_active = False`. Это один подзапрос в `stats.py`. Подписчик = `channel_verified AND is_active AND NOT заблокирован` — ровно те, кому уходят уведомления. Разблокировавший с `is_active = False` не попадает ни в заблокировавших, ни в подписчиков, только во «всего зарегистрированных». Заблокировавшие за сегодня и 7 дней — по событиям `user.blocked`.
- **Активные пользователи:** `COUNT(DISTINCT telegram_id)` по видам `cmd`, `button`, `settings.changed`, `webapp.open`, `summary.requested`.
- **Успешные саммари:** все `summary.result` с `ref = ok`, включая ответ из БД и присоединение к идущей задаче — метрика означает «пользователь получил саммари». Нагрузку на модель отражает конвейер, поэтому `ref` эти случаи не различает.
- **Упёрлись в лимит за месяц:** `COUNT(DISTINCT telegram_id)` событий `summary.limit` с начала текущего месяца по Москве. `summarization_usage` для этого не годится: он хранит число попыток, а не отказы.
- **«Нет данных»:** `tracking_since = MIN(events.at)`. Недели, которые целиком раньше этой даты, в рядах из журнала получают `null`, а не `0`. Фронт рисует `null` штриховкой или «—».
- **Последняя проверка:** последнее событие `check.ok` / `check.failed`. Пометка «требует внимания», если оно старше `3 × CHECK_INTERVAL_MINUTES` или последнее — сбой.
- **Лента:** последние 50 событий без `check.ok`, `notify.sent` и `act.processed`. Это массовые события: одна рассылка на 80 человек или день с сотней актов вытеснили бы из ленты все действия людей, а их и так отражают строка последней проверки, плитки доставки и конвейера. `notify.failed` остаётся: это сигнал, что пользователь отвалился. Описание на русском формирует сервер: словарь вида события → шаблон («открыл Mini-App · дайджест», «⛔ заблокировал бота»), чтобы тексты жили в одном месте. Флаг `is_admin` у строки ставится по текущему `ADMIN_CHAT_IDS`.
- **Фильтры:** `GROUP BY level` по `user_filters` среди подписчиков (в смысле выше) без администраторов, плюс число подписчиков без строк (без ограничения).

Альтернатива — предрасчёт агрегатов джобой раз в 15 минут. Даёт отставание, требует второй таблицы и риска рассинхрона, а при таком объёме не нужен. Отклонено.

### 6. HTTP: `GET /admin/api/stats` и `GET /admin/api/meta`

- `GET /admin/api/stats?view=pulse` и `?view=trend` — `require_admin`, затем `_json(...)`. Неверные параметры → `400`. Исключение → `500` с понятным сообщением, как у `handle_state`.
- `GET /admin/api/meta` → `{"moderation": bool}`. Страница вызывает его первым, чтобы решить, показывать ли вкладку «Подборка» и какую вкладку открыть. Отдельная крошечная ручка проще, чем шаблонизировать статичный `admin.html` или угадывать по `404` от `/admin/api/state`.

### 7. Условия подключения панели

`setup_admin` делится на два уровня:
- **база панели** (`/admin`, `/admin/login`, `/admin/api/meta`, `/admin/api/stats`) — при заданных `WEBAPP_URL` и `ADMIN_CHAT_IDS`;
- **модерация** (`/admin/api/state`, `toggle`, `summary`, `export`) — дополнительно при `moderation_unavailable_reason(config) is None`.

Без модерации её ручки не регистрируются, поэтому на них приходит `404`, а это и есть «отклоняются» из спеки. Напоминание и лог причины в `main.py` не меняются. Команда `/admin` регистрируется всегда, но `_send_admin_link` сейчас сам проверяет `moderation_unavailable_reason` и без `WEEKLY_DIGEST_TIME` отвечает «Панель модерации недоступна». Эта проверка переносится на условие базы панели (`WEBAPP_URL` + `ADMIN_CHAT_IDS`), см. п. 10.

### 8. Фронт: вкладки, Пульс, Тренд, автообновление

- В `admin.html` сверху вкладки «Подборка | Статистика». Вкладка «Подборка» скрыта, если `meta.moderation = false`. Внутри «Статистики» — сегментный переключатель «Пульс | Тренд». Тренд всегда за 12 недель: длинный ряд при журнале, начатом с нуля, почти год был бы «нет данных». Последняя выбранная вкладка запоминается в `localStorage` (в `try/catch`).
- Пульс: сетка плиток (значение + подпись + «7 дн»), строка конвейера, блок фильтров, лента. Тренд: на каждый ряд строка с подписью, последним значением и мини-гистограммой из inline SVG; `null` — пунктирный контур. Без библиотек. Цвета берутся из токенов `webapp.css`, включая тёмную тему.
- Автообновление: `setInterval` 60 с. Обработчик выполняет запрос, только если `document.visibilityState === 'visible'`, открыта «Статистика» и выбран «Пульс». На `visibilitychange` → `visible` — немедленное обновление. Ответ заменяет содержимое блоков без пересоздания страницы, поэтому прокрутка сохраняется. Ошибка → прежние данные остаются, показывается метка «обновлено N мин назад».

### 9. Очистка журнала

Отдельная задача `purge_old_events` в `JobQueue`: раз в 24 часа, первый запуск через несколько минут после старта. Выполняет `DELETE FROM events WHERE at < now − 365 дней`. Тренду нужно около 12 недель, а год хранится на случай будущего длинного Тренда: при таком объёме это дёшево. Если когда-нибудь показывать 52 недели, учесть, что самая ранняя из них (с текущей неполной) начинается до 363 дней назад, — запас до 365 дней всего пара дней. Задача не привязана к backup-джобу, у которого свои условия регистрации и своя зона ответственности.

### 10. Ответ на `/admin`: сводка, ссылка и кнопка Mini-App

- **Общий построитель сводки.** Строки сводки подборки (когда уйдёт и три числа) выносятся из `build_review_ping` в одну функцию в `scheduler.py`. Её используют и напоминание, и `/admin`, чтобы формат не разошёлся. Текст напоминания не меняется: для него время по-прежнему подаётся как «сегодня в 18:00». Для `/admin` используется «в пт 18:00 (через …)» — та же подпись, что делает `_deadline_label` в панели. Данные берутся через `load_review_target` и `review_counts`, как у `/test_digest review`.
- **Прошедший момент отправки.** Если `seconds_left ≤ 0`, а подборка ещё не ушла (ждёт дневного окна или оценки), вместо времени выводится «отправка ожидается».
- **Порядок в сообщении:** пометка «🛠 Служебное сообщение для администратора» → сводка (если модерация доступна) → одноразовая ссылка с предупреждением «не пересылайте» → inline-кнопка `web_app` «📋 Открыть панель» на `{WEBAPP_URL}/admin`. Превью ссылки отключено, как сейчас: иначе Telegram откроет ссылку сам и сожжёт токен.
- **Только в личном чате.** Кнопка `web_app` добавляется, если `chat.type == "private"`: Telegram не принимает такие inline-кнопки в группах. В группе приходит сообщение без кнопки.
- **Колбэк «🔗 Ссылка для браузера»** из напоминания продолжает присылать только ссылку: сводка и кнопка уже есть в самом напоминании над ним. Поэтому `_send_admin_link` делится на «выдать ссылку» (общая часть) и сборку ответа `/admin`.
- Альтернатива — ссылка вторым сообщением по кнопке, как в напоминании. Токен не создаётся зря, но браузеру нужен лишний тап. Отклонено по выбору пользователя.

## Risks / Trade-offs

- [Формат дат в SQLite: `DateTime(timezone=True)` пишет строку, сравнения и `julianday` чувствительны к формату] → `at` всегда пишется одним способом (aware UTC через `record_event`), границы в запросах передаются как UTC-значения через параметры SQLAlchemy того же типа. При реализации проверить вручную на реальной БД, что `julianday(at)` не возвращает `NULL`.
- [Объём `notify.sent`: рассылка на N пользователей = N строк] → при меньше чем 100 пользователях это порядка тысячи строк в сутки, плюс индекс `(kind, at)` и ротация 365 дней. Если аудитория вырастет на порядки, можно перейти на одно событие на рассылку с числом в `ref`.
- [Потеря событий при остановке процесса (фоновые задачи)] → приемлемо для статистики, в спеке нет требования доставки «минимум раз».
- [Повторные открытия Mini-App (перезагрузка страницы, возврат из фона) завышают «открытия»] → считается каждое открытие. «Активные пользователи» считают уникальных и не искажаются.
- [`username` в `users` записывается только при регистрации и может устареть] → лента показывает сохранённый `@username`, а без него — Telegram ID. Обновление `username` вне объёма.
- [Москва без перехода на летнее время, но код берёт `ZoneInfo("Europe/Moscow")`, а не фиксированные +3] → корректно и при изменении правил.

- [Трекер в группе `-1` видит и апдейты, отклонённые гейтом канала] → это осознанное решение (п. 3): активность считается по намерению пользователя.
- [Расширение доступности панели меняет поведение при выключенной подборке] → затронут только сценарий без `WEEKLY_DIGEST_TIME`. На проде все три переменные заданы.
