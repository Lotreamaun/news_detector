## Context

См. proposal.md — Why. Факты, проверенные 05.10.2026 на реальном API `publication.pravo.gov.ru`:

- Пагинация: параметр `index=N` (страницы с `index=1` и `index=2` не пересекаются; `PageNumber`, `page`, `currentPage` игнорируются). Ответ содержит `itemsTotalCount`, `itemsPerPage`, `currentPage`, `pagesTotalCount`.
- `PeriodType=daily` (дефолт `PRAVO_API_URL`) отдаёт 30 документов на страницу, 222 документа за сутки, 8 страниц.
- Параметр `pageSize` принимает 100 и 200; значение 50 даёт HTTP 400, значение 1 тоже. Бэкфилл уже использует `pageSize=200`.
- Сейчас `fetch_documents()` делает один запрос и не смотрит на `pagesTotalCount`; `fetch_day()` (бэкфилл) тоже один запрос на день.

## Goals / Non-Goals

**Goals:**
- Приём всех страниц и в регулярной проверке, и в бэкфилле.
- Минимальное изменение: логика идемпотентности (`articles.external_id`) и классификации не трогается.

**Non-Goals:**
- Сужение набора типов (см. Decisions, п. 3).
- Изменение окна бэкфилла и условия `needs_backfill`.
- Параллельная загрузка страниц, кеш, вынос пагинации в отдельный модуль/класс.

## Decisions

1. **Пагинация внутри `fetch_documents`**, а не отдельной функцией-обёрткой: цикл по `index=1..pagesTotalCount`, результаты склеиваются в один список `FeedEntry`. Обе точки входа (`check_legislation_updates` и `fetch_day`) получают её автоматически, вызывающий код не меняется. Альтернатива — новая `fetch_documents_all` — отвергнута: два почти одинаковых метода и риск, что где-то забудут вызвать полный.
2. **Размер страницы 200 для регулярной проверки.** В `fetch_documents` базовый URL дополняется `pageSize=200` и `index=N` (существующие параметры `PeriodType=daily` сохраняются, чужой `pageSize` в `.env` перезаписывается). За сутки это 2 запроса вместо 8. Альтернатива — оставить 30 — отвергнута: лишние запросы без выгоды.
3. **Типы не сужаем.** Серверный фильтр `documentTypes=` сократил бы приём, но у пользователей есть фильтры `REGIONAL`/`DEPARTMENTAL`, а будущий `/today` показывает все законы дня. Выбор «кандидатов» (ФЗ/ФКЗ/указы/постановления) для LLM делается в коде по `level`, а не в запросе к API.
4. **Частичный сбой не роняет цикл.** Первая страница нужна всегда: её ошибка пробрасывается как сейчас (`FetchError`). Ошибка страницы N>1 после ретраев `_fetch_with_retries` логируется как предупреждение, цикл продолжается с тем, что получено. Это безопасно, потому что идемпотентность по `external_id` и суточное окно `daily` дают следующим циклам шанс подобрать пропущенное.
5. **Потолок страниц** — константа модуля (`_MAX_PAGES = 20`). При размере страницы 200 это 4000 документов за запрос, на порядок выше реального суточного объёма (~700). Превышение логируется, загрузка останавливается на потолке.
6. **Окно бэкфилла не меняем.** `/latest` и онбординг опираются на 30 дней ФЗ/ФКЗ из бэкфилла; их судьбу решит замена на `/today`, а не этот change.

## Risks / Trade-offs

- [Рост числа запросов к API] → 2 запроса вместо 1 за цикл при размере страницы 200; нагрузка пренебрежима.
- [Порядок документов на страницах может смещаться между запросами страниц (новые документы появляются во время загрузки), и документ может выпасть или продублироваться] → дубликаты отсекает идемпотентность по `external_id`, выпавшее подхватит следующий цикл.
- [Разовый «всплеск» при первом запуске после исправления: подберутся документы, которые раньше терялись] → при `is_first_run` рассылка уже подавляется; для уже работающей БД всплеск ограничен суточным окном API и пачками, которые бот и так должен был разослать.
- [`PRAVO_API_URL` в `.env` пользователя может содержать свой `pageSize`] → перезапись в коде; поведение описано здесь, формат `.env` не меняется.
