## Context

`_configure_logging()` (`app/main.py`) вешает консольный и файловый хендлеры на root и
ставит всем уровень `config.LOG_LEVEL`. PTB использует `httpx` как транспорт, `httpx`
пишет каждый запрос на INFO (`HTTP Request: POST <url> "<status>"`), а URL Bot API
содержит токен (`/bot<TOKEN>/<method>`). `httpcore` (транспорт под `httpx`) на DEBUG
пишет ещё более подробные трассы. Остальные внешние вызовы (pravo.gov.ru, GigaChat) идут
через `aiohttp` и токены в URL не передают — GigaChat-ключ живёт в заголовке, в логах
не встречается.

Второй источник найден при проверке на `LOG_LEVEL=DEBUG`: логгер `telegram.ext.ExtBot`
при `builder.build()` пишет `Set Bot API URL: https://api.telegram.org/bot<TOKEN>` и
`Set Bot API File URL: https://api.telegram.org/file/bot<TOKEN>`.

## Goals / Non-Goals

**Goals:**
- Минимальный, очевидно-корректный hotfix, который можно выкатить сегодня.
- Не зависеть от `LOG_LEVEL`: даже `DEBUG` не должен возвращать утечку.

**Non-Goals:**
- Универсальный редактор секретов для всех логов: маскируется только
  `TELEGRAM_BOT_TOKEN`. Ключ GigaChat передаётся в заголовке и в логи не попадает.
- Ротация токена и чистка уже записанных логов в Dockhost — токен тестового бота уходит из
  употребления при переезде на боевого бота.
- Тесты: в проекте нет тестового контура, проверка — ручная (см. tasks.md).

## Decisions

**1. Поднять `httpx` и `httpcore` до `WARNING` в `_configure_logging()`.**
Две строки `logging.getLogger(...).setLevel(logging.WARNING)` после настройки root.
Это стандартный приём, который рекомендует и сама PTB в своих примерах. Уровень
фиксированный, не из `.env` — KISS, и чтобы нельзя было случайно вернуть утечку
конфигом. Это подавление шума и первая линия защиты, но не единственная мера — см.
решение 2.

*Альтернатива — поднять `LOG_LEVEL` до WARNING глобально.* Отвергнуто: теряем полезные
INFO-логи самого приложения (обработка документов, рассылки).

**2. Маскирующий форматтер.**
Подкласс `logging.Formatter`, в `format()` —
`super().format(record).replace(token, "***")`; вешается на консольный и файловый
хендлеры вместо обычного форматтера.

- *Точная строка, а не регэксп:* значение токена известно из `Config`, поэтому нет
  ложных срабатываний и не нужен regex на каждую запись.
- *Formatter, а не Filter:* трейсбек (`exc_text`) и `stack_info` дописываются уже внутри
  `format()`, `Filter` их не видит; к тому же `Filter` пришлось бы менять `record`, общий
  для всех хендлеров.

*Альтернатива — поднять `telegram.ext.ExtBot` до INFO.* Отвергнуто: пропадает полезная
DEBUG-трасса вызовов Bot API, и это снова точечное решение под один источник.

*Альтернатива — `logging.Filter` с регэкспом `bot\d+:[\w-]+`.* Ранее была отложена «до
второго источника»; второй источник нашёлся, и вместо неё выбран форматтер с точной
строкой (причины выше).

**3. Ротация токена не входит в этот change.**
Прод сейчас работает на тестовом боте; при переезде на боевого бота меняется весь `.env`,
включая `TELEGRAM_BOT_TOKEN`. Поэтому отдельный `/revoke` сейчас не нужен, но код-фикс
обязан попасть в прод **до** переезда — иначе токен боевого бота утечёт так же.

## Risks / Trade-offs

- [Теряем INFO-трассу запросов к Telegram, которая помогала при отладке прокси
  `TELEGRAM_PROXY_URL`] → ошибки/таймауты по-прежнему логируются самим PTB и на
  WARNING+ `httpx`; при необходимости локальной отладки уровень можно временно поднять
  руками, не коммитя.
- [Токен в изменённом виде (например, URL-encoded, `:` → `%3A`) маскировкой не ловится]
  → принимаем: известные источники пишут токен как есть; смок-проверка `grep` по логу
  после деплоя (tasks.md) ловит регрессию.
- [Будущие библиотеки/логгеры могут снова вывести токен] → в исходном виде его закроет
  форматтер; прочее ловит та же смок-проверка.

## Migration Plan

1. Ветка `fix/mask-bot-token-in-logs` → коммит → PR → merge в `main` → автодеплой Dockhost.
2. Проверить прод-логи: строк `HTTP Request: … api.telegram.org/bot` больше нет.
3. Откат: revert коммита (фикс не трогает данные и схему БД).
