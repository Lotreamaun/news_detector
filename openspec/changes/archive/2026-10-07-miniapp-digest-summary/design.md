## Context

Мотивация — в `proposal.md`. Текущее состояние, которое определяет подход:

- `app/webapp/server.py` — aiohttp-сервер с одной HTML-страницей (`HTML_PAGE`, inline CSS+JS) и read-only `GET /full_text`. Режим `?ids=` строит аккордеон из `<details class="doc">`: `<summary>` — одна строка с эллипсисом, тело — полный заголовок, дата (`extractSigningDate`), текст (`renderResult`/`renderLawText`) и ссылка. Сервер не знает, кто открыл страницу, и получает только `session_maker`.
- Вся принудительная саммаризация живёт в `_summarize_and_reply` (`app/bot/handlers.py`): лечение псевдозаголовка → лимит (`SummarizationUsage`, `AUTO_LEVELS`, `ADMIN_CHAT_IDS`) → кеш саммари → `get_legal_text` / `ocr_document_text` → сохранение текста → `Summarizer` → сохранение/создание `Article` → `+1` к счётчику, с ветками `GigaChatError` и общего исключения. Логика и доставка в Telegram (`_deliver`, `_deliver_summary_failure`, `_summary_final`, `_summary_refused`) переплетены. Лимит проверяется **до** кеша — пользователь с исчерпанным лимитом не получает даже уже сохранённое саммари.
- `ocr_document_text` сам ловит `GigaChatError` и возвращает `None`, поэтому в ветку `except GigaChatError` попадает только ошибка саммаризатора — к этому моменту текст всегда получен и сохранён.
- Тизер дайджеста (`_build_digest` в `app/services/scheduler.py`) показывает до 3 документов; для пунктов без саммари добавляет кнопки «Сделать саммари №N» (`DIGEST_SUMMARIZE_PREFIX` → `force_summarize_digest`, результат отдельным сообщением), при >3 документах и заданном `WEBAPP_URL` — строку «Все документы — в полном списке по кнопке ниже».
- Кнопка «📖 Дайджест» — inline-кнопка `web_app`, поэтому Telegram передаёт странице подписанные `Telegram.WebApp.initData` с `user.id`.
- Гейт подписки на канал (`require_channel_verified`) обёрнут вокруг bot-хендлеров и в WebApp не действует. Флаг `channel_verified` только поднимается и не сбрасывается, а шедулер шлёт дайджесты только подтверждённым — так что в WebApp неподтверждённый пользователь практически не попадает.
- HTTPS перед WebApp-сервером даёт посредник, которым мы не управляем: локально ngrok, на проде — маршрутизация домена Dockhost. Его таймаут на долгие запросы из репозитория не настраивается.

## Goals / Non-Goals

**Goals:**
- Одна реализация правил принудительной саммаризации на обе точки входа (бот и WebApp), чтобы лимит/кеш/OCR не разъехались.
- Поведение и тексты сообщений бота о принудительной саммаризации остаются прежними — с одним намеренным исключением: уже сохранённое саммари отдаётся и при исчерпанном месячном лимите (кеш проверяется до лимита).
- Саммари документа из дайджеста делается в одном месте — в Mini-App: тизер в чате ведёт туда одной кнопкой и прямо об этом говорит.
- Карточка без саммари в свёрнутом виде — пиксель в пиксель как сейчас.

**Non-Goals:**
- Одиночный режим WebApp (`?external_id=`); состав и формат пунктов тизера дайджеста.
- Удаление обработчика `force_summarize_digest` — он нужен кнопкам «№N» в уже отправленных сообщениях.
- Фоновая очередь / поллинг статуса саммаризации — запрос синхронный.
- «Живое» обновление страницы (таймер, WebSocket/SSE) — актуальность проверяется только при разворачивании карточки и после сетевой ошибки.
- Настройка таймаутов прокси/туннеля перед WebApp.
- Общий рефакторинг `HTML_PAGE` (вынос в отдельные файлы, сборка фронтенда).
- Автотесты (их в проекте нет); проверка ручная.

## Decisions

### 1. Вынести ядро саммаризации в `app/services/force_summary.py`

Функция `force_summarize(config, session_maker, user, external_id) -> ForceSummaryResult`, где результат — простой dataclass без готовых текстов: `status` (`"ok" | "limit" | "no_text" | "refused" | "error"`), `title`, `url`, `title_known`, `summary`, `text`. Внутри — текущая последовательность из `_summarize_and_reply` без единого вызова Telegram, с одним изменением порядка: **кеш саммари проверяется до лимита** (лечение псевдозаголовка → кеш → лимит → текст/OCR → …). `AUTO_LEVELS` переезжает туда же (handlers импортирует его обратно, если он нужен где-то ещё).

Правила заполнения:
- `text` — заполнен всегда, когда текст был получен (в т.ч. при `refused` и при `error` из ветки `GigaChatError`), иначе `None`;
- `refused` — `GigaChatError` с отказом/пустым ответом модели; `error` — прочие `GigaChatError` (текст есть) и непредвиденное исключение (текст может быть, а может не быть);
- `title_known` — результат `_has_real_title` для итоговой записи; заменяет передачу `cached_article` наружу.

Тексты сообщений формирует каждая точка входа. `_summarize_and_reply` становится адаптером: вызвать сервис → по `status` выбрать `_deliver`/`_deliver_summary_failure`/`_summary_refused`/`_summary_final`, а текущие строки (`Месячный лимит … исчерпан`, `Не удалось получить текст закона … /summary <id>`, `Языковая модель отказалась … «Полный текст»`, `Не удалось сделать саммари…`) переезжают в `handlers.py` без изменений. Чтобы бот не изменился: `error` с непустым `text` (сбой GigaChat после получения текста) доставляется как сейчас ветка `GigaChatError` — через `_summary_refused` с кнопкой «Полный текст»; `error` без текста — через `_deliver_summary_failure`.

*Альтернативы:* (а) вызывать `_summarize_and_reply` из WebApp с фейковым `context` — хрупко и тащит Telegram в веб-слой; (б) скопировать логику в `server.py` — два места для лимита и кеша, которые гарантированно разойдутся; (в) отдавать из сервиса готовый бот-текст `fallback` — в карточке WebApp были бы чужие отсылки к `/summary` и кнопке «Полный текст». Выделение одной функции со статусом — минимальная абстракция, которая это предотвращает, и ложится в правило слоёв (бизнес-логика — в `app/services/`).

### 2. Идентификация через `initData`, проверка на сервере

Страница шлёт `POST /summarize` с JSON `{"external_id": ..., "init_data": Telegram.WebApp.initData}`. Сервер проверяет подпись по официальной схеме Telegram: `secret = HMAC_SHA256(key="WebAppData", msg=bot_token)`, `data_check_string` — отсортированные `key=value` всех полей, кроме `hash`, через `\n`; `hmac.compare_digest(hex(HMAC_SHA256(secret, dcs)), hash)`. Плюс проверка свежести `auth_date` (момент открытия Mini-App; не старше 24 ч — страница может долго висеть открытой). Из поля `user` (JSON) берётся `id`. Хелпер — небольшая функция `_verify_init_data(init_data, bot_token) -> int | None` в `server.py`.

Пользователь ищется по `users.telegram_id`. Не найден → 403. Если задан `REQUIRED_CHANNEL_ID` и `channel_verified` ложен → 403 (страховка по принципу default-deny, как `require_channel_verified` в боте; кнопки проверки подписки в WebApp нет — только текст). Создавать пользователя из WebApp не будем: в дайджест попадают только зарегистрированные подписчики.

*Альтернативы:* передавать `user_id` в URL кнопки — подделывается тривиально и позволяет тратить чужой лимит и GigaChat; `tg.sendData` — работает только для reply-keyboard WebApp, не для inline-кнопки.

### 3. Контракт эндпоинтов и тексты WebApp

- `GET /full_text` — добавляется поле `"summary": str | null`. Остальное без изменений.
- `POST /summarize` — 200 для всех «доменных» исходов: `{"status", "summary", "text", "is_text_available", "message"}`, где `message` — короткая причина для показа в карточке (для `ok` — `null`). 400 — нет `external_id`/невалидный JSON; 401 — нет/неверная/устаревшая `initData`; 403 — пользователь неизвестен или не подтвердил подписку (`{"message"}`); 500 — непредвиденная ошибка вне сервиса. Ответы с CORS-заголовком, как у `/full_text`.

Тексты WebApp. Серверные (`message`, формирует `server.py` по `status`; `N` — `FORCE_SUMMARIZE_MONTHLY_LIMIT`):

| исход | `message` |
|---|---|
| `limit` | Месячный лимит саммаризаций (N) исчерпан. Попробуйте в следующем месяце. |
| `no_text` | Не удалось получить текст закона. Попробуйте позже. |
| `refused` | Языковая модель отказалась сформировать саммари для этого документа. |
| `error` | Не удалось сделать саммари. Попробуйте позже. |
| 403, нет пользователя | Откройте бота и нажмите /start. |
| 403, нет подписки | Подтвердите подписку на канал в боте. |

Клиентские (в JS, без запроса или без ответа сервера):

| исход | текст |
|---|---|
| загрузка | подпись кнопки «Саммари в процессе создания…» (многоточие анимировано) |
| нет `initData` | Саммари можно сделать, открыв дайджест из Telegram. |
| 401 | Сессия устарела — закройте и снова откройте дайджест. |
| сеть / 5xx, перепроверка не нашла саммари | Не удалось дождаться ответа — возможно, саммари ещё создаётся. Попробуйте через минуту. |

`config` передаётся в `create_app`/`start_webapp` (`app["config"]`), т.к. серверу теперь нужны токен бота, GigaChat-настройки, лимит, `ADMIN_CHAT_IDS`, `REQUIRED_CHANNEL_ID`.

### 4. Вёрстка карточки

```
<details class="doc">
  <summary>
    <span class="doc-head-title">Заголовок (одна строка, …)</span>   ← ▸/▾ через ::before
    <div class="sum sum-preview">…</div>                             ← только если есть саммари
  </summary>
  <div class="doc-body">
    doc-title · date · [ .sum | .sum-action ] · text · link
  </div>
</details>
```

- Эллипсис переезжает с `<summary>` на `.doc-head-title` — без саммари визуально ничего не меняется.
- `.sum` — акцентная плашка в цвете кнопки темы. Цвета вынесены в переменные `:root`: `--sum-accent` (`--tg-theme-button-color`), `--sum-bg` (заливка: `color-mix(in srgb, var(--sum-accent) 14%, transparent)`, запасной `rgba(38, 136, 212, 0.12)` через `@supports` для webview без `color-mix`) и `--sum-border` (около 45% того же цвета). Плашка: рамка 1px `--sum-border`, радиус 8px, шрифт 14px; сверху метка «Саммари» (11–12px, uppercase, цвет `--sum-accent`). Левой полосы нет. Так плашка читается и в тёмной теме, где `secondary-bg-color` почти совпадает с фоном, и родственна плашкам страницы («Текст распознан с помощью ИИ…», «Текст недоступен»). Те же переменные использует кнопка в `loading` (решение 5).
- `.doc[open] .sum-preview { display: none; }` — в развёрнутом виде саммари одно, после даты: порядок «заголовок → дата → саммари → текст».
- `.sum-action` — контейнер кнопки «Сделать саммари» (`--tg-theme-button-color` / `--tg-theme-button-text-color`, компактная, не во всю ширину) и строки `.sum-status` под ней — только для сообщений об ошибках и подсказок (в состоянии загрузки не используется).
- Карточка, которую не удалось загрузить (`/full_text` → 404/ошибка/сеть), остаётся как сейчас — сообщение об ошибке без кнопки «Сделать саммари».

### 5. Поведение карточки на фронтенде

Функция `renderCard(details, data)` пересобирает заголовок и тело из одного объекта `{title, url, text, is_text_available, summary}` — используется при первичной загрузке, после ответа `/summarize` и после перезапросов `/full_text` (ответ сливается в объект данных; непустые `summary`/`text` из ответа заменяют прежние при **любом** статусе — так распознанный текст появляется и при `refused`/`error`).

Кнопка «Сделать саммари». Состояния `.sum-action`: idle → loading → по исходу. В `loading` кнопка `disabled` и `aria-busy="true"` и выглядит нажатой: она принимает вид плашки готового саммари — тот же фон `--sum-bg`, тонкая рамка `--sum-border` (через `box-shadow: inset`, чтобы размер кнопки не менялся), текст в `--sum-accent` — так плашка «вырастает» из нажатой кнопки. Перед подписью «Саммари в процессе создания…» вращается спиннер (CSS-рамка с `border-right-color: transparent`); его размер чётный (14px), а у кнопки целая высота строки (`line-height: 20px`) и `will-change: transform` — иначе центр вращения попадает на дробный пиксель и спиннер «гуляет». Блика и точек нет; при `prefers-reduced-motion` спиннер статичен. Песочные часы не используем: эмодзи ⏳ не вращается без отдельной анимации. Исходы:
- `ok` → `renderCard` с саммари и текстом, кнопки нет;
- `limit` / `refused` → `renderCard` (с текстом, если пришёл), на месте кнопки — `message`, кнопка не возвращается;
- `no_text` / `error` → `renderCard` (с текстом, если пришёл), `message` и снова активная кнопка;
- сетевая ошибка / 5xx → сначала один перезапрос `/full_text` этой карточки: если саммари появилось (запрос дошёл до сервера и завершился, но ответ оборвал посредник) — `renderCard` с ним; иначе — клиентский текст «Не удалось дождаться ответа…» и активная кнопка;
- пустой `initData` (проверяется ещё до запроса) или 401 → клиентский текст, запрос не повторяется; 403 → `message` из ответа.

Перепроверка при разворачивании. На событие `toggle` (только при открытии) карточки без саммари страница делает один перезапрос `/full_text` и, если саммари появилось, перерисовывает карточку через `renderCard` — вместо кнопки пользователь сразу видит готовое саммари. Перезапрос не делается, если в карточке идёт саммаризация (состояние loading), чтобы не затереть индикатор, и для карточек, которые не загрузились.

Клик по кнопке внутри `<details>` не сворачивает секцию (кнопка в теле, не в `<summary>`).

### 6. Тизер дайджеста: одна кнопка и подсказка

Саммари документа из дайджеста теперь делается в Mini-App, поэтому `_build_digest` перестаёт генерировать кнопки «Сделать саммари №N» — в клавиатуре тизера остаётся только «📖 Дайджест». Строка «Все документы — в полном списке по кнопке ниже» (была только при >3 документах) заменяется одной подсказкой, которая выводится всегда при заданном `WEBAPP_URL`:

> Саммари и полные тексты — в дайджесте по кнопке ниже. Там же можно сделать саммари для любого закона

Без `WEBAPP_URL` нет ни кнопки, ни подсказки (ссылаться не на что); второй ветки с кнопками «№N» для этого случая не делаем — на проде `WEBAPP_URL` задан, а `/summary <id>` остаётся.

`force_summarize_digest`, `DIGEST_SUMMARIZE_PREFIX` и регистрация `CallbackQueryHandler` в `app/main.py` остаются без изменений: у дайджестов, уже лежащих в чатах, кнопки «№N» есть, и без обработчика их нажатие повисло бы. Докстринги `_build_digest`/`force_summarize_digest` обновляются, чтобы было видно, что новые тизеры кнопку не содержат.

*Альтернатива:* удалить обработчик вместе с префиксом — несколько строк экономии ценой сломанных кнопок в старых сообщениях.

## Risks / Trade-offs

- [OCR + саммари могут идти десятки секунд, webview могут закрыть посреди запроса] → aiohttp 3.13 не отменяет обработчик при обрыве соединения: сервер доводит работу до конца, текст и саммари сохраняются в БД, лимит списывается; при следующем открытии карточка покажет саммари. Индикатор загрузки честно говорит, что это долго.
- [Посредник перед WebApp (ngrok локально, маршрутизация Dockhost на проде) может оборвать долгий запрос по своему таймауту, который мы не настраиваем] → результат всё равно сохраняется на сервере; фронт при сетевой ошибке/5xx сначала перепроверяет `/full_text` и показывает саммари, если оно уже готово, а иначе просит повторить через минуту. Реальное поведение проверяется вручную на OCR-документе (задача 4.3).
- [Повторное нажатие, пока первый запрос ещё идёт на сервере (после обрыва посредником), или два устройства по одному документу] → кнопка блокируется на клиенте, после обрыва текст просит подождать; оставшаяся гонка допускается так же, как в боте сейчас (максимум лишний вызов GigaChat и лишнее списание), отдельной блокировки не вводим.
- [Регрессия в боте из-за выноса логики] → выносим без изменения ветвлений (кроме порядка кеш/лимит), тексты бота переезжают в `handlers.py` дословно; затем вручную прогоняем `/summary` и кнопки «Сделать саммари» (успех, лимит, кеш, кеш при исчерпанном лимите) — тексты сообщений должны совпасть с текущими.
- [Утечка/подделка `initData`] → проверка HMAC токеном бота + окно свежести 24 ч; `initData` не логируется (только `user.id`), токен — только из `Config`.
- [`/summarize` открывает GigaChat внешнему миру] → без валидной подписи запрос отклоняется до любой работы; лимит тот же, что в боте.

- [Без `WEBAPP_URL` (локальный запуск без HTTPS) из тизера больше нельзя сделать саммари кнопкой] → допускается: остаётся `/summary <id>`; на проде `WEBAPP_URL` задан.
- [Старые дайджесты с кнопками «№N»] → обработчик сохраняется, кнопки работают по прежним правилам (результат — новым сообщением в чат).

## Migration Plan

Миграций БД нет. Деплой обычным перезапуском бота; фронтенд обновится сам (страница отдаётся сервером). Настройки прокси/туннеля не меняются. Откат — откат коммита; старая страница просто не читает поле `summary`.
