## Context

Мотивация — см. proposal.md («Why»), требования — `specs/gigachat-request-queue/spec.md`.

Текущее устройство, которое определяет подход:

- `GigaChatClient` (`app/services/gigachat.py`) создаётся во многих местах и живёт недолго: `_llm_tools` планировщика (саммаризатор + клиент для оценки и OCR на цикл), `Summarizer` внутри себя, `_summarize_document` в `force_summary.py` (отдельный клиент OCR + свой `Summarizer`), `scripts/calibrate_importance.py`. Общего клиента на процесс нет, у каждого — свой токен и своя `aiohttp`-сессия.
- Все запросы к API идут через `_request_json` (ретраи 3 попытки, пауза `2**attempt`: 1 с, 2 с) → `_request_json_once`. Через тот же `_request_json` идёт и OAuth (`_request_access_token`).
- Таймаут — `aiohttp.ClientTimeout(total=60)` на сессии, т.е. на один HTTP-запрос.
- Пользовательский путь к GigaChat ровно один — `_summarize_document` в `force_summary.py` (из него идут бот, Mini-App и панель модерации, задачи там уже дедуплицированы по `external_id`). Всё остальное — фон планировщика через `_llm_tools`.
- Один event loop на процесс: PTB `run_polling` и aiohttp Mini-App работают в нём же.

## Goals / Non-Goals

**Goals:**
- Очередь — на процесс, а не на экземпляр клиента: клиентов много, поток у ключа один.
- Минимальные правки вне `gigachat.py`: вызывающие (`importance.py`, `rss_parser.py`, планировщик, скрипты) не меняются.
- Приоритет задаётся тем, кто создаёт клиента, явно, а не выводится из контекста.

**Non-Goals:**
- Не координируем несколько процессов (локальный бот, скрипты) — это операционное правило.
- Не меняем политику ретраев и таймаутов (это `gigachat-timeout-no-retry`) и обработку срока токена (`fix-gigachat-token-expiry`).
- Не показываем пользователю позицию в очереди и не меняем доставку — это changes 3 и 4; здесь только функция, отдающая число.
- Не прерываем и не вытесняем выполняющиеся запросы.
- Пользователь не присоединяется к уже идущей фоновой саммаризации документа (P2, `join-background-summary`).

## Decisions

### D1. Модульная очередь с двумя деками ожидающих, а не `asyncio.Lock` / `PriorityQueue`

Состояние в модуле `gigachat.py`: флаг «поток занят» и две `collections.deque` с `asyncio.Future` ожидающих — `user` и `background`. Захват — асинхронный контекст-менеджер `_stream_slot(priority)`:

- поток свободен и никто не ждёт → занять сразу, без `await`;
- иначе положить свой `Future` в деку своего приоритета и ждать его;
- освобождение (`_release`): снять первый неотменённый `Future` из `user`, если пусто — из `background`, и выставить ему результат (поток передаётся «из рук в руки», флаг остаётся «занят»); ожидающих нет — снять флаг.

Почему так: `asyncio.Lock` не умеет приоритеты; `asyncio.PriorityQueue` — это очередь элементов для воркера, а не захват ресурса, и потребовала бы фоновый воркер-таск с передачей корутин и результатов. Две деки + `Future` — ~40 строк без новых зависимостей, FIFO внутри класса получается бесплатно.

Альтернатива — `asyncio.Semaphore(1)` + «пользователь ждёт, фон проверяет, нет ли ждущих пользователей» — гонки между проверкой и захватом, отвергнута.

### D2. Отмена ожидающего

`await fut` отменён:
- `fut` ещё не получил результат → убрать его из деки, пробросить `CancelledError`;
- `fut` уже получил результат (поток передан ему, но задача отменена до возобновления) → немедленно `_release()` дальше, пробросить `CancelledError`.

Отмена во время выполнения запроса обрабатывается `finally` контекст-менеджера — тот же `_release()`. Это закрывает требование «Отмена ожидания не блокирует очередь». На практике отменять может aiohttp-хендлер при обрыве соединения, но `force_summarize` ждёт задачу через `asyncio.shield`, так что сама саммаризация отменяется редко (остановка процесса).

### D3. Граница слота — весь `_request_json` с ретраями, OAuth снаружи

Новый приватный метод клиента `_api_request(method, url, *, headers, data, json, expect_json)`: `async with _stream_slot(self._config.priority)` → `token = await self.get_access_token()` → добавить `Authorization: Bearer` → `await self._request_json(...)`. Через него идут `complete`, `upload_file`, `delete_file`, `get_models`; `_request_access_token` по-прежнему вызывает `_request_json` напрямую — OAuth вне очереди.

- Слот держится на всех попытках и паузах между ними: если 429 пришёл от постороннего процесса с тем же ключом, отдать поток своему следующему запросу — значит гарантированно получить ещё один 429. Альтернатива «слот на каждую попытку» отвергнута по этой причине и потому, что меняла бы порядок обслуживания посреди ретраев.
- Токен берётся **внутри** слота: запрос может ждать очереди минутами, и токен, полученный до ожидания, мог бы протухнуть к моменту отправки (особенно после фикса `fix-gigachat-token-expiry`). Цена — OAuth-запрос (≈0,5 с, раз в ~30 мин на клиента) выполняется при занятом слоте; приемлемо.
- Ожидание в очереди происходит до `session.request`, поэтому `ClientTimeout(total=60)` его не включает — требование «таймаут с момента отправки» выполняется без изменений таймаутов.

### D4. Приоритет — поле конфигурации клиента, по умолчанию фоновый

`Priority = Literal["user", "background"]`; `GigaChatConfig.priority: Priority = "background"`, `SummarizerConfig.priority: Priority = "background"` (передаётся в `GigaChatConfig` внутри `Summarizer`). В `_summarize_document` (`force_summary.py`) клиент OCR и саммаризатор создаются с `priority="user"`.

Почему по умолчанию фон: забытое поле в новом месте не даст «пролезть» без очереди, а всё существующее, кроме `force_summary.py`, и так фон — планировщик, `importance.py`, `rss_parser.py` и скрипты не трогаем.

Альтернатива — `contextvars.ContextVar` с приоритетом, выставляемая в `force_summarize` (задача копирует контекст): меньше правок, но неявно — приоритет «приезжает» неизвестно откуда, и легко потерять его при создании задачи вне контекста. Альтернатива — аргумент `priority` у каждого `complete`/`upload_file`/`delete_file` — пришлось бы протягивать через `ocr_document_text`, `Summarizer.summarize`, `score_importance`. Обе отвергнуты: поле конфигурации явно и правится в одном месте.

### D5. «Сколько впереди» — одна публичная функция

`calls_ahead_of_user() -> int` = `1` если поток занят, иначе `0`, плюс `len(` деки `user` `)` (без отменённых `Future`). Только чтение. Число — в вызовах API, а не документах (OCR = до трёх вызовов): точнее для оценки времени не нужно, changes 3/4 сами решают, как перевести его в «~N мин». Отдельную структуру статуса (`busy`, длины обеих дек) не вводим, пока её никто не потребляет.

### D6. Лог ожидания

Если запрос не получил слот сразу — после получения `logger.info("GigaChat: %s-запрос ждал очереди %.1f с (впереди было %d)", ...)`. Без ожидания — ничего, чтобы не засорять лог циклом планировщика, который и так работает последовательно.

## Risks / Trade-offs

- [До changes 3/4 ожидание очереди держит хендлер бота (PTB обрабатывает апдейты последовательно) и `POST /summarize` Mini-App] → change выезжает в `main` только вместе с асинхронной доставкой (интеграционная ветка `release/stage-10-prod`); по отдельности не деплоить.
- [Голодание фона: при непрерывном потоке пользовательских запросов цикл планировщика стоит, уведомления о новых актах задерживаются; следующий запуск джобы APScheduler пропускается, пока предыдущий не завершился] → принято решением «пользователи вне очереди, без потолка». Пользовательские запросы конечны (месячный лимит, дедуп по документу, кеш саммари в БД), пик — часы. Если в логах будут видны долгие ожидания фона (лог D6), — отдельный change с квотой «1 фоновый на N пользовательских».
- [Пользователь ждёт выполняющийся фоновый OCR: до 60 с × 3 попытки (+ до ~180 с на попытку после `gigachat-timeout-no-retry`)] → выполняющийся запрос не прерываем (спека); после change 5 ретрая по таймауту не будет, худший случай — одна попытка.
- [Посторонний процесс с тем же ключом (локальный бот, скрипты) по-прежнему даёт 429] → операционное правило «не запускать с прод-ключом»; ретраи внутри слота смягчают.
- [Состояние очереди модульное и привязано к event loop] → в процессе один loop; скрипты запускаются отдельными процессами. При `asyncio.run` дважды в одном процессе очередь к моменту выхода пуста (все слоты освобождены в `finally`).
- [Последовательные шаги OCR (upload → complete → delete) могут перемежаться чужими запросами] → допустимо: файл в хранилище не зависит от потока; пользовательский запрос между шагами фонового OCR — это и есть приоритет.

## Migration Plan

Без миграций БД и `.env`. Деплой — в составе `release/stage-10-prod` → `main` вместе с changes 3 и 4. Откат — revert коммита: внешние интерфейсы (`complete`, `upload_file`, `delete_file`, `Summarizer`) не меняются, новое поле конфигурации имеет значение по умолчанию.
