## Why

У GigaChat для физлица один поток: второй одновременный запрос получает HTTP 429. Бот же обращается к GigaChat из нескольких мест независимо — цикл планировщика (саммари, OCR, оценка важности, добор оценок, пятничная «попытка 2»), команды бота (`/summary`, кнопки «Сделать саммари») и Mini-App (`POST /summarize`, aiohttp обрабатывает запросы реально параллельно). Ретраи клиента (1 с + 2 с) сгорают за ~3 с, пока поток занят генерацией на 5–60 с, — в логах 08.10 уже 57 × `HTTP 429` при одном пользователе. Перед анонсом (ожидается 150–200 новых пользователей за несколько часов) наши же запросы будут массово выбивать друг друга, причём пользовательский запрос проигрывает фоновому так же часто, как наоборот.

## What Changes

- Все запросы процесса к API GigaChat (генерация, загрузка и удаление файлов, список моделей) выполняются строго по одному через общую очередь; одновременных запросов к API из одного процесса больше не бывает. Получение OAuth-токена в очередь не входит (другой сервис, поток не занимает).
- Запросы, сделанные ради пользователя (принудительная саммаризация из бота, Mini-App и панели модерации, включая OCR), обслуживаются раньше ожидающих фоновых (всё, что делает планировщик). Внутри каждого класса — в порядке поступления. Уже выполняющийся фоновый запрос не прерывается.
- Потолка ожидания в очереди нет: запрос ждёт столько, сколько нужно; таймаут HTTP-запроса отсчитывается только с момента, когда запрос реально отправлен.
- Повторы запроса после временной ошибки (429, 5xx, сеть) идут, не отдавая поток другим запросам.
- Очередь сообщает, сколько вызовов будет обслужено раньше нового пользовательского запроса, — для оценки времени ожидания в следующих changes (асинхронная доставка саммари в боте и Mini-App). В этом change значение никому не показывается.
- Ожидание в очереди и его длительность пишутся в лог.

## Capabilities

### New Capabilities
- `gigachat-request-queue`: последовательное обращение к единственному потоку GigaChat — один запрос к API за раз на процесс, приоритет пользовательских запросов над фоновыми, повторы без потери очереди, отмена ожидания без блокировки очереди, число вызовов впереди пользовательского запроса.

## Impact

- Код: `app/services/gigachat.py` — модульная очередь с двумя приоритетами вокруг запросов к API (не OAuth), поле приоритета в `GigaChatConfig`, публичная функция «сколько вызовов впереди пользовательского». `app/services/summarizer.py` — поле приоритета в `SummarizerConfig`, передаётся клиенту. `app/services/force_summary.py` — клиент OCR и саммаризатор создаются с пользовательским приоритетом. Планировщик (`app/services/scheduler.py`), `importance.py`, `rss_parser.py`, `scripts/` не меняются: значение по умолчанию — фоновый приоритет.
- Состояние: только в памяти процесса; без изменений БД, `.env` и конфигурации.
- Поведение для пользователя: меньше отказов «модель недоступна» из-за 429; при занятом потоке ответ может прийти позже (ожидание очереди + генерация). До асинхронной доставки (changes 3, 4 этапа 10) это ожидание держит хендлер бота и запрос Mini-App — поэтому этот change выезжает в `main` только вместе с ними.
- Не покрывается: другие процессы с тем же ключом (локальный бот, `scripts/calibrate_importance.py`, `scripts/seed_weekly_window.py`) по-прежнему конкурируют с продом за поток — это операционное правило «не запускать с прод-ключом», а не код. Повтор `chat/completions` после таймаута (гарантированный 429) — отдельный change `gigachat-timeout-no-retry`.
