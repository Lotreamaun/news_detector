## Context

Мотивация — в `proposal.md`. Текущее состояние, которое определяет подход:

- `app/webapp/server.py` — aiohttp-сервер с одной HTML-страницей (`HTML_PAGE`, inline CSS+JS) и read-only `GET /full_text`. Режим `?ids=` строит аккордеон из `<details class="doc">`: `<summary>` — одна строка с эллипсисом, тело — полный заголовок, дата (`extractSigningDate`), текст (`renderResult`/`renderLawText`) и ссылка. Сервер не знает, кто открыл страницу, и получает только `session_maker`.
- Вся принудительная саммаризация живёт в `_summarize_and_reply` (`app/bot/handlers.py`): кеш саммари → лечение псевдозаголовка → лимит (`SummarizationUsage`, `AUTO_LEVELS`, `ADMIN_CHAT_IDS`) → `get_legal_text` / `ocr_document_text` → сохранение текста → `Summarizer` → сохранение/создание `Article` → `+1` к счётчику, с ветками `GigaChatError` и общего исключения. Логика и доставка в Telegram (`_deliver`, `_deliver_summary_failure`, `_summary_final`, `_summary_refused`) переплетены.
- Кнопка «📖 Дайджест» — inline-кнопка `web_app`, поэтому Telegram передаёт странице подписанные `Telegram.WebApp.initData` с `user.id`.
- Гейт подписки на канал (`require_channel_verified`) обёрнут вокруг bot-хендлеров и в WebApp не действует.

## Goals / Non-Goals

**Goals:**
- Одна реализация правил принудительной саммаризации на обе точки входа (бот и WebApp), чтобы лимит/кеш/OCR не разъехались.
- Поведение и тексты сообщений бота остаются прежними.
- Карточка без саммари в свёрнутом виде — пиксель в пиксель как сейчас.

**Non-Goals:**
- Одиночный режим WebApp (`?external_id=`), тизер дайджеста в чате, кнопки «Сделать саммари №N».
- Фоновая очередь / поллинг статуса саммаризации — запрос синхронный.
- Общий рефакторинг `HTML_PAGE` (вынос в отдельные файлы, сборка фронтенда).
- Автотесты (их в проекте нет); проверка ручная.

## Decisions

### 1. Вынести ядро саммаризации в `app/services/force_summary.py`

Функция `force_summarize(config, session_maker, user, external_id) -> ForceSummaryResult`, где результат — простой dataclass: `status` (`"ok" | "limit" | "no_text" | "refused" | "error"`), `title`, `url`, `title_known`, `summary`, `text`, `cached_article`, `fallback` (готовый текст причины, тот же, что сейчас уходит в чат). Внутри — дословно текущая последовательность из `_summarize_and_reply` без единого вызова Telegram. `AUTO_LEVELS` переезжает туда же (handlers импортирует его обратно, если он нужен где-то ещё).

`_summarize_and_reply` становится адаптером: вызвать сервис → по `status` выбрать `_deliver`/`_deliver_summary_failure`/`_summary_refused` с тем же текстом и разметкой, что сейчас.

*Альтернативы:* (а) вызывать `_summarize_and_reply` из WebApp с фейковым `context` — хрупко и тащит Telegram в веб-слой; (б) скопировать логику в `server.py` — два места для лимита и кеша, которые гарантированно разойдутся. Выделение одной функции — минимальная абстракция, которая это предотвращает, и ложится в правило слоёв (бизнес-логика — в `app/services/`).

### 2. Идентификация через `initData`, проверка на сервере

Страница шлёт `POST /summarize` с JSON `{"external_id": ..., "init_data": Telegram.WebApp.initData}`. Сервер проверяет подпись по официальной схеме Telegram: `secret = HMAC_SHA256(key="WebAppData", msg=bot_token)`, `data_check_string` — отсортированные `key=value` всех полей, кроме `hash`, через `\n`; `hmac.compare_digest(hex(HMAC_SHA256(secret, dcs)), hash)`. Плюс проверка свежести `auth_date` (не старше 24 ч — дайджест могут открыть не сразу). Из поля `user` (JSON) берётся `id`. Хелпер — небольшая функция `_verify_init_data(init_data, bot_token) -> int | None` в `server.py`.

Пользователь ищется по `users.telegram_id`. Не найден → 403 «Откройте бота и нажмите /start». Если задан `REQUIRED_CHANNEL_ID` и `channel_verified` ложен → 403 с той же формулировкой про подписку, что и в боте. Создавать пользователя из WebApp не будем: в дайджест попадают только зарегистрированные подписчики.

*Альтернативы:* передавать `user_id` в URL кнопки — подделывается тривиально и позволяет тратить чужой лимит и GigaChat; `tg.sendData` — работает только для reply-keyboard WebApp, не для inline-кнопки.

### 3. Контракт эндпоинтов

- `GET /full_text` — добавляется поле `"summary": str | null`. Остальное без изменений.
- `POST /summarize` — 200 для всех «доменных» исходов: `{"status", "summary", "text", "is_text_available", "message"}`, где `message` — короткая причина для показа в карточке (для `ok` — `null`). 400 — нет `external_id`/невалидный JSON; 401 — нет/неверная/устаревшая `initData`; 403 — пользователь неизвестен или не подтвердил подписку; 500 — непредвиденная ошибка вне сервиса. Ответы с CORS-заголовком, как у `/full_text`.

`config` передаётся в `create_app`/`start_webapp` (`app["config"]`), т.к. серверу теперь нужны токен бота, GigaChat-настройки, лимит, `ADMIN_CHAT_IDS`, `REQUIRED_CHANNEL_ID`.

### 4. Вёрстка карточки

```
<details class="doc">
  <summary>
    <span class="doc-head-title">Заголовок (одна строка, …)</span>   ← ▸/▾ через ::before
    <div class="sum sum-preview">…</div>                             ← только если есть саммари
  </summary>
  <div class="doc-body">
    doc-title · date · [ .sum | .sum-action ] · text · link
  </div>
</details>
```

- Эллипсис переезжает с `<summary>` на `.doc-head-title` — без саммари визуально ничего не меняется.
- `.sum` — нейтральный блок: фон `var(--tg-theme-secondary-bg-color, #f4f4f5)`, тонкая левая полоса `var(--tg-theme-hint-color)`, радиус 6px, шрифт 14px; сверху метка «Саммари» (11–12px, uppercase, hint-цвет). В свёрнутом состоянии превью ограничено ~3 строками (`-webkit-line-clamp`), в развёрнутом показывается полностью.
- `.doc[open] .sum-preview { display: none; }` — в развёрнутом виде саммари одно, после даты.
- `.sum-action` — контейнер кнопки «Сделать саммари» (`--tg-theme-button-color` / `--tg-theme-button-text-color`, компактная, не во всю ширину) и строки статуса/ошибки под ней.

### 5. Поведение кнопки на фронтенде

Функция `renderCard(details, data)` пересобирает заголовок и тело из одного объекта `{title, url, text, is_text_available, summary}` — используется и при первичной загрузке, и после ответа `/summarize` (слияние ответа в объект данных). Состояния `.sum-action`: idle → loading (кнопка `disabled`, «⏳ Саммари в процессе создания…») → по `status`:
- `ok` → `renderCard` с саммари и текстом;
- `refused` → `renderCard` с текстом, вместо кнопки — сообщение;
- `limit` → сообщение, кнопка убирается;
- `no_text` / `error` / сетевая ошибка / 5xx → сообщение, кнопка снова активна;
- 401 или пустой `initData` (проверяется ещё до запроса) → «Саммари доступно, если открыть дайджест из Telegram»; 403 → `message` из ответа.

Клик по кнопке внутри `<details>` не сворачивает секцию (кнопка в теле, не в `<summary>`).

## Risks / Trade-offs

- [OCR + саммари могут идти десятки секунд, webview могут закрыть посреди запроса] → сервер доводит работу до конца: текст и саммари сохраняются в БД, лимит списывается; при следующем открытии карточка покажет саммари. Индикатор загрузки честно говорит, что это долго.
- [Два одновременных нажатия (два устройства) по одному документу] → кнопка блокируется на клиенте; гонка между устройствами допускается так же, как в боте сейчас (максимум лишний вызов GigaChat), отдельной блокировки не вводим.
- [Регрессия в боте из-за выноса логики] → выносим «как есть» без изменения ветвлений, затем вручную прогоняем `/summary` и кнопки «Сделать саммари» (успех, лимит, кеш) — тексты сообщений должны совпасть с текущими.
- [Утечка/подделка `initData`] → проверка HMAC токеном бота + окно свежести 24 ч; `initData` не логируется (только `user.id`), токен — только из `Config`.
- [`/summarize` открывает GigaChat внешнему миру] → без валидной подписи запрос отклоняется до любой работы; лимит тот же, что в боте.

## Migration Plan

Миграций БД нет. Деплой обычным перезапуском бота; фронтенд обновится сам (страница отдаётся сервером). Откат — откат коммита; старая страница просто не читает поле `summary`.
