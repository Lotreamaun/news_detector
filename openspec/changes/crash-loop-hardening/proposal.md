## Why

19.10 бот больше часа (17:59–19:08) падал сразу после старта, а потом не работал до 10:56 следующего дня. Причина — 340-ФЗ «Об исполнении федерального бюджета за 2025 год»: «важный» акт без готового текста уходит на OCR, а `_download_pdf` сначала читает PDF целиком в память и только потом сравнивает его с лимитом 40 МБ. PDF этого закона весит 163 МБ (3293 страницы), процесс исчезает без единой строки ошибки (судя по всему, его убивает лимит памяти контейнера). Документ сохраняется в БД только после обработки, поэтому после каждого перезапуска он снова «новый» — цикл падений. Тот же путь открыт и для пользователя: «Сделать саммари» под актом без текста запускает OCR через тот же `_download_pdf`, а 19.10 на портале был и региональный акт с PDF на 559 МБ.

В том же окне один запуск упал по другой причине: Telegram не ответил при старте, а `run_polling` по умолчанию (`bootstrap_retries=0`) не повторяет попытку и завершает процесс. Сбои внутри обработчиков апдейтов (таймауты Telegram и т. п.) сейчас уходят в лог PTB как `No error handlers are registered` с полным трейсбеком — шумно и трудно отличить сеть от бага.

## What Changes

- PDF для OCR больше не читается в память сверх лимита (40 МБ): если сервер заранее сообщает размер больше лимита, файл не скачивается; если размер не сообщён, загрузка обрывается, как только превысит лимит. OCR для такого документа не выполняется, повторных попыток скачать его нет. Это касается всех точек входа OCR: обработки нового акта, добора оценок и фоновой саммаризации, принудительной саммаризации (бот, Mini-App, панель модерации).
- Акт со слишком большим PDF обрабатывается как акт без текста: сохраняется, рассылается со ссылкой, оценивается по названию по существующим правилам. Пользователь принудительной саммаризации получает существующее сообщение о том, что текст получить не удалось.
- При старте бот ждёт, пока Telegram станет доступен (бесконечные повторы с паузами), а не завершает процесс после первого таймаута. Неверный токен по-прежнему останавливает запуск.
- В приложении регистрируется обработчик ошибок PTB: сетевой сбой Telegram при обработке апдейта пишется одной строкой WARNING без трейсбека, `Message is not modified` — одной строкой INFO, всё остальное — ERROR с трейсбеком, как сейчас.

Вне рамок change:
- отдельный текст для пользователя «документ слишком большой для распознавания» (сейчас — общее сообщение о недоступном тексте);
- догрузка документов предыдущего дня после простоя через полночь и разовая догрузка самого 340-ФЗ (отдельный change / разовая операция);
- общая защита от цикла падений на любом «ядовитом» документе (сохранять акт до OCR и т. п.);
- повторные нажатия «Сделать саммари» и уведомления старше 48 часов (отдельный change);
- политика перезапусков Dockhost: почему после 19:08 контейнер больше не поднимался, не выяснено.

### Modified Capabilities
- `legislation-ingestion`: новое требование — ограничение размера PDF, скачиваемого для распознавания, во всех точках входа OCR; поведение для акта со слишком большим PDF.
- `deployment`: новое требование — запуск при временно недоступном Telegram не завершает процесс.
- `secret-safe-logging`: новое требование — сбои обработчиков апдейтов логируются компактно по виду сбоя (сеть / «не изменено» / прочее), маскирование токена сохраняется.

## Impact

- `app/services/rss_parser.py`: `_fetch_once` / `_fetch_with_retries` получают ограничение размера бинарного ответа (проверка `Content-Length` и чтение кусками с обрывом), новый `TooLargeError(RssError)` без повторов; `_download_pdf` ловит его и возвращает `None`.
- `app/main.py`: `run_polling(..., bootstrap_retries=-1)`; `application.add_error_handler(...)` в `_build_application`.
- `app/bot/handlers.py`: функция обработчика ошибок PTB (только логирование).
- `CLAUDE.md`: строки про OCR (лимит PDF) и старт/обработчик ошибок.
- Схема БД, `.env`, зависимости, тексты пользователю не меняются.
