## Context

Бот сейчас запускается только `python -m app.main` на машине разработчика. `app/main.py`
поднимает один PTB `Application` (`run_polling`, блокирующий) и внутри его же `post_init`
стартует aiohttp WebApp (`app/webapp/server.py`) в том же процессе/event loop — то есть это
уже архитектурно один процесс, не два независимых сервиса. `app/core/config.py` уже читает
все нужные для прода переменные (`TELEGRAM_PROXY_URL`, `WEBAPP_HOST`, `WEBAPP_PORT`,
`WEBAPP_URL`, `LOG_FILE`, ...) — деплой не требует правок кода, только упаковку и прод-конфиг.
Мотивация — см. `proposal.md`; требования к поведению — см. `specs/deployment/spec.md`.

## Goals / Non-Goals

**Goals:**
- Контейнеризовать существующий процесс без изменения его логики.
- Дать воспроизводимую, задокументированную последовательность ручного деплоя на Dockhost.
- Сохранить WebApp доступным по HTTPS через бесплатный динамический домен Dockhost.

**Non-Goals:**
- CI/CD (деплой ручной, по решению пользователя).
- Миграция данных из текущей локальной `news_detector.db` (чистый старт).
- Внешний мониторинг/алертинг аптайма (только `restart: unless-stopped`).
- Управление секретами через что-либо, кроме `.env`-файла руками на сервере.
- Исправление существующего `GIGACHAT_VERIFY_SSL=false` TODO (отдельная, не связанная задача).

## Decisions

**Платформа: Dockhost, а не голый VPS + nginx/certbot.**
Пользователь уже деплоил на Dockhost раньше (есть опыт и аккаунт), платформа сама выдаёт
TLS-сертификат и домен на контейнер — это закрывает HTTPS-требование Telegram WebApp без
отдельной настройки reverse-proxy. Голый VPS дал бы больше контроля, но потребовал бы ручной
nginx+certbot конфигурации — не оправдано для пет-проекта (KISS). Соответствует изначальному
выбору в `docs/vision.md`.

**Один сервис в compose (`bot`), не два.**
WebApp и бот уже живут в одном процессе/event loop (`app/main.py::_post_init` стартует
`start_webapp` внутри того же `Application`). Разносить их на два контейнера означало бы
рефакторинг связи "webapp читает `session_maker` из `bot_data`" в межконтейнерное
взаимодействие — не нужно и не входит в объём этого change.

**Сеть: `WEBAPP_HOST=0.0.0.0`, `WEBAPP_PORT=8080`, `EXPOSE 8080` в Dockerfile.**
Динамический домен Dockhost маршрутизирует трафик на TCP-порт сетевого сервиса контейнера
(internal route), а не на loopback — дефолтный для локальной разработки `WEBAPP_HOST=127.0.0.1`
не будет доступен извне. Порт 8080 оставлен как есть (Dockhost поддерживает маршрутизацию на
произвольный объявленный порт, не только 80/443 — см. Open Questions про то, как именно он
объявляется в панели).

**Персистентность: bind-mount volumes `./data` и `./logs`, не именованные Docker-volume.**
Проще для ручного бэкапа/инспекции одним `cp`/`scp`, что соответствует принятому ручному
(без CI, без снапшот-автоматизации) процессу эксплуатации.

**Restart policy: `restart: unless-stopped`, без внешнего health-check сервиса.**
Покрывает крэши процесса; не покрывает «завис, но жив» сценарии. Осознанный компромисс по
запросу пользователя — см. Risks ниже.

**Чистый старт БД.**
Прод стартует с пустого volume; `init_db_schema()` создаёт таблицы сам. Текущая локальная
`news_detector.db` не переносится — решение пользователя, не техническое ограничение.

## Risks / Trade-offs

- [Риск] Точный механизм объявления порта для internal-route в Dockhost (нужен ли только
  `EXPOSE` в Dockerfile, или ещё что-то в панели/конфиге) подтверждён с ваших слов из
  документации Dockhost, но не проверен эмпирически → **Митигация**: проверяется на первом
  реальном деплое (задача в tasks.md); `WEBAPP_PORT` остаётся переменной окружения, так что
  порт можно сменить без правки кода, если понадобится.
- [Риск] `restart: unless-stopped` не ловит «процесс жив, но перестал полезно работать»
  (зависший network-запрос, тихие сбои внешних API) → **Митигация**: осознанно принято для v1
  (KISS, пет-проект); дешёвый heartbeat-пинг (healthchecks.io/UptimeRobot) можно добавить
  позже отдельной небольшой задачей, не меняя эту архитектуру.
- [Риск] Ручной деплой (`git pull` + `docker compose up -d --build` по SSH) человекозависим,
  нет CI-проверки перед выкладкой → **Митигация**: точная последовательность команд
  зафиксирована в README, смоук-тест — последний шаг перед тем, как считать деплой успешным.
- [Риск] Прод стартует без данных текущей локальной БД → **Митигация**: явно подтверждено
  пользователем как приемлемое; проверить ещё раз перед первым реальным деплоем, пока не
  поздно передумать.

## Migration Plan

Разворачивание (ручное, по SSH/панели Dockhost):
1. Создать проект/контейнер на Dockhost из этого репозитория (Dockerfile).
2. Создать `.env` на сервере вручную: `TELEGRAM_BOT_TOKEN`, `GIGACHAT_AUTH_KEY` (с `Basic `),
   `GIGACHAT_SCOPE`, `DATABASE_URL=sqlite+aiosqlite:///./data/news_detector.db`,
   `GIGACHAT_VERIFY_SSL=false`, `TELEGRAM_PROXY_URL=<рабочий RU-прокси до api.telegram.org>`,
   `WEBAPP_HOST=0.0.0.0`, `WEBAPP_PORT=8080`, `WEBAPP_URL=<динамический домен Dockhost>`.
3. Настроить internal route в панели Dockhost: домен → сетевой сервис контейнера, порт 8080.
4. `mkdir -p data logs` (или эквивалент на смонтированных volume).
5. `docker compose up -d --build`.
6. Смоук-тест: `/start`, `/latest`, `/summary` + кнопка «Полный текст» (WebApp открывается по
   HTTPS), проверить, что бот реально получает апдейты через прокси (RU-сегмент блокирует
   `api.telegram.org` напрямую), `is_first_run` не спамит старыми законами.

Откат: `docker compose down`, поправить `.env`/образ, `docker compose up -d --build` заново —
без сложностей отката данных, т.к. БД чистая и это первый прод-запуск.

## Open Questions

- Точный UI/конфиг-механизм объявления порта контейнера для internal-route в Dockhost
  (только `EXPOSE`, или нужен отдельный шаг в панели) — не меняет спеку и не меняет разбивку
  задач (проверка/донастройка — уже отдельная задача в tasks.md), поэтому можно оставить
  выяснить эмпирически на первом деплое, а не сейчас.
