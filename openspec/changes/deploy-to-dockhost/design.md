## Context

Бот сейчас запускается только `python -m app.main` на машине разработчика. `app/main.py`
поднимает один PTB `Application` (`run_polling`, блокирующий) и внутри его же `post_init`
стартует aiohttp WebApp (`app/webapp/server.py`) в том же процессе/event loop — то есть это
уже архитектурно один процесс, не два независимых сервиса. `app/core/config.py` уже читает
все нужные для прода переменные (`TELEGRAM_PROXY_URL`, `WEBAPP_HOST`, `WEBAPP_PORT`,
`WEBAPP_URL`, `LOG_FILE`, ...) — деплой не требует правок кода, только упаковку и прод-конфиг.
Мотивация — см. `proposal.md`; требования к поведению — см. `specs/deployment/spec.md`.

## Goals / Non-Goals

**Goals:**
- Контейнеризовать существующий процесс без изменения его логики.
- Задокументировать настройку прод-окружения на Dockhost (сам деплой — автоматический, по
  `git push` в `main`, без ручных команд на сервере).
- Сохранить WebApp доступным по HTTPS через бесплатный динамический домен Dockhost.

**Non-Goals:**
- Полноценный CI-гейт перед деплоем (автодеплой Dockhost по push в `main` и так работает без
  него — ошибка в `main` уезжает в прод немедленно, см. Risks).
- Миграция данных из текущей локальной `news_detector.db` (чистый старт).
- Внешний мониторинг/алертинг аптайма (только платформенный авто-restart Dockhost, см. Open
  Questions).
- Управление секретами через что-либо, кроме переменных окружения, заданных вручную в форме
  «Переменные окружения» панели Dockhost (SSH/VPS-доступа нет).
- Исправление существующего `GIGACHAT_VERIFY_SSL=false` TODO (отдельная, не связанная задача).

## Decisions

**Платформа: Dockhost, а не голый VPS + nginx/certbot.**
Пользователь уже деплоил на Dockhost раньше (есть опыт и аккаунт), платформа сама выдаёт
TLS-сертификат и домен на контейнер — это закрывает HTTPS-требование Telegram WebApp без
отдельной настройки reverse-proxy. Голый VPS дал бы больше контроля, но потребовал бы ручной
nginx+certbot конфигурации — не оправдано для пет-проекта (KISS). Соответствует изначальному
выбору в `docs/vision.md`.

**Один контейнер (`bot`), не два.**
WebApp и бот уже живут в одном процессе/event loop (`app/main.py::_post_init` стартует
`start_webapp` внутри того же `Application`). Разносить их на два контейнера означало бы
рефакторинг связи "webapp читает `session_maker` из `bot_data`" в межконтейнерное
взаимодействие — не нужно и не входит в объём этого change.

**Сеть: `WEBAPP_HOST=0.0.0.0`, `WEBAPP_PORT=8080`, `EXPOSE 8080` в Dockerfile.**
Динамический домен Dockhost маршрутизирует трафик на TCP-порт сетевого сервиса контейнера
(internal route), а не на loopback — дефолтный для локальной разработки `WEBAPP_HOST=127.0.0.1`
не будет доступен извне. Порт 8080 оставлен как есть (Dockhost поддерживает маршрутизацию на
произвольный объявленный порт, не только 80/443 — см. Open Questions про то, как именно он
объявляется в панели).

**Персистентность: сетевой диск Dockhost (SSD), подключаемый к контейнеру напрямую через
панель — не bind-mount через `docker-compose.yml`.**
Панель Dockhost собирает контейнер из Git прямо по `Dockerfile` и не использует
`docker-compose.yml` вообще — bind-mount volumes из compose-файла в проде никогда бы не
применялись (это подтвердилось на практике: ребилд обнулял БД). Реальный механизм —
нативный ресурс «Сетевые диски» (отказоустойчивое сетевое блочное хранилище, HDD/SSD),
создаваемый в разделе «Сетевые диски» проекта и подключаемый к контейнеру с явным путём
монтирования через модалку редактирования контейнера (режим ReadWriteOnce/ReadWriteMany
выбирается платформой автоматически по числу подключённых контейнеров, вручную не
задаётся). Путь монтирования — `/app/data`, что совпадает с `DATABASE_URL` и
`DB_BACKUP_DIR`, уже указывающими на `./data/...` относительно `WORKDIR /app` — код менять
не нужно. `docker-compose.yml` в репозитории остаётся полезен только для локальной
разработки (см. задачи 2.1–2.2) — прод его не видит вообще.

**Restart policy: платформенное поведение Dockhost, не `restart: unless-stopped` из
compose.**
`docker-compose.yml` в проде не читается, поэтому директива `restart: unless-stopped` там
ни на что не влияет. Предполагается, что Dockhost перезапускает упавший контейнер
автоматически (типичное поведение управляемых контейнерных платформ), но это не
подтверждено документацией — см. Open Questions.

**Чистый старт БД.**
Прод стартует с пустого сетевого диска; `init_db_schema()` создаёт таблицы сам. Текущая
локальная `news_detector.db` не переносится — решение пользователя, не техническое
ограничение.

## Risks / Trade-offs

- [Риск] Точный механизм объявления порта для internal-route в Dockhost (нужен ли только
  `EXPOSE` в Dockerfile, или ещё что-то в панели/конфиге) подтверждён с ваших слов из
  документации Dockhost, но не проверен эмпирически → **Митигация**: проверяется на первом
  реальном деплое (задача в tasks.md); `WEBAPP_PORT` остаётся переменной окружения, так что
  порт можно сменить без правки кода, если понадобится.
- [Риск] Неясно, что именно платформенный авто-restart Dockhost (если он есть) покрывает —
  вероятно, падения процесса, но не «завис, но жив» сценарии (зависший network-запрос, тихие
  сбои внешних API) → **Митигация**: осознанно принято для v1 (KISS, пет-проект); дешёвый
  heartbeat-пинг (healthchecks.io/UptimeRobot) можно добавить позже отдельной небольшой
  задачей, не меняя эту архитектуру.
- [Риск] Автодеплой по `git push` в `main` пересобирает и передеплоивает прод **без ручного
  подтверждения и без CI-гейта** — ошибка в `main` уезжает в прод немедленно, а не после
  осознанного шага «применить» → **Митигация**: осознанный компромисс для pet-проекта без
  CI; смоук-тест выполняется вручную после каждого пуша, пока нет автоматизированных тестов.
- [Риск] Прод стартует без данных текущей локальной БД → **Митигация**: явно подтверждено
  пользователем как приемлемое; проверить ещё раз перед первым реальным деплоем, пока не
  поздно передумать.

## Migration Plan

Разворачивание (через панель Dockhost, без SSH — доступа к серверу нет):
1. Создать проект/контейнер на Dockhost из этого репозитория (Git-интеграция, сборка по
   `Dockerfile`).
2. Задать прод-переменные через форму «Переменные окружения» в панели Dockhost (не файл
   `.env` на сервере): `TELEGRAM_BOT_TOKEN`, `GIGACHAT_AUTH_KEY` (с `Basic `),
   `GIGACHAT_SCOPE`, `DATABASE_URL=sqlite+aiosqlite:///./data/news_detector.db`,
   `GIGACHAT_VERIFY_SSL=false`, `TELEGRAM_PROXY_URL=<рабочий RU-прокси до api.telegram.org>`,
   `WEBAPP_HOST=0.0.0.0`, `WEBAPP_PORT=8080`, `WEBAPP_URL=<динамический домен Dockhost>`.
3. Настроить internal route в панели Dockhost: домен → сетевой сервис контейнера, порт 8080.
4. Создать сетевой диск (SSD) в разделе «Сетевые диски», подключить его к контейнеру с
   mountPath `/app/data`.
5. Задеплоить: `git push` в `main` — автодеплой Dockhost сам пересобирает образ и
   передеплоивает контейнер, ручных команд на сервере не требуется.
6. Смоук-тест: `/start`, `/latest`, `/summary` + кнопка «Полный текст» (WebApp открывается по
   HTTPS), проверить, что бот реально получает апдейты через прокси (RU-сегмент блокирует
   `api.telegram.org` напрямую), `is_first_run` не спамит старыми законами, и что данные на
   сетевом диске (пользователи, статьи, бэкапы) переживают повторный `git push` — не только
   restart, а именно пересборку образа.

Откат: поправить переменные/код и запушить исправление в `main` — автодеплой передеплоит
заново; без сложностей отката данных, т.к. БД чистая и это первый прод-запуск.

## Open Questions

- Переживает ли сетевой диск именно пересборку образа (`git push` → автодеплой), а не только
  restart того же контейнера — ожидается по архитектуре (диск отделён от контейнера,
  аналогично PersistentVolume), но не подтверждено документацией явно; проверяется
  эмпирически, см. задачу в tasks.md.
- Как Dockhost перезапускает упавший процесс без `docker-compose`'овского
  `restart: unless-stopped` (которого прод не видит) — не найдено отдельной страницы в
  документации; предположительно поведение платформы по умолчанию, не подтверждено.
- Точный UI/конфиг-механизм объявления порта контейнера для internal-route в Dockhost
  (только `EXPOSE`, или нужен отдельный шаг в панели) — не меняет спеку и не меняет разбивку
  задач (проверка/донастройка — уже отдельная задача в tasks.md), поэтому можно оставить
  выяснить эмпирически на первом деплое, а не сейчас.
