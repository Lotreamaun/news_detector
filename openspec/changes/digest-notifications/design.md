## Context

См. proposal.md — Why/What Changes для мотивации. Текущее состояние (`app/services/scheduler.py`):

- `check_legislation_updates` идёт по `new_entries` последовательно и для каждого вызывает `_process_entry`, которая в конце сама вызывает `_notify_users(context, session_maker, article)` — то есть обработка одного документа и его рассылка всем пользователям происходят внутри одной итерации, до перехода к следующему документу.
- `_notify_users` выбирает `is_active` пользователей одним запросом, затем в цикле по каждому пользователю проверяет соответствие фильтру (`UserFilter`) и шлёт `_build_notification(article, ...)` через `context.bot.send_message`, с `asyncio.sleep(0.05)` между пользователями и retry на 429/обработкой 403.
- Значит: рассылка сейчас организована "по документу" (один документ → все подходящие юзеры), а нужно "по пользователю за цикл" (один пользователь → все подходящие ему документы цикла, одним сообщением при 2+).

## Goals / Non-Goals

**Goals:**
- Перевести рассылку с "одно сообщение на документ" на "одно сообщение на пользователя за цикл" (при 2+ подходящих документах).
- Сохранить существующую защиту от 429/403 и паузу между отправками.
- Не трогать `/latest`, обработку OCR/саммаризации отдельного документа.

**Non-Goals:**
- Группировка через несколько циклов проверки (только в рамках одного вызова `check_legislation_updates`).
- Изменение самого содержания саммари (GigaChat-вызовы не меняются, они уже происходят на этапе обработки документа).

## Decisions

### Разделить обработку документов и рассылку на два прохода
`check_legislation_updates` меняется: сначала цикл по `new_entries` только обрабатывает и сохраняет каждый документ (текст/саммари/классификация/`_save_article`), собирая список успешно сохранённых `Article`. Рассылка (`_notify_users` → переименовать в `_notify_users_batch` или похожее) вызывается один раз, после того как все документы цикла обработаны, и принимает весь список статей цикла, а не одну.
**Альтернатива (отклонена):** копить статьи в буфере и слать дайджест только по таймеру/расписанию отдельно от цикла проверки — усложняет модель (два независимых расписания вместо одного), при этом реального выигрыша нет, т.к. и так нужно дождаться обработки всех документов цикла.

### Группировка — по пользователю, внутри одного прохода по списку пользователей
Новая `_notify_users_batch` один раз выбирает активных и (после `channel-subscription-gate`) подтверждённых пользователей, затем для каждого — фильтрует список статей цикла по его `UserFilter` (переиспользуя существующую логику сопоставления фильтра, которая сейчас инлайн в цикле `_notify_users`). Если подходящих статей 1 — вызывается существующий путь построения сообщения (`_build_notification`); если 2+ — вызывается новая функция построения дайджеста.
**Альтернатива (отклонена):** сначала сгруппировать статьи по уникальным комбинациям пользовательских фильтров и слать один и тот же текст всем с одинаковым фильтром — экономит немного CPU на форматировании, но фильтры пользователей — множества, а не enum, комбинаций может быть много; текущий масштаб (единицы-десятки пользователей) не оправдывает эту оптимизацию.

### Дайджест переиспользует форматирующие функции, но не запрос `/latest`
Новая функция дайджеста использует тот же паттерн, что `_format_summary`/`_full_text_block` в `app/bot/handlers.py` (жирный заголовок + summary + markdown-ссылка), но работает со списком `Article`, переданным вызывающей стороной — не делает собственный SQL-запрос (в отличие от `/latest`, у которого фиксированный `WHERE level IN (FKZ, FZ)` и своё окно в 30 дней, не связанные с текущим циклом проверки).
**Альтернатива (отклонена):** дословно переиспользовать `handlers.latest()` — не подходит, `/latest` завязан на собственный независимый запрос к БД, а не на список статей конкретного цикла.

### Лимит длины сообщения — обрезка по количеству, не по символам "жёстко"
Дайджест строится путём последовательного накопления отформатированных блоков; как только суммарная длина превышает порог (с запасом от 4096, например 3800 символов на текст), добавление новых блоков останавливается, добавляется строка `"...и ещё N законов, смотрите /latest"`.
**Альтернатива (отклонена):** заранее ограничить дайджест фиксированным числом документов (как `LIMIT 10` в `/latest`) — не подходит, т.к. длина блока зависит от длины саммари конкретной статьи, а не только от количества.

## Risks / Trade-offs

- [Риск] Пользователь с 1 подходящим документом теперь получает уведомление только после того, как обработаны **все** документы цикла (включая более медленные — OCR ФКЗ), а не сразу как раньше. **Митигация**: осознанный trade-off — при типичном размере цикла (1 документ) разница в задержке минимальна; выигрыш от отсутствия спама перевешивает.
- [Риск] Рефакторинг `_notify_users` → `_notify_users_batch` меняет сигнатуру и место вызова — затрагивает retry-логику на 429/403, которую важно не потерять при переносе. **Митигация**: retry/403-деактивация переносятся как есть, тестируются вручную (см. tasks.md).
- [Trade-off] Персональный (не глобальный) порог группировки — точнее соответствует исходной жалобе, но требует фильтрации списка статей цикла на каждого пользователя (не более десятков пользователей на данный момент — не проблема производительности).
