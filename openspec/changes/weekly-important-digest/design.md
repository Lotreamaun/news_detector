## Context

См. proposal.md — Why. Текущее состояние, на которое опирается дизайн:

- `Article` (`app/models/article.py`) не хранит время приёма: только `published_at`, а это **дата без времени** (из `publishDateShort`, полночь UTC). Окно «пятница 18:00 → пятница 18:00» по `published_at` задать нельзя.
- `_process_entry` (`scheduler.py`) для каждого нового документа пробует получить текст, суммаризует (если текст есть) и сохраняет; саммари у указов и постановлений бывает редко (текст готов не сразу).
- `_build_digest` — готовый тизер: заголовок «Приняли новые законы — N» и сортировка по уровню/алфавиту зашиты в функции; кнопка «Дайджест» ограничена `DIGEST_ID_CAP = 30`.
- Расписание — PTB `JobQueue`. В установленной PTB 22.6 `run_daily(days=...)` нумерует дни 0–6 как **воскресенье–суббота** (пятница = 5).
- Миграции колонок — ручные идемпотентные `_ensure_*_column` в `app/core/database.py`; новые таблицы создаёт `create_all`.
- Образ деплоя `python:3.14-slim`, в `requirements.txt` нет `tzdata`; `zoneinfo` на slim-образах может не найти `Europe/Moscow`.

## Goals / Non-Goals

**Goals:**
- Точность оценки важности (приоритет над объяснимостью): отдельный запрос, рубрика с долями уровней, few-shot, измеримая калибровка.
- Подборка без пропусков и дублей между неделями, одинаковая для всех.
- Безопасное включение: оценки и предпросмотр до первой реальной рассылки.

**Non-Goals:**
- `/latest` и `/today`, мгновенные уведомления, пользовательские фильтры, показ меток важности.
- Финальное ранжирование «топ-N из пачки»: подборка берёт все уровни `3` и `2`.
- Настройка дня недели (пятница зашита), персональные подборки, сферы/регионы.

## Decisions

1. **Колонки `importance` и `created_at` у `Article`.** `importance` — nullable `SmallInteger` (NULL = не оценён, 0–3 уровни); `created_at` — nullable `DateTime(timezone=True)`, заполняется в `_save_article` (время приёма, UTC). Старые строки получают NULL и в окна не попадают (безопасно: прошлое не рассылаем). Миграции — `_ensure_importance_column`, `_ensure_created_at_column` по образцу `_ensure_is_demo_column`. Альтернатива — окно по `published_at` с интервалом в сутки — отвергнута: теряет акты, пришедшие в пятницу после 18:00, и выходные.

2. **Окно по времени приёма + защитное условие по дате публикации.** Подборка выбирает `created_at` в `(prev_moment, this_moment]` **и** `published_at >= prev_moment.date()`. Условие по дате отсекает старые акты, попавшие в БД позже (бэкфилл создаёт строки с `created_at = now`, но 30-дневной давности). `prev_moment`/`this_moment` — запланированные моменты (пятница 18:00 в `DIGEST_TZ`), не фактическое время отправки: при догоне окна не пересекаются и не имеют разрывов.

3. **Отдельный модуль `app/services/importance.py`, функции без классов** (KISS, как `summarizer`). Публично: `score_importance(client, title, body) -> int` и константа `CANDIDATE_LEVELS = {"CONSTITUTION","FKZ","FZ","DECREE","GOV_RESOLUTION"}`. Промпты — константы модуля (prompt management, vision.md). Использует `GIGACHAT_MODEL` из конфига (`GigaChat-2-Max`).

4. **Рубрика (источник правды; финальные формулировки уточняются на калибровке и живут в константах модуля).**
   - Повышает: (1) охват — сколько людей/организаций; (2) прямое влияние на деньги, права, обязанности (налоги, штрафы, пособия, пенсии, тарифы, ипотека, уголовная/административная ответственность); (3) новизна — новый закон/кодекс/запрет/льгота против технической правки; (4) скорое вступление в силу; (5) общественный резонанс.
   - Понижает: ратификации, кадровые акты и награждения, технические уточнения («в связи с переименованием»), продления сроков, нормы для узкого круга.
   - Шкала и ориентиры долей в промпте: `3` — единицы в месяц (≲2% кандидатов); `2` — ~10–15%; `1` — основная масса; `0` — технические/кадровые/ратификации. Без ориентиров LLM завышает.
   - Приёмы точности: один запрос на одну задачу; ответ JSON `{"reason": "...", "level": N}` — поле `reason` идёт **первым** (короткое рассуждение перед меткой повышает точность) и не хранится; низкая температура (0–0.1; сейчас у суммаризации 0.3); 6–8 few-shot примеров из реальных актов (по 1–2 на уровень), подобранных на калибровке; при невалидном JSON — один повтор, затем «не оценено».

5. **Вход оценки.** Название + саммари; иначе название + начало текста (≤ ~3000 символов, константа); иначе только название — но только на финальном проходе перед отправкой. На приёме без саммари и текста оценка откладывается (текст часто появляется позже).

6. **Когда оценивать.** (а) При приёме в `_process_entry`, в собственном `try/except`: сбой оценки не должен ломать сохранение и рассылку (принцип «бот не молчит»). (б) Добор в начале каждого цикла `check_legislation_updates`: кандидаты окна без оценки, не более `N` за цикл (константа, ~20), с повторным получением текста, если его не было. (в) Финальный проход перед рассылкой — оценивает всё оставшееся, в т.ч. по названию. Отказ GigaChat (`classify_reply == "refusal"`) → сразу `2` (чувствительная тема не должна выпадать); временная ошибка → NULL и повтор.

7. **Расписание.** `JobQueue.run_daily(weekly_digest_job, time=time(h, m, tzinfo=ZoneInfo(DIGEST_TZ)), days=(5,))` — пятница по нумерации PTB 22.6 (0 = воскресенье). Конфиг: `DIGEST_TIME` (формат `HH:MM`, пусто = выключено), `DIGEST_TZ` (по умолчанию `Europe/Moscow`); валидация в `Config.load()` с `ConfigError`. День недели не настраивается (YAGNI). В `requirements.txt` добавляется `tzdata`.

8. **Идемпотентность — таблица `weekly_digest_runs`** (`period_end` — запланированный момент, уникален; `started_at`; `finished_at` NULL до конца рассылки). Задача и догон при старте проверяют: есть ли запись с `finished_at` за этот `period_end`. Пустая подборка тоже фиксируется как завершённый период (чтобы догон не пытался снова). При падении посреди рассылки `finished_at` остаётся NULL, и догон отправит подборку заново **всем** — часть пользователей получит дубль. Альтернатива — таблица доставок на пользователя — отвергнута как избыточная для масштаба проекта; семантика «минимум один раз» та же, что у `Article.notified`.

9. **Догон.** В `_post_init` после `_run_initial_check`: вычислить последний прошедший запланированный момент; если за него нет завершённого периода и сейчас не позже конца воскресенья этой недели в `DIGEST_TZ` — запустить рассылку. Позже воскресенья пропущенное не отправляется. Догон срабатывает и в первый деплой: пустая БД оценок даёт пустую подборку и пустой период фиксируется.

10. **`_build_digest` получает необязательные параметры** `header: str | None` и `sort_key`; значения по умолчанию сохраняют текущее поведение дневных дайджестов. Недельная подборка передаёт свой заголовок (константа, например «📌 Главные законы недели — N» + пояснение «еженедельная подборка по пятницам», точный текст — при реализации) и упорядоченный список (`importance` ↓, `published_at` ↓). Альтернатива — отдельная функция сборки недельного сообщения — отвергнута: дублирует разметку и логику кнопок «Сделать саммари».

11. **Рассылка.** Получатели — те же, что в `_notify_users_batch` (активные, `channel_verified`), без `UserFilter`; отправка через существующий `_send_notification` (обработка `Forbidden`) с той же анти-спам паузой. Один и тот же текст/клавиатура строится один раз.

12. **Предпросмотр.** `/test_digest weekly` расширяет `test_digest_command` (проверка `ADMIN_CHAT_IDS` уже есть): строит подборку за текущее окно (последний запланированный момент → сейчас) тем же селектором, отправляет только администратору, **не** пишет в `weekly_digest_runs`, и добавляет второе сообщение со списком `external_id` и оценок.

13. **Калибровка.** Скрипт `scripts/calibrate_importance.py` + файл разметки `scripts/importance_golden.csv`: пользователь размечает ~40 актов из пачки 04.08.2026 (59 актов — от технических поправок до крупных), скрипт прогоняет `score_importance`, печатает матрицу ошибок и список расхождений. Критерий готовности (согласован на калибровке): граница `1/2` верна на подавляющем большинстве эталонных актов, `3` не раздаётся щедро. Это разовый инструмент, а не тесты репозитория (проект не стремится к полному покрытию).

## Risks / Trade-offs

- [Модель завышает/занижает границу `1/2`: каждая завышенная `2` попадает всем подписчикам] → ориентиры долей в промпте, few-shot, калибровка на эталоне, админский предпросмотр перед включением `DIGEST_TIME`.
- [Отказы GigaChat приходятся именно на важные темы] → отказ = `2` (пусть лучше лишний показ, чем потеря); при сбое — повторы и оценка по названию на финальном проходе.
- [Дубль подборки части пользователей при падении посреди рассылки] → принято сознательно (см. п. 8); редкость и низкая цена.
- [Оценка по названию точна хуже] → применяется только на финальном проходе, когда ни саммари, ни текста так и не появилось.
- [Пакетные дни (59 актов) = десятки вызовов GigaChat подряд, возможны лимиты] → добор ограничен числом за цикл; приём не блокируется оценкой.
- [`DIGEST_TIME` задан без `WEBAPP_URL`: пользователь видит только 3 закона без кнопки] → предупреждение в лог при старте; конфигурация рассылки без WebApp считается ошибкой настройки, а не поддерживаемым режимом.
- [Неверная нумерация дней в PTB (воскресенье = 0)] → зафиксирована в п. 7, покрыта ручной проверкой расписания в задачах.

## Migration Plan

1. Выкатить `fix-ingestion-pagination` (предусловие).
2. Выкатить этот change с пустым `DIGEST_TIME`: миграции колонок, оценка при приёме и добор работают, рассылки нет.
3. Накопить оценки, сверить с эталоном и проверить подборку через `/test_digest weekly`.
4. Задать `DIGEST_TIME=18:00` (и `DIGEST_TZ`) в `.env` прода; первая рассылка — ближайшая пятница.
5. Откат: очистить `DIGEST_TIME` — рассылка выключается без отката кода и БД; колонки и таблица безвредны при отключении.
