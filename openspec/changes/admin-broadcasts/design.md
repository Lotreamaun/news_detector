## Context

- Отправка пользователю уже отлажена в `app/services/scheduler.py`: `_send_notification` → `_deliver_notification` повторяет при 429, при 403 ставит `is_active = False` и возвращает `None`, пишет `notify.sent` / `notify.failed`. Обе функции берут PTB-`context`, но используют только `context.bot`. Отправка всегда идёт с `parse_mode="MarkdownV2"`.
- Админ-панель — aiohttp в том же процессе (`app/webapp/admin.py`): `require_admin` (initData или cookie-сессия), POST только с `X-Admin-Panel: 1` и JSON. У приложения есть `app["bot"]` и `app["session_maker"]`. Вкладки в `admin.html`: «Подборка» и «Статистика».
- Схема БД создаётся `create_all` при старте: новые таблицы появляются сами, ALTER не нужен.
- Гейт канала: все обработчики, кроме явного allowlist в `app/main.py`, обёрнуты в `require_channel_verified`.
- `track_activity` (группа -1) пишет любое нажатие инлайн-кнопки как `button` с первыми двумя сегментами `callback_data`.
- Масштаб: ~50 живых получателей. Рассылка на всех занимает несколько секунд.

## Goals / Non-Goals

**Goals:**
- Рассылка уходит каждому получателю не больше одного раза и доходит до конца после рестарта.
- Отправка, 403 и журнал работают тем же кодом, что и обычные уведомления.
- Ответ на опрос можно привязать к рассылке и сегменту, а итоги видны без SQL.

**Non-Goals:**
- Очередь рассылок, приоритеты, ограничение скорости сверх существующей паузы 0,05 с.
- Аналитика по отдельным ответившим (кто что выбрал): в панели только числа по вариантам.
- Строго «ровно один раз»: допускается один дубль на рестарт (см. Risks).

## Decisions

### 1. Три таблицы: рассылка, доставка, ответ

- `broadcasts`: `id`, `created_at`, `created_by` (Telegram ID админа), `text`, `options` (JSON-список из 0–4 строк), `action_kind` (`link` / `check_subscription` / NULL), `action_label`, `action_url`, `segment`, `recipients` (число в момент запуска), `status` (`sending` / `done`), `finished_at`, `client_token` (уникальный).
- `broadcast_deliveries`: PK (`broadcast_id`, `telegram_id`), `status` (`pending` / `sent` / `blocked` / `error`), `sent_at`.
- `broadcast_answers`: PK (`broadcast_id`, `telegram_id`), `option` (индекс варианта), `answered_at`.

Строки доставки создаются сразу при запуске, в одной транзакции с рассылкой. Это и снимок аудитории (пришедший позже пользователь рассылку не получит), и состояние для возобновления, и источник итогов. Альтернатива — держать прогресс в памяти и снимок в JSON — теряет состояние при рестарте, а итоги «кто получил» пришлось бы собирать из журнала событий, у которого нет ссылки на рассылку.

Ответ — отдельная таблица с PK (рассылка, пользователь): «один ответ на человека, учитывается последний» превращается в upsert. Писать ответы только в журнал событий нельзя: у `button` нет варианта ответа (только первые два сегмента), а журнал чистится через 365 дней.

### 2. Сегменты — фиксированный список функций, админы исключены

| Сегмент | Условие |
|---|---|
| `subscribers` | `is_active AND channel_verified` (как у обычной рассылки) |
| `active_14d` | `subscribers` с событием из `stats.ACTIVE_KINDS` за 14 дней |
| `silent_14d` | `subscribers` без таких событий за 14 дней |
| `unverified` | `is_active AND NOT channel_verified`; доступен только при заданном `REQUIRED_CHANNEL_ID` |

`active_14d` и `silent_14d` в сумме дают `subscribers`, так что группы не пересекаются и легко сравнивать ответы. Новые пользователи не попадают в «молчунов» по ошибке: кнопки онбординга считаются активностью.

`ADMIN_CHAT_IDS` исключаются из всех сегментов, как из метрик Пульса: иначе голос админа смешается с ответами пользователей. Как сообщение выглядит, админ видит через тестовую отправку (решение 6).

Конструктор условий не делаем: четырёх сегментов хватает для пилота (напоминание гейта) и для вопросов «что нравится / что отталкивает». Новый сегмент — одна функция.

### 3. Отправка — фоновая задача в процессе панели через существующую доставку

`_send_notification` и `_deliver_notification` переходят с `context` на `bot`. Вызовы в `scheduler.py` передают `context.bot`, логика не меняется. Тогда `run_broadcast(bot, session_maker, config, broadcast_id)` из `app/services/broadcasts.py` вызывается и из обработчика панели, и из `post_init`.

Цикл: читаем `pending`-строки рассылки по порядку, для каждой вызываем `_send_notification(..., kind="broadcast")`, сразу пишем статус строки (`True` → `sent`, `None` → `blocked`, `False` → `error`) и `sent_at` с отдельным commit, затем пауза 0,05 с. Когда `pending` закончились — `status = done`, `finished_at`. Задачи держим в модульном `set` (как `events._pending`), чтобы их не собрал GC.

Текст админа экранируется `escape_markdown(version=2)` целиком, поэтому `MarkdownV2` в `_deliver_notification` не мешает: пользователь видит ровно введённый текст. Отдельный режим без разметки не вводим.

Альтернатива — `job_queue.run_once` из панели: у aiohttp-приложения нет `Application`, пришлось бы протаскивать его в `create_app`. Переход на `bot` проще и делает функции доставки независимыми от PTB-контекста.

### 4. Одна рассылка одновременно, защита от двойного клика

Запуск отклоняется (409), если есть рассылка в `sending`. Две параллельные рассылки удвоили бы скорость отправки, а пользу при ~50 получателях не дали бы. Клиент генерирует `client_token` при открытии формы. Повторный POST с тем же токеном возвращает уже созданную рассылку, а не новую (уникальный индекс плюс проверка перед вставкой).

### 5. Возобновление после рестарта

`post_init` после старта панели находит рассылки в `sending` и запускает для каждой `run_broadcast`. Обычно такая одна, см. решение 4. Отправляются только `pending`-строки.

### 6. Кнопки и ответ

- Вариант ответа: `callback_data = "bc:<id>:<n>"`. `track_activity` сам пишет `button` с `bc:<id>`, без варианта. Ответ отдельно в журнал не пишется.
- Обработчик `^bc:` регистрируется **без** `require_channel_verified` (правка allowlist в спеке гейта). Проверки: рассылка существует, `n` в пределах `options`, у пользователя есть строка доставки этой рассылки. Подделанный callback от не-получателя отбрасывается. Дальше upsert ответа, `query.answer("Спасибо!")`, правка клавиатуры: у выбранного варианта ✓, кнопка действия остаётся. «Message is not modified» игнорируется (как `_edit_ignoring_not_modified`).
- Кнопка действия: `link` — URL-кнопка (только `https://`); `check_subscription` — кнопка с тем же `callback_data`, что в онбординге. Обработчик уже есть и уже вне гейта.
- Тестовая отправка шлёт сообщение только вызвавшему админу, в таблицы не пишет. Варианты получают `bc:0:<n>`, и обработчик на `id = 0` отвечает всплывашкой «Тестовая рассылка — ответ не сохраняется».

### 7. Ограничения ввода (проверяет сервер)

Текст 1–3500 символов, и после экранирования не длиннее 4096. Вариантов 0–4, каждый 1–40 символов, без повторов. Подпись кнопки действия 1–40 символов. URL только `https://`. Сегмент из списка, `unverified` только при включённом гейте. Если пользователей в сегменте 0, запуск отклоняется.

### 8. API и вкладка

- `GET /admin/api/broadcasts/audience?segment=` → `{count}`.
- `POST /admin/api/broadcasts/test` → отправка себе.
- `POST /admin/api/broadcasts` → запуск, `{id, recipients}`.
- `GET /admin/api/broadcasts` → список (новые сверху, последние 20) с итогами: `sent / blocked / error / pending`, ответы по вариантам (число и доля от `sent`).

Маршруты добавляются в `setup_admin` всегда (панель уже требует `WEBAPP_URL` и `ADMIN_CHAT_IDS`), вкладка «Рассылки» не прячется. Форма: текст, 4 поля вариантов, выбор действия, сегмент с живым счётчиком, «Отправить себе» и «Разослать N получателям». Подтверждение — повторное нажатие («Нажмите ещё раз, чтобы разослать N»), без `confirm()`: в Mini-App он ведёт себя по-разному. Пока есть рассылка в `sending`, список опрашивается раз в 3 с.

### 9. Журнал и Пульс

Новый вид `broadcast.started` (системный, `ref = "<id>:<recipients>"`), строка в `stats._describe`: «📣 рассылка #id запущена · получателей: N». Доставка идёт как `notify.sent` / `notify.failed` с `ref = broadcast`, поэтому плитка «Доставка» в Пульсе включает рассылки. Это правильно (это доставка), но текст в `HINTS` надо поправить.

## Risks / Trade-offs

- [Рестарт между отправкой и commit статуса] → получатель увидит сообщение дважды. При ~50 получателях и редких рестартах это допустимо; хранить `message_id` и сверяться с Telegram нельзя: API не умеет спрашивать «доставлено ли».
- [Рассылка раздражает и ведёт к блокировкам] → итоги показывают `blocked` по рассылке; панель предупреждает числом получателей перед запуском. Отдельной метрики «заблокировали в течение 48 ч после рассылки» нет, при необходимости это следующий шаг.
- [Сегмент `unverified` на момент пилота: многие из 23 могли уже заблокировать бота] → 403 сам их деактивирует, а итог `blocked` покажет, сколько аудитории волны ещё живо.
- [Рассылка совпала с циклом уведомлений] → суммарная скорость выше паузы 0,05 с. 429 обрабатывается повтором в `_deliver_notification`.
- [Подделка `callback_data`] → ответ принимается только от получателя этой рассылки, индекс проверяется.
- [Смена сигнатуры `_send_notification` / `_deliver_notification`] → три вызова в одном файле, поведение то же. Проверяется обычной рассылкой и недельной подборкой после деплоя.

## Migration Plan

Таблицы создаются при старте. Откат — предыдущий образ: новые таблицы останутся неиспользуемыми и ничему не мешают. Первый запуск на проде: тест себе, затем пилот на сегменте `unverified` с кнопкой «Проверить подписку».
