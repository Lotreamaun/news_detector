## MODIFIED Requirements

### Requirement: Целостность резервной копии
Каждая резервная копия SHALL быть валидным, самодостаточным файлом БД, пригодным для
восстановления путём простой подстановки вместо основного файла — включая случай, когда
бэкап создаётся в момент, когда приложение параллельно читает или пишет в БД (копия не
SHALL быть частично записанной или повреждённой из-за гонки с активной транзакцией).
Когда основная БД работает в режиме журнала WAL, копия SHALL содержать все записи,
зафиксированные до начала бэкапа, включая ещё не перенесённые из WAL-файла в основной файл,
и SHALL оставаться одним файлом без сопутствующих `-wal`/`-shm`. При восстановлении служебные
файлы `-wal`/`-shm` старой базы SHALL удаляться до подстановки копии, иначе SQLite применит
их к подставленному файлу.

#### Scenario: Бэкап во время активной записи
- **WHEN** резервное копирование запускается в момент, когда приложение сохраняет новую
  статью или обновляет пользователя в БД
- **THEN** результирующий файл бэкапа остаётся валидной, не повреждённой БД, открываемой без
  ошибок целостности

#### Scenario: Свежие записи из WAL попадают в копию
- **WHEN** незадолго до бэкапа зарегистрировался новый пользователь, и его запись ещё
  находится только в WAL-файле основной БД
- **THEN** этот пользователь есть в файле бэкапа, открытом отдельно, без WAL-файла основной БД

#### Scenario: Восстановление из копии
- **WHEN** бот остановлен, служебные файлы `-wal`/`-shm` основной БД удалены, и файл бэкапа
  подставлен по пути из `DATABASE_URL`
- **THEN** бот стартует на восстановленной базе, пользователи, фильтры и статьи соответствуют
  моменту бэкапа
